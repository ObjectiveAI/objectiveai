# Response module fidelity audit, pass 3

Third three-slice sweep, after: flat `StopReason`, flat rate-limit
enums, the de-globbed `response/mod.rs`, the no-skip-serialize
nullable param fields, and `PermissionMode::Bubble`. Everything fixed
or previously ruled is omitted. Load-bearing claims re-verified at
the emission sites.

The changed surfaces themselves all verified clean: the flat
`StopReason` round-trips losslessly with no from/into-under-Option
gotcha; all 21 rate-limit literals byte-match schema AND producer
aliases, `unknown` distinct from `Other`; the eleven
no-skip-serialize fields map one-to-one onto the d.ts's
optional-AND-nullable set with the retained skips all
optional-not-nullable; `ApiKeySource`'s four non-identifier renames
each confirmed against a literal return site; `PermissionMode`'s
seven byte-match the internal union.

## New findings

### 1. The assistant-record `usage` is missing six wire fields — HIGH

- Rust: `message/usage.rs` — four fields, faithfully `BetaUsage` at
  SDK 0.39.
- Truth: the emitters write a ten-plus-key usage into every
  assistant message. The synthetic default (`messages.ts:362-376`,
  verified) carries `server_tool_use {web_search_requests,
  web_fetch_requests}`, `service_tier`, `cache_creation
  {ephemeral_1h_input_tokens, ephemeral_5m_input_tokens}`,
  `inference_geo`, `iterations`, `speed`; the real accumulators
  (`claude.ts:2947-3035`) read and write the same; real API messages
  reach stdout by verbatim spread. This is the SAME richer shape
  `result::Usage` already models from `EMPTY_USAGE` — the message-
  level port just stopped at the pinned d.ts.
- Consequence: parse succeeds, but decode→encode silently drops six
  fields from every assistant record — data loss, not failure.
  Natural fix: widen `message::Usage` the way `result::Usage`
  already is (extras optional/defaulted; note several are NULLABLE
  here — `service_tier: null` etc. — so `Option` without skip).

### 2. `Message` is missing `container` — MEDIUM

- Every synthetic assistant message emits `container: null`
  (`messages.ts:392`, verified — the line right above the
  `context_management` the port DOES carry); real messages spread
  whatever the API returns. Same injected-sibling class as
  `context_management`, handled inconsistently — looks like
  oversight, same silent-drop consequence. Shape unknown at the
  pinned SDK → `Option<serde_json::Value>`, like its sibling.

### 3. `ContentBlock`'s four variants reject block types the stream path really carries — MEDIUM

- The source's own exhaustive switch over `content_block.type` on
  the `content_block_start` path (`messages.ts:3011-3045`, verified)
  names, beyond our four: `server_tool_use`,
  `web_search_tool_result`, `code_execution_tool_result`,
  `mcp_tool_use`, `mcp_tool_result`, `container_upload`,
  `web_fetch_tool_result`, `bash_code_execution_tool_result`,
  `text_editor_code_execution_tool_result`,
  `tool_search_tool_result`, `compaction`.
- These arise when server-side tools / MCP-connector betas are in
  play; Claude Code passes the blocks through verbatim. With the
  strict four-variant union, such a record hard-fails the whole
  line. Our container's agents may never enable those betas — but
  the failure mode is a dead stream, and the precedent for
  API-owned open vocabularies is already set by `StopReason`.
  Candidate fix if wanted: an `Other(serde_json::Value)` tail on
  `ContentBlock` (and `ContentBlockDelta`'s start-block payloads)
  — degraded block instead of dead line.

### 4. Doc links orphaned by the de-globbing — LOW

- `assistant.rs` (`super::System::ApiRetry`), `result.rs`
  (`super::System::SessionStateChanged`), and `message/mod.rs`'s
  three (`super::Assistant`, `super::StreamEvent`, `super::User`)
  now dangle — the glob that made those paths resolve is gone.
  Rustdoc-warning only; needs `super::system::System::…`-style
  qualification. Every other link and every non-doc `use` verified
  resolving.

### 5. `StopReason::Compaction` could not be corroborated as a stop reason in the clone — LOW

- The clone's only `'compaction'` literals are content-BLOCK type
  discriminants, not stop reasons. Our variant came from the api
  crate's port of a newer SDK, which does list it; if that port is
  trusted (it was mechanical), the variant is right and merely
  uncorroborated by this clone. Harmless either way — without the
  variant the value would land in `Other("compaction")` losslessly.
  Also: the doc says "the current API documents eight"; if
  compaction is counted the eight is right, otherwise seven.

### 6. The live control-request vocabulary is wider than the published union — INFORMATIONAL

- The stdin dispatcher handles twelve subtypes absent from
  `SDKControlRequestInnerSchema` and from our 21: `end_session`,
  `channel_enable`, `mcp_authenticate`, `mcp_oauth_callback_url`,
  `claude_authenticate`, `claude_oauth_callback`,
  `claude_oauth_wait_for_completion`, `mcp_clear_auth`,
  `generate_session_title`, `side_question`, `set_proactive`,
  `remote_control` (print.ts:2850-3892). All stdin-only; the only
  OUTBOUND producer sends four (`can_use_tool`, `hook_callback`,
  `elicitation`, `mcp_message`), so no stdout line can fail on
  these. Matters only if these types ever drive stdin.

### 7. `initialize.agents` is consumed by a different schema than the one published — INFORMATIONAL

- The runtime parser (`parseAgentsFromJson` → `AgentJsonSchema`,
  `loadAgentsDir.ts:73-99`) accepts `hooks` and `isolation`
  (neither in the published `AgentDefinitionSchema` nor our
  `AgentDefinition`) and does NOT accept
  `criticalSystemReminder_EXPERIMENTAL` (which both carry). A
  source-side schema/consumer inconsistency; serde tolerates the
  extras on read, loses them on re-serialize. Recorded, not a port
  error.

## Verified clean this pass

- The five changed surfaces, as summarized up top.
- All marker literals across all thirteen record files and the
  control slice, re-expanded and byte-checked.
- Emitter-side enum tracing across the control slice found NO new
  `ApiKeySource`-class leak: all 27 hook_event_names, session
  sources, exit reasons, config-change sources, elicitation
  actions/modes, permission behaviors/destinations — every emitted
  value is inside its schema enum. One near-miss chased and
  cleared: the wider `MemoryType` (`AutoMem`/`TeamMem`) is guarded
  by `isInstructionsMemoryType()` at both dispatch sites and cannot
  reach `InstructionsLoaded`.
- The 13 internal-only system subtypes re-confirmed unreachable
  from any stdout sink; `RateLimitInfo`'s field set matches its
  sole producer exactly (`unifiedRateLimitFallbackAvailable` is
  never copied in); no fractional/negative producer feeds any
  remaining integer field.
- `pending_permission_requests` can only ever carry `can_use_tool`
  entries (the producer filters), so the recursive `Vec<ControlRequest>`
  never sees an exotic subtype.
- `permission_mode` on hook inputs is correctly a plain
  `Option<String>` (the base schema says `z.string().optional()`),
  noted explicitly so it isn't later "fixed" into the enum.
