# Report 5 — status: from typed wire to working container

Reports 1–4 audited one thing: whether `src/response` tells the
truth about Claude Code's stdout. Since then the crate has grown
from a typed wire into most of a container — a queue protocol in the
provider SDK, a reference implementation of it in openrouter, and in
cc itself the subprocess machinery, the queue verbs with strict
fates, the chunk conversion, and an error policy. This report is the
state of all of it: what exists, the decisions that shaped it, and
what deliberately does not exist yet.

## 1. Where the crate stands

```

  continuation.rs    token = the session's files; parse/tokenize/write/read
```

`cargo check` and `cargo doc` both clean throughout; every step
landed as a pathspec commit.

## 2. Provider SDK: the queue protocol

New client-sent channel requests and their response channels, plus a
root module all agentic-loop containers share:

- **`enqueue`** — `{prompt: String}`. The response IS the fate, and
  it arrives only when the fate is known — no timeout anywhere:
  `delivered` (the agent took the message into the conversation),
  `dequeued` (the caller withdrew it first), `missed` (the run ended
  before it could be taken; nothing malfunctioned — resend it as the
  next run's prompt if it still matters).
- **`dequeue`** — empty payload, clears the WHOLE queue. Answers
  `dequeued` or `empty`. Each withdrawn message's own enqueue
  answers `dequeued` individually.
- **`user` chunk** — a new response chunk carrying the prompt
  verbatim; its position in the stream marks where the delivered
  message entered the conversation.
- **`agentic_loop_container`** — the root module every container
  implements: `request`/`response` aliases, the enqueue/dequeue
  request and response shapes, routes (`POST /enqueue`,
  `POST /dequeue` beside `POST /` on 8080). No in-band error
  variants: a container that cannot answer says so as HTTP does,
  with a non-2xx status and a JSON body.

## 3. Openrouter: the reference implementation

The sibling container implements the protocol with its own queue,
since IT owns the conversation loop:

- One root request per container lifetime — an atomic-swap CLAIMED
  guard; the second arrival gets `409 {"kind":"claimed"}`.
- A global tokio-mutex queue; delivery at the loop's two seams:
  messages folded onto the tool-response turn inside one
  `<system-reminder>` section (derived at message-construction time
  only — the continuation stores bare `Prompt` items), or opening a
  new turn.
- Categorical fate delivery: `take_or_close` closes the queue under
  the same lock hold that proves it empty; a `CloseOnDrop` guard
  constructed as the loop's first act covers unpolled drops and
  panics; the enqueue window is maximized by tokenizing the
  continuation speculatively before the last look.

## 4. cc: the subprocess (`spawn/`)

cc does NOT own the loop — Claude Code does — so the container's
queue machinery is a bridge to CC's own: enqueues become stream-json
stdin `user` messages, dequeues become `cancel_async_message`
control requests, and the fates are read back off stdout.

### The architecture, as it settled

The design iterated hard and is worth recording:

1. A writer TASK owning stdin behind a command channel — built,
   then eradicated.
2. One global mutex holding (stdin, uuid vec, reply receiver) —
   simpler, but fate tracking was write-time-optimistic.
3. **Final**: two mutexes and a map. `WRITER` holds stdin: holding
   it is the sole right to write AND to register a fate — the
   pairing invariant. `REPLIES` holds the cancel-reply receiver; the
   reader task permanently holds the matching sender, so reading
   replies is a right only the lock holder has. `PENDING` (dashmap,
   beside the locks, never under them) maps each enqueued uuid to a
   oneshot fate wire; its keys ARE the queue as this container
   knows it.

A fourth global — a FIFO "gate" mutex drawing the withdrawal
boundary — was added and then deleted on the realization that
tokio's writer mutex is itself FIFO-fair: **a dequeue's position in
the writer's wait queue IS the boundary**. Everything ahead of it
registers and is withdrawn; everything behind is out of reach. The
gate was a redundant prefix of a queue that already existed, and
removing it restored the fully parallel `join!(WRITER, REPLIES)`
acquisition with no lock-order cycles (the gate could not join that
join: enqueue held gate-then-writer, a genuine deadlock).

### Strict fates — the triangle

An enqueue answers when its fate is truly known, not when its write
lands:

- **Delivered** — the reader sees the replay echo
  (`--replay-user-messages`; `isReplay: true` + our uuid), removes
  the PENDING entry, sends the fate, and pushes the `user` chunk at
  exactly that stream position (CC yields tool responses BEFORE the
  replay, so the mark lands behind the answers it followed).
- **Dequeued** — the dequeue writes one cancel per snapshotted uuid
  and, still holding the locks, reads CC's `control_response`
  replies (matched by request id; stale ids from an abandoned
  dequeue skipped). Each reply's `cancelled` flag decides that
  message's fate strictly: `true` → dequeued; `false` → the queue no
  longer held it, so its true fate is delivered. The dequeue's own
  HTTP verdict is receipt-based: all replies in → `dequeued`.
- **Missed** — a failed write (the process dying), a fate wire dying
  undecided, an enqueue with no session, or the reader's
  end-of-stream drain, which misses everything still pending AFTER
  the writer is cleared — so nothing can register behind the drain.

Dequeue holds each lock exactly as long as its job: the writer from
snapshot through the cancel flush (then enqueues flow again — they
write no control responses, so reply attribution survives), the
replies until the last reply is in.

### The deadlock audit (standing)

The reader never takes a lock while reading — only at end of
stream, AFTER dropping the reply sender (so a mid-wait dequeue wakes
on the closed channel), and then one lock at a time. Dequeue is the
only holder of two locks at once, acquired jointly. Stdout always
drains while an enqueue blocks on a full stdin pipe, so the
pipe-backpressure cycle cannot close.

## 5. cc: stdin (`spawn/stdin.rs`)

Serialize-only, the mirror of `response`'s deserialize-only: the
`user` message line (content + the correlation uuid the replay
echoes back) and the `control_request`/`cancel_async_message` line —
the only two things this container ever says. Plus the line
writers (`user_message_line`, `write_lines`). The vocabulary is
deliberately narrow: a shape nothing sends is a shape nobody has had
to be right about.

## 6. cc: the conversion (`response::*::into_chunks`)

Openrouter's conventions, applied strictly: a uniform
`into_chunks(self, chunks: &mut Vec<AgenticLoopChunk>)` on each
response type; every parent delegates each child field to the
child's own method; SDK-chunk literals only at leaves with
`r#type: Default::default()`; rmcp inners via their constructors
(`TextContent::new`, `CallToolResult::success/error`,
`ContentBlock::text/image` — `CallToolResult` is non_exhaustive, so
constructors are mandatory anyway).

The mapping doctrine:

- **Usage: the `result` record ONLY** — the api crate's doctrine,
  verified against its source and kept: per-message usage is never
  read, nothing accumulates, `prompt_tokens = input + cache writes +
  cache reads`, one UsageChunk per run, emitted for BOTH result arms
  (an error result still spent the tokens). Per-model shares,
  dollar cost and durations have no chunk home and are dropped.
- **Assistant blocks**: text → text chunk (citations dropped);
  thinking → reasoning chunk (signature dropped — api parity); ALL
  THREE tool-use kinds (client, server, MCP-connector) → tool-call
  chunks, arguments as the JSON they already are (api parity —
  report 4 would have predicted only the client kind). Redacted
  thinking, the server-tool result kinds, container uploads,
  compaction: silent, as the api drops them all.
- **User records**: `tool_result` blocks → ToolResponse chunks
  (`is_error` picks MCP's arm; content renders text and base64
  images faithfully, URL images as their address, search results /
  documents / tool references in the api's synthesized-element text
  forms), plus the api's subagent fallback (`tool_use_result` +
  `parent_tool_use_id` → the JSON as one text block answering the
  spawning call). Bare user prose is the prompt, not a chunk.
- **Subagent narration** (assistant records with
  `parent_tool_use_id`) is skipped — the sidechain's outcome arrives
  as the spawning call's tool result.
- The dispatch enumerates every silent record kind with its reason.

The reader wires it: sender carries
`Result<AgenticLoopChunk, spawn::Error>`, one reusable buffer, taps
before conversion (cancel replies → REPLIES; replay deliveries →
fate + `user` chunk).

## 7. cc: the positional error policy

Error-typed records are judged by POSITION relative to the first
assistant message (`assistant_seen`, flipped only by an assistant
record with no error marker — a synthetic failure stand-in is not
the model speaking):

- **Before** it, they are the request's own failure and travel as
  the stream's `Err` the moment they are seen — openrouter's
  "status before the stream" made streamwise; chunks are forfeited
  with the failed request (an early error result loses its usage
  chunk, exactly as openrouter's pre-stream failures emit nothing).
- **After** it, they are news inside a working run: a rejected rate
  limit → NON-fatal notification (Claude Code queues and retries
  through it on its own — the automatic retry is CC's, which is the
  whole reason not to kill anything); a failed auth status → fatal
  notification (nothing to wait out); an error result → its
  conversion's fatal notification plus the bill.

The error-typed set: `RateLimitEvent` with `status == rejected`
(allowed/warning/queueing are the limiter coping and stay silent);
`AuthStatus` with `error` carried — the argv now passes
`--enable-auth-status`, without which the record cannot occur;
`Result::Error`. Considered and EXCLUDED: assistant-record `error`
markers and `api_retry` narration — CC's retry in flight, whose
terminal verdict arrives as the result record; notifying on them
would report every failure twice.

`spawn/error.rs` carries the whole records as payloads
(`Parse`/`RateLimit`/`Auth`/`Result`) so the root handler can pick
HTTP status and body when it lands. The reader keeps draining after
any `Err` — fates, control replies and reaping continue; aborting
is the consumer's choice.

## 8. Deliberately not done yet

- **The root handler** (`POST /`): the CLAIMED guard, agent/
  continuation validation, the `spawn()` call, SSE-framing the chunk
  stream, mapping `spawn::Error` to status/body, and at exit the
  `Continuation::read` harvest → `tokenize` → Continuation chunk.
  Everything it needs now exists.
- **Claude Code installation** in the Containerfile (the argv
  assumes `claude` on PATH).
- **Skills / claude_code_agents mounting**: the SDK's `Fetch`
  channel (kind + dirhash → per-file frames) and the agent fields
  exist; the server-side fetch-and-mount flow does not.
- **SDK client executor wiring** for the enqueue/dequeue channels,
  and the server handle (the big refactor still pending).
- **`--include-partial-messages`** — a conversion-scope decision,
  currently off; content arrives as whole blocks per record.
- **Rich-content prompts** (stdin is text-only today) and
  enqueue-time content blocks.
- **`meta`/provenance stamping** on chunks (openrouter stamps an
  upstream id; we have nothing to stamp yet, by decision).
- **session_id capture** for the harvest — trivial, but it belongs
  to the root handler.
- **Spec site pages** for the queue feature and the cc container.

## 9. Open questions and accepted edges

- A message dequeued mid-delivery may still enter the conversation;
  its fate was answered `dequeued` and its replay taps nothing — no
  `user` chunk. Consistent with the answer given; accepted.
- A cancel answered by an `error` control response (which the source
  cannot produce for `cancel_async_message`) leaves that fate for
  the end of stream to miss — visible drift rather than a silent
  guess.
- The `user` chunk on a replay renders blocks' text joined by blank
  lines; enqueues write plain strings today, so this is verbatim in
  practice.
- Report 3 item 3 (an `Other(Value)` tail for content blocks vs.
  strict failure) remains decided in favor of strictness: the image
  pins CC's version, so the union is closed by construction.
- Report 1 cosmetics (items 7, 8, 10, 11) remain open and cosmetic.
- The channel-frame `Error` variants consistency question (SDK-wide)
  remains noted and unruled.
