# Response module fidelity audit, pass 2 — after the untagged refactor

Fresh three-slice sweep (message/, records, control/) against the
Claude Code source and the pinned SDK d.ts, focused on the surface the
untagged conversion created plus a full re-diff. Everything already
fixed (ApiKeySource union, fractional retry_delay_ms, optional bare
unknowns, the nested ControlRequest literal) or already ruled fine
(number narrowing, McpServerStatus, UserRole, `Auto`) is omitted.
Load-bearing claims re-verified against the source directly.

Still open from `1.md`, unchanged, not re-elaborated: items 7
(Option leniency both directions), 8 (`result::Usage` doc vs its
`#[serde(default)]`s), 10 (`max_turns` admits 0), 11
(`context_management` round-trip).

## New findings

### 1. `StopReason` is a closed four, and the emitter passes through a wider API vocabulary — HIGH

- Rust: `message/assistant.rs` — `enum StopReason { EndTurn, MaxTokens,
  StopSequence, ToolUse }`, used by `Message.stop_reason` and
  `MessageDelta.stop_reason`.
- Truth: Claude Code copies the RAW API value onto the outgoing
  message verbatim (`claude.ts:2242,2247`), and its own code branches
  on values outside the four: `model_context_window_exceeded`
  (`claude.ts:2279`, documented at `withRetry.ts:386` — "the API now
  returns 'model_context_window_exceeded' stop_reason instead" of a
  400) and `refusal` (`errors.ts:1185-1188`). The pinned SDK's
  four-value union is simply older than the API the source actually
  talks to; the field is a passthrough, so the wire vocabulary is the
  API's, open-ended.
- Failure: an API refusal or context-window stop makes the assistant
  record (or a `message_delta` stream event) unparseable — and under
  the untagged top level the error is a whole-line "did not match any
  variant". Same defect class as `ApiKeySource`: the local type
  declaration is not what the wire carries. Candidate fixes: add the
  two known extra variants, or accept the field is open and widen to
  a string-or-known union.

### 2. All four `rate_limit_event` enums are unchecked casts of raw HTTP headers — MEDIUM

- Rust: `rate_limit_event.rs` — `RateLimitStatus` (3), `RateLimitType`
  (5), `OverageDisabledReason` (13) as closed enums (status appears
  twice: `status`, `overageStatus`).
- Truth: every one is `headers.get(…) as <ClosedUnion>` with no
  validation (`claudeAiLimits.ts:379-404`, `errors.ts:511-515`),
  passed straight to the wire by `toSDKRateLimitInfo`
  (`mappers.ts:221-252`). The source's own display code is defensive
  about unknown values (`RATE_LIMIT_DISPLAY_NAMES[type] || type`,
  `claudeAiLimits.ts:87-88`). One concrete wrinkle: `rateLimitType`
  is read from `anthropic-ratelimit-unified-representative-claim`,
  and the same file's claim vocabulary elsewhere uses abbreviations
  (`'5h'`, `'7d'` — `claudeAiLimits.ts:73-77`) that are cast without
  passing through the mapping — if the header speaks that vocabulary,
  the wire value is `"5h"`, which nothing local admits.
- Failure: a server-side addition (or the abbreviation case) kills
  the whole `rate_limit_event` line. Exactly the `ApiKeySource` class,
  not yet widened. These records are also purely informational to the
  harness, which strengthens the case for tolerance here.

### 3. `SuccessSubtype` is defined twice and both reach the same glob namespace — LOW

- `result.rs` and `control/mod.rs` each define `pub enum
  SuccessSubtype` (new marker types from the refactor), and
  `response/mod.rs` glob-re-exports both (`pub use control::*;`,
  `pub use result::*;`). Rust tolerates colliding glob imports until
  someone NAMES the ambiguous path — `response::SuccessSubtype` is a
  hard error the first time it's referenced. Compiles today; a trap
  for the harness tomorrow. (Rename one, e.g. the control one to
  `ResponseSuccessSubtype`/`ResponseErrorSubtype`, or drop the glob.)

### 4. Serialize-side: `null` collapses to absent on optional-AND-nullable param fields — LOW

- In the SDK d.ts, `cache_control` and text-param `citations` are
  `?: X | null` — both spellable, distinct. The Rust fields carry
  `skip_serializing_if`, so a parsed explicit `null` re-serializes as
  key-absent. Read side unaffected. New nuance beyond `1.md` item 7
  (which covered the accept-side leniency): this is the emit side,
  and only for the fields that are BOTH optional and nullable.

### 5. Latent: the internal permission-mode union has a seventh value, `bubble` — NOTE

- `permissions.ts:28` — `InternalPermissionMode = … | 'auto' |
  'bubble'`; `forkSubagent.ts:67` sets it, and `system/init`'s
  `permissionMode` is an unguarded cast from the store. Reachability
  onto stdout could NOT be demonstrated (the store's initial mode is
  validated against a list excluding `bubble`, the fork override
  lives in a closure, and the `status` emitter whitelists six), so
  this is recorded as latent rather than live. If `PermissionMode`
  is ever widened again, add `Bubble` alongside.

### 6. Diagnostics regression from the untagged conversion — INFORMATIONAL

- By construction, ANY leaf failure anywhere in a line — an unknown
  enum value, a missing field five levels deep — now surfaces as
  "data did not match any variant of untagged enum StdoutMessage",
  with no path and no offending value. Findings 1 and 2 would both
  manifest that way. Not a fidelity issue; worth remembering when the
  harness grows error reporting (a `serde_path_to_error`-style probe
  on failed lines would recover the detail).

### 7. Source anomaly, recorded so it isn't re-found as a Rust bug — INFORMATIONAL

- `Initialize.hooks`: the zod is `z.record(HookEventSchema(), …)`,
  which in zod v4 demands ALL 27 keys; every real client sends a
  subset. The Rust partial map is what the wire carries; the zod is
  the anomaly.
- New instances of the already-seen required-nullable leniency class
  (`1.md` item 7) on the message/ side: `usage` cache counts,
  `stop_reason`/`stop_sequence`, `Text.citations`, citation
  `document_title` — absence parses as `None` where the d.ts requires
  the key. Same class, same severity, listed here only for
  completeness of instance coverage. Also `max_thinking_tokens` and
  `PreCompact.custom_instructions` on the control side (zod
  required-nullable, Rust accepts absence).

## Verified clean this pass

- All 31 marker literals in message/, all 16 `StdoutMessage` markers,
  all 16 system subtype markers, the result subtypes, all 21 control
  subtype markers, all 27 PascalCase hook-event markers, and the 6
  camelCase permission-update markers — byte-exact against their
  sources (serde's snake_case rule checked against each, including
  the digit-boundary case `Base64` → `base64`).
- No untagged misroute hazard anywhere: every union's markers are
  required and pairwise disjoint; the only optional marker is
  `McpServerConfig::Stdio`'s, deliberately, ordered last — and the
  Rust ordering was proven accept-set-equivalent to the zod's.
- The nested-`ControlRequest` fix is complete: `r#type` is required,
  always serialized, and matches what `structuredIO.ts:263-267` hands
  back for `pending_permission_requests`.
- No missing record type: the 14 other `system` subtypes in the
  source (`informational`, `turn_duration`, `stop_hook_summary`, …)
  are internal transcript messages that never reach a stdout sink;
  `bridge_state` remains the only escape-hatch emission, and it is
  typed.
- Integer fields re-checked against their producers: all genuinely
  integral, including `num_turns` (provably ≥ 1 at both emit sites).
- The seven-value `AssistantMessageError` covers every value the
  error categorizer can produce.
