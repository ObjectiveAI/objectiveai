# Response module fidelity audit — differences only, nothing fixed

Second audit pass over `src/response/` against the Claude Code source
(`temp/`, zod schemas in `src/entrypoints/sdk/{coreSchemas,controlSchemas}.ts`)
and the pinned `@anthropic-ai/sdk@0.39.0` type definitions. Three
independent audit agents swept the three slices (message/, records,
control/); every load-bearing claim below was re-verified against the
source directly before inclusion.

Known-intentional deviations (bridge_state, workflow_progress, the
`auto` permission mode, the merged User struct, the EMPTY_USAGE-derived
result usage, `z.unknown()` → `Value`) are excluded except where noted
for the record.

---

## Wire-breaking

### 1. `ApiKeySource` will reject every real `system/init` line

- Rust: `system.rs` — `enum ApiKeySource { User, Project, Org, Temporary, Oauth }`,
  required on `System::Init`.
- Zod agrees (`coreSchemas.ts:57-59`) — **but the only producer lies to
  the schema**. `systemInit.ts:72` writes
  `getAnthropicApiKeyWithSource().source as ApiKeySource`, and that
  function's real return type is
  `'ANTHROPIC_API_KEY' | 'apiKeyHelper' | '/login managed key' | 'none'`
  (`src/utils/auth.ts:208-212`, verified: the function at
  `auth.ts:226+` returns exactly these). The `as` cast is unchecked
  widening; the five zod values never occur on the wire.
- Consequence: `init` opens **every turn**, so under the strict union
  the very first line of every run fails to parse. Same class as the
  sanctioned schema-escaping emissions, but this one was not on the
  intentional list — the port followed the zod where the zod is wrong.

### 2. `System::ApiRetry.retry_delay_ms: u64` rejects the fractional value the source emits

- Rust: `system.rs` — `retry_delay_ms: u64`.
- Source: `z.number()` (`coreSchemas.ts:1579`); the value is
  `getRetryDelay`'s return (`withRetry.ts:530-548`), which is
  `baseDelay + Math.random() * 0.25 * baseDelay` — **always
  fractional** except on the `Retry-After`-header path. Verified
  directly. `serde_json` refuses a non-integral float into `u64`, so a
  routine retry kills the line. The port already uses `f64` for the
  other durations (`result.rs` `duration_ms`, `tool_progress.rs`
  `elapsed_time_seconds`); this one is the outlier.

## Lossy (parse-failure on schema-valid input, or re-serialize drift)

### 3. Required `Value` fields where the zod accepts a missing key

- Rust: `hook_input.rs` `tool_input` / `tool_response` (PreToolUse,
  PostToolUse, PostToolUseFailure, PermissionDenied,
  PermissionRequest) and `control/mod.rs` `mcp_message.message` are
  `serde_json::Value` with no `#[serde(default)]` — a missing key is a
  hard error.
- Source: all are `z.unknown()` (`coreSchemas.ts:419,442,452,466,430`;
  `controlSchemas.ts:37,379`), and a `z.unknown()` field in a zod
  object tolerates the key's absence. The producers do currently set
  them, so this is latent rather than live.
- (Contrast `can_use_tool.input`: `z.record(...)` — genuinely
  required, correctly required in Rust.)

### 4. Nested `ControlRequest` loses its `type` literal on re-serialization

- Rust: `ControlResponseInner::Error.pending_permission_requests:
  Option<Vec<ControlRequest>>` where `ControlRequest` is only
  `{request_id, request}` — the `"type": "control_request"` literal
  lives on the outer `StdoutMessage` tag.
- Source: the array element is the full `SDKControlRequestSchema`
  *including* `type: z.literal('control_request')`
  (`controlSchemas.ts:578-584`, referenced at `:599-601`).
- Deserialization is unaffected (the extra key is ignored);
  re-serializing emits elements without `type`, which the schema
  requires. Only matters if the port ever writes these back.

### 5. `SetMaxThinkingTokens.max_thinking_tokens: Option<u64>` vs unconstrained `z.number().nullable()`

- Source (`controlSchemas.ts:150`) has no `.int()`/`.positive()`; a
  fractional or negative value is schema-valid and would fail `u64`.
  Sibling numbers were done right (`seed_read_state.mtime: f64`,
  `HookCallbackMatcher.timeout: f64`).

### 6. `number` → unsigned-integer narrowing across message/

- Rust: citation indices/offsets, stream `index`, and all
  `usage.rs` token counts are `u64`; the d.ts types every one as bare
  `number` (`beta-messages.d.ts:62-99, 265-276, 601-618`).
- All are counts/indices in practice, so this is theoretical — but a
  fractional or negative value is in-type for the SDK and hard-fails
  here. Recorded as the same policy question as items 2 and 5: how
  literally to read TypeScript `number`.

## Cosmetic / for the record

### 7. Leniency: `Option<T>` accepts both `null` and absent where the source distinguishes

- Required-but-nullable zod fields (`.nullable()` without
  `.optional()`) parse as `None` when the key is *absent*, which zod
  would reject: `Status.status`, `ApiRetry.error_status`,
  `stop_reason` (both result arms), and all three
  `parent_tool_use_id`s. Round-trip stays faithful (no
  `skip_serializing_if`, so `None` re-emits as `null`).
- Mirror case in message/: four fields optional-but-NOT-nullable in
  the d.ts (`ToolResultBlockParam.content`, `.is_error`,
  `DocumentBlockParam.citations`, `CitationsConfig.enabled`) accept an
  explicit `null` in Rust that the d.ts does not admit. Both
  directions are reader-lenient only.

### 8. `result::Usage`'s doc vs its own attributes

- The doc says "the four token counts are always present," but
  `cache_creation_input_tokens` and `cache_read_input_tokens` carry
  `#[serde(default)]` while `input_tokens`/`output_tokens` do not —
  two of the four are quietly more forgiving than documented.

### 9. `McpServerStatus` name shadows a richer source type

- The Rust `McpServerStatus {name, status: String}` correctly mirrors
  the *inline* object in the init schema (`coreSchemas.ts:1467-1472`),
  but the source separately owns a much larger `McpServerStatusSchema`
  (`coreSchemas.ts:167-220`: 5-value status enum, serverInfo, error,
  config, scope, tools, capabilities) used by control responses. Same
  name, different shape — a naming trap for future work.

### 10. `AgentDefinition.max_turns: Option<u64>` admits `0`

- Source is `z.number().int().positive()` (`coreSchemas.ts:1148-1155`).
  Reader-lenient only.

### 11. `context_management` round-trip asymmetry

- The producer always emits the key (`messages.ts:763`,
  `... ?? null`); Rust parses the `null` to `None` and then omits the
  key on re-serialization, and `Option<Value>` cannot represent
  "present and null" distinctly. Decode→encode is not byte-stable
  against the producer.

### 12. `UserMessage.role` — checked and NOT a difference, with a nuance

- An auditor flagged the single-variant `UserRole` against the SDK's
  `MessageParam.role: 'user' | 'assistant'`. The actual truth side for
  `user` records is Claude Code's own wrapper
  (`src/types/message.ts:92-96`), whose role is literally `'user'` —
  the port matches the record, not the wider SDK type it superficially
  resembles. No action implied; noted so it isn't re-flagged later.

### 13. `PermissionMode::Auto`, for the record

- The sanctioned sixth variant is reachable not only from the status
  record but from `set_permission_mode.mode`,
  `PermissionUpdate::SetMode.mode`, and
  `AgentDefinition.permissionMode`, all of which the zod limits to
  five values. Reader-widening only; already intentional.

## Verified faithful (no differences found)

- `StdoutMessage`'s 16 tags vs `StdoutMessageSchema` expanded through
  `SDKMessageSchema` — exact, including the correct exclusion of the
  stdin-only `update_environment_variables`.
- `System`'s subtype roster: exactly the source's fifteen system
  schemas plus sanctioned `bridge_state`; a sweep of every
  `subtype: '…'` literal reaching stdout found nothing further.
- `Init`'s sixteen fields, `Result` success/error field split,
  `ModelUsage`'s eight camelCase fields, `PermissionDenial`,
  `rate_limit_event`'s camelCase names and all three enum sets
  (including all thirteen overage reasons), the seven-value
  `AssistantMessageError`, and all small records.
- message/: `BetaMessage`, all four content blocks, the six stream
  events and five delta kinds, both citation families (Param vs
  response verified byte-identical, so the type reuse is sound), the
  seven param blocks, both source unions, media-type literals.
- control/: all 21 request subtypes with their tags and camelCase
  renames, the 27 `HookEvent`s, the 27 `HookInput` variants with
  per-variant intersection requiredness (SubagentStart/Stop promotion
  verified), `PermissionUpdate`'s six camelCase tags, all four MCP
  transports, and every small enum.
