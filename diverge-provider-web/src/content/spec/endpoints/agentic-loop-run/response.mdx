Each response's payload is a single tag byte followed by that
variant's own payload — a JSON text for tags `0` and `1`, read under
the layer's [notation](/endpoints/#notation); a named body for tag
`2`; raw bytes for tag `3`.

```rust
pub enum Response<'a> {
    /// Tag 0. One piece of the loop's output.
    Chunk(AgenticLoopChunk),
    /// Tag 1. The scope's final response.
    Error(Error),
    /// Tag 2. A resource the run rewrote, whole:
    /// `[u32 BE: name length][name, UTF-8][body]`.
    Resource { name: &'a str, body: &'a [u8] },
    /// Tag 3. One piece of the continuation: raw bytes, the loop's
    /// closer.
    Continuation(&'a [u8]),
}

/// An arbitrary JSON value, the server's to compose. This
/// specification does not constrain it.
pub struct Error(pub serde_json::Value);
```

- **An error is terminal.** A response bearing tag `1` is the scope's
  final response; the response finish follows it.
- **Chunks are ordered.** The chunks of one scope form one stream, in
  the order sent.
- **A resource is the run handing state back.** A response bearing
  tag `2` carries the whole new content of a resource the request
  supplied by identity, under the dotted path of the request field
  that supplied it (`provider.auth_resource`,
  `toolsets.spotify.auth_resource`). The client replaces what it
  holds and names the new content's identity next time. Not
  terminal; it may repeat, and the last one wins.
- **The continuation closes the stream.** Responses bearing tag `3`
  carry the loop's continuation — the server's own opaque state, as
  bytes — in one or more pieces; the response finish says the
  sequence is whole. Nothing but the finish follows them. A loop that
  issues none is not resumable. The pieces are kept as pieces: the
  client stores them in order, never joined or re-split, and answers
  the next request's
  [continuation fetch](/endpoints/agentic-loop-run/channels/) with
  the same pieces, one frame each, in the same order.

## Chunks

A chunk is one of nine kinds. The union is untagged: each kind is
discriminated by its own constant `type` member, and goes on the wire
as its members alone.

```rust
#[serde(untagged)]
pub enum AgenticLoopChunk {
    AssistantReasoning(AssistantReasoningChunk),
    AssistantTextContent(AssistantTextContentChunk),
    AssistantImageContent(AssistantImageContentChunk),
    AssistantAudioContent(AssistantAudioContentChunk),
    AssistantToolCall(AssistantToolCallChunk),
    AssistantRefusal(AssistantRefusalChunk),
    ToolResponse(ToolResponseChunk),
    Usage(UsageChunk),
    Notification(NotificationChunk),
}
```

`TextContent`, `ImageContent`, `AudioContent`,
`CallToolResult` and `MetaObject` are the
types of the
[Model Context Protocol specification](https://modelcontextprotocol.io/specification/2025-11-25),
incorporated by reference; each is linked beneath the declaration
that references it. Where a chunk flattens one of them, the MCP
type's members appear directly in the chunk's object.

### `assistant_reasoning`

Reasoning text the agent produced.

```rust
pub struct AssistantReasoningChunk {
    /// "assistant_reasoning"
    pub r#type: AssistantReasoningChunkType,
    /// The tool call whose sub-agent produced this chunk; absent on
    /// the main thread. A nested sub-agent names its IMMEDIATE
    /// spawning call, so depth is a chain of ids a caller can follow.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub parent_tool_call_id: Option<String>,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub logprobs: Option<Vec<Logprob>>,
    #[serde(flatten)]
    pub inner: TextContent,
}

pub enum AssistantReasoningChunkType {
    #[serde(rename = "assistant_reasoning")]
    AssistantReasoning,
}

pub struct Logprob {
    pub token: String,
    pub bytes: Option<Vec<u8>>,
    pub logprob: Decimal,
    pub top_logprobs: Vec<TopLogprob>,
}

pub struct TopLogprob {
    pub token: String,
    pub bytes: Option<Vec<u8>>,
    pub logprob: Option<Decimal>,
}
```

### `assistant_tool_call`

A tool call the agent issued, as a delta: consecutive tool call
chunks bearing the same `id` continue one call, their `arguments`
fragments concatenating, in the order sent, into the call's JSON
text; a chunk with a new `id` is a new call.

```rust
pub struct AssistantToolCallChunk {
    /// "assistant_tool_call"
    pub r#type: AssistantToolCallChunkType,
    /// The tool call whose sub-agent produced this chunk; absent on
    /// the main thread. A nested sub-agent names its IMMEDIATE
    /// spawning call, so depth is a chain of ids a caller can follow.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub parent_tool_call_id: Option<String>,
    /// Quoted by the answering tool_response chunk.
    pub id: String,
    #[serde(rename = "_meta", default, skip_serializing_if = "Option::is_none")]
    pub meta: Option<RequestMetaObject>,
    /// The name of the tool to call.
    pub name: String,
    /// One fragment of the call's arguments: JSON text, complete
    /// only once every fragment with this id has been concatenated.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub arguments: Option<String>,
}

pub enum AssistantToolCallChunkType {
    #[serde(rename = "assistant_tool_call")]
    AssistantToolCall,
}
```

Type definitions, in [rmcp](https://docs.rs/rmcp/3.1.2/rmcp/) 3.1.2, the MCP implementation this revision builds against: [`rmcp::model::RequestMetaObject`](https://docs.rs/rmcp/3.1.2/rmcp/model/struct.RequestMetaObject.html).
