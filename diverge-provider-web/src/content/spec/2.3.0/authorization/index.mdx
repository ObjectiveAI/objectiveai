The party that initiated the WebSocket connection is the
**connector**; the party that accepted it is the **connectee**. Either
protocol role may occupy either position: a client may connect to a
server, and a server may connect to a client. Each party sends exactly
one authorization frame, whose payload is its token and nothing
else. The two tokens need not name the same issuer. A token that either party does not accept closes the
connection.

## The requirement

- **Every connection of the Protocol.** This layer governs every
  connection on which the Protocol is served. A connection that a
  layer of this specification declares to be no connection of the
  Protocol is not governed by this layer, and carries no authorization
  frame.
- **Each party's first frame.** The first frame each party sends is
  an authorization frame (type `0`), whose payload is that party's
  token. No frame of that party precedes it.
- **Both parties send.** The connector sends an authorization frame,
  and the connectee sends an authorization frame.
- **Nothing else without acceptance.** A party that has not accepted
  the other party's token sends no frame other than its authorization
  frame, and serves no frame of the other party's.
- **No shared issuer.** The connectee's token and the connector's
  token need not name the same issuer. Each party presents the token
  of the identity it presents itself as, whatever issuer the other
  party's token names. A party does not close a connection because
  the other party's token names an issuer other than that of its own
  token.
- **Exactly one each.** Each party sends exactly one authorization
  frame. A second authorization frame from a party, in either
  direction, is a protocol violation; the party receiving it closes
  the connection.
- **Each party judges.** Each party alone determines whether the
  other party's token is acceptable, and which token it presents. The criteria of acceptability —
  the issuers a party trusts, the signature, the expiry, the
  audience, and the subjects a party admits — are not part of this
  protocol.

## The payload

The authorization frame's payload is the token, and nothing else.
The scope and channel fields of the frame are ignored.

```text
[token …]
```

- **The token.** Every byte of the payload: a JSON Web Token, as
  RFC 7519 defines one, encoded as UTF-8. No byte precedes the token
  and no byte follows it. No length field precedes it, because
  WebSocket already delimits messages.
- **The issuer.** The token's `iss` claim names the issuer of the
  token. A party does not determine the issuer of its own token from
  the other party's token.
- **Nothing else.** The payload states nothing but the token. It
  carries no flag, no description, and no statement of what the
  sender asks of the connection. Whether the server lists the
  client's identity is the matter of
  [daemons::announce](/endpoints/daemons-announce/), and of no frame
  of this layer.
- **Malformed.** A payload that is empty and a payload that is not
  valid UTF-8 are malformed. A party that receives a malformed
  payload closes the connection.

The payload is defined by `diverge-sdk-rs/src/wire/frame/auth.rs`:

```rust include=diverge-sdk-rs/src/wire/frame/auth.rs
```

## Refusal is a close

No frame states a refusal.

- A token a party **accepts** is followed by the connection
  proceeding.
- A token a party **does not accept** is followed by closure of the
  connection, and by nothing else. The party sends no frame that
  states the refusal.
- A party that holds no token to present closes the connection, and
  sends nothing.
- A connection that ends before a party's authorization frame has
  arrived carries no service.

**Remark.** An invalid, an expired and an untrusted token are
indistinguishable from the sender's side: each is observed as a
connection that closed.

## What acceptance establishes

Acceptance establishes, at each party, the other party's
**identity**: the pair of the `iss` and `sub` claims of the token the
other party presented. Each party holds the other's identity for the
life of the connection. Where the client is the connector, the server
serves every scope on the connection under the client's identity. The
identity is the receiving party's own value: the server does not
transmit it on the wire, does not derive a value it sends from it, and
does not serve a scope under any identity other than that of the
connection the scope was opened on. The layers at which the identity
bears on an exchange name it where it applies.
