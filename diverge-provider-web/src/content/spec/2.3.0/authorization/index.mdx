The party that initiated the WebSocket connection is the
**connector**; the party that accepted it is the **connectee**. Either
protocol role may occupy either position: a client may connect to a
server, and a server may connect to a client. Each party sends exactly
one authorization frame, which carries its discover flag and its
token. The connector sends its frame first. The connectee answers with its own token, from the
same issuer. A token that either party does not accept closes the
connection.

## The requirement

- **Every connection of the Protocol.** This layer governs every
  connection on which the Protocol is served. A connection that a
  layer of this specification declares to be no connection of the
  Protocol is not governed by this layer, and carries no authorization
  frame.
- **The connector's first frame.** The first frame the connector
  sends is an authorization frame (type `0`), whose payload carries
  the connector's discover flag and the connector's token. No frame precedes it. The connector sends no
  other frame until the connectee's authorization frame has arrived
  and the connector has accepted it.
- **The connectee's first frame.** The first frame the connectee
  sends is an authorization frame, whose payload carries the
  connectee's discover flag and the connectee's token. The connectee sends it only after it has accepted the
  connector's token. The connectee serves no frame of the connector's
  before it has sent its own authorization frame.
- **The same issuer.** The `iss` claim of the connectee's token is
  exactly the `iss` claim of the connector's token. The connector
  closes a connection whose answering token names any other issuer.
- **Exactly one each.** Each party sends exactly one authorization
  frame. An authorization frame that arrives after a party's first
  frame, in either direction, is a protocol violation; the party
  receiving it closes the connection.
- **Each party judges.** Each party alone determines whether the
  other party's token is acceptable. The criteria of acceptability —
  the issuers a party trusts, the signature, the expiry, the
  audience, and the subjects a party admits — are not part of this
  protocol.

## The payload

The authorization frame's payload is one byte, the discover flag,
followed by the description when the flag is `2`, followed by the
token. The scope and channel fields of the frame are ignored.

```text
[0][token …]                                  not discoverable
[1][token …]                                  discoverable, no description
[2][length, u16][description …][token …]      discoverable, described
```

- **The discover flag.** The first byte of the payload. The byte `0`
  states that the sender is not discoverable. The byte `1` states that
  the sender is discoverable and gives no description. The byte `2`
  states that the sender is discoverable and gives a description.
  [The discover flag](#the-discover-flag) states what the flag binds.
- **The description.** After the byte `2` only: the description's
  length in bytes, a `u16`, big-endian, followed by exactly that many
  bytes, the description encoded as UTF-8.
  [The description](#the-description) states what a description is.
- **The token.** Every byte of the payload after the flag and the
  description: a JSON Web Token, as RFC 7519 defines one, encoded as
  UTF-8. No length field precedes it, because WebSocket already
  delimits messages.
- **The issuer.** The token's `iss` claim names the issuer of the
  token. The connectee reads it to determine the issuer of its own
  token.
- **Malformed.** A payload that is empty, a payload whose first byte
  is none of `0`, `1` and `2`, a payload whose description length or
  description runs past the end of the payload, a description that is
  not valid UTF-8 or breaks a rule of
  [The description](#the-description), a payload with no byte after
  the flag and the description, and a payload whose token is not
  valid UTF-8 are malformed. A party that receives a malformed payload
  closes the connection.

## The discover flag

The discover flag states whether the server lists the client's
identity in its [discover](/endpoints/discover/) listings.

- **The client's flag binds the server.** The server honors the flag
  of the client's authorization frame, whether the client is the
  connector or the connectee. A client whose flag is `1` or `2` is in
  every `discover` listing the server keeps, on any connection, for as
  long as the connection that carried the flag remains open, with the
  description the flag `2` carried: it is sent as added when that
  connection completes its authorization, and as removed when that
  connection ends. A client whose flag is `0` is not listed on account
  of that connection.
- **The server's flag.** The server sends the byte `0`. The client
  reads the server's flag and ignores it.
- **For the connection's life.** A flag and its description hold for
  the connection that carried them. No frame changes them. A client
  changes its flag or its description only by opening another
  connection.
- **Malformed.** A flag that is none of `0`, `1` and `2` is malformed,
  and the party that receives it closes the connection, as
  [The payload](#the-payload) provides.

## The description

A description is what a discoverable client says of itself. The
server lists it beside the client's identity. Its rules are the
limit and the plain-text rule of the `description` of a Chrome
extension's manifest.

- **Plain text.** A description is one line. It holds no control
  character: no newline and no tab.
- **Short.** A description holds at least one character and at most
  `132`, counted as Unicode scalar values.
- **Trimmed.** A description neither begins nor ends with whitespace.
- **Equal is the same.** Two descriptions are the same description
  exactly when their bytes are equal.

The description is defined by `diverge-sdk-rs/src/shared/discover.rs`:


## Refusal is a close

No frame states a refusal.

- A token a party **accepts** is followed by the connection
  proceeding: the connectee answers, or the connector begins its
  requests.
- A token a party **does not accept** is followed by closure of the
  connection, and by nothing else. The party sends no frame of any
  kind before the closure.
- A connectee that holds no token from the issuer the connector's
  token names closes the connection, and sends nothing.
- A connection that ends before a party's authorization frame has
  arrived carries no service.

**Remark.** An invalid, an expired and an untrusted token are
indistinguishable from the sender's side: each is observed as a
connection that closed.

## What acceptance establishes

Acceptance establishes, at each party, the other party's
**identity**: the pair of the `iss` and `sub` claims of the token the
other party presented. Each party holds the other's identity for the
life of the connection. Where the client is the connector, the server
serves every scope on the connection under the client's identity. The
identity is the receiving party's own value: the server does not
transmit it on the wire, does not derive a value it sends from it, and
does not serve a scope under any identity other than that of the
connection the scope was opened on. The layers at which the identity
bears on an exchange name it where it applies.

Acceptance also establishes, at the server, the client's discover
flag, which the server holds for the life of the connection, as
[The discover flag](#the-discover-flag) provides.
