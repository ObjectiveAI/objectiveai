The client opens this channel to send a batch of one or more messages
to the agent, in order. A batch sent while no loop runs starts one,
as its input; a batch sent while one runs is placed in its queue, and
the agent takes it at a seam of its own choosing. Nothing interrupts
a loop. What the agent
says in reply is the main stream of the scope, as
[Response](/container-proxy-endpoints/agents-begin/response/) states.

- **The request.** The tag byte `2` followed by the batch as JSON.
  [Request](/container-proxy-endpoints/agents-begin/client/enqueue/request/) states its form.
- **The response.** Exactly one channel response, sent when the fate
  of the batch is known, however long that takes, and the channel
  response finish. The fate is the fate of every message of the
  batch. [Response](/container-proxy-endpoints/agents-begin/client/enqueue/response/) states the
  sequence.
- **Two kinds.** A request is a batch of chat messages or exactly one
  structured decision, as its `type` states. The paragraph above
  states what a batch of chat messages does. A structured decision
  joins no loop: the server hands it to the program alone, as the
  rules below state.
- **Order.** The server keeps the requests it holds in the order of
  their `index`, whatever order their channel requests reached it in,
  and keeps the messages of each batch in the order the batch states.
  The server places a request in its queue only when it has placed
  every request of a lower index; a request that reaches the server
  before a request of a lower index waits for it. The server never
  splits a batch and never reorders its messages. The batches of a
  call that the program does not take return to the front of the
  queue, in the order they held, ahead of every request placed after
  them. The server has at most one call carrying messages to the
  program at a time.
- **Chat at the head.** When the first request of the queue is a
  batch of chat messages, the server takes that batch and every batch
  of chat messages that follows it, up to the first structured
  decision, and hands them to the program in one call, in order. The
  call is a `/run` when the program has no run open, and an
  `/enqueue` when the program has a run open that chat messages
  started.
- **A structured decision at the head.** When the first request of
  the queue is a structured decision, the server sends the program
  nothing while the program has a run open. When the program has no
  run open, the server starts a `/run` on that structured decision
  alone.
- **Nothing joins a structured decision.** While the run that a
  structured decision started is open, the server sends the program
  no message and no structured decision. The run is open until its
  response body ends. The server then treats the queue as the two
  rules above state.
- **A client that sends at once.** A client may open an enqueue
  channel before the channel before it is answered. The order in
  which the program is handed the requests is the order of their
  `index`.
- **A loop ending.** A loop that ends with a batch still waiting
  does not lose it: the server starts the next loop on every batch
  still waiting, the content of their messages concatenated into one,
  in the order stated above. A container that refuses that content
  refuses every batch of it.
- **No timeout.** The server holds the channel open until the fate is
  known.
