A client opens the scope with a request whose payload is the tag byte
`18` followed by the request as JSON: the image, named by its digest
and by zero or more references, and a description, or none. The
server obtains the image from exactly one source, as
[Image sources](/endpoints/#image-sources) states for a push, and
keeps its own copy. The server sends zero or more responses, each a
blob it took from the client, then exactly one response which states
that the image is in the client's Store, that the client owned the
digest already, that the server has insufficient capacity for it,
that no source supplied it, that the nonce check failed, that the
image is malformed, that the server keeps no Store, or an error. The
response finish follows that response, and no frame follows the
finish.

- **The request.** [Request](/endpoints/images-push/request/) states
  its form.
- **The response.** [Response](/endpoints/images-push/response/)
  states the responses and the sequence of the main stream.
- **The channels.** The client opens no channel on the scope. The
  server opens the channels that
  [Server Channels](/endpoints/images-push/server/) defines, and only
  where it obtains the image from the client.

## The order

1. **The server reads the request.** A request whose payload does not
   decode is answered by a response finish that no response precedes,
   as [Endpoints](/endpoints/) provides.
2. **No Store.** A server that holds out no
   [`images_store`](/capabilities/#images_store) capability answers
   every other request by exactly one response, the byte `7` and
   nothing else, and the response finish, and does nothing of what
   follows.
3. **Exists.** When the digest of the request is the digest of an
   image in the client's Store, the server answers by exactly one
   response, the byte `2` followed by the digest, and the response
   finish. The server obtains nothing, opens no channel, and leaves
   the description of the image in the Store as it was.
4. **A registry.** When a registry that is in the server's
   [`images_registries`](/capabilities/#images_registries) and that a
   reference of the request names serves the digest, the source is
   `Registry`. The server takes the manifest the digest names first,
   and, where that manifest is an image index, the manifest of one
   platform that the index lists. The server determines from the
   sizes the manifest declares whether the Store has room for the
   image, before it takes any blob. The server takes every blob the
   image manifest references and verifies each against its digest.
   The server keeps the bytes and the digests the registry served,
   unaltered. The server makes no nonce check.
5. **The client.** Otherwise the source is `Client`. The server asks
   the client for the manifest the digest names on an
   [oci-manifest](/endpoints/images-push/server/oci-manifest/)
   channel, and, where that manifest is an image index, for the
   manifest of one platform that the index lists on another, and
   verifies each against its digest. The server determines from the
   sizes the manifest declares whether the Store has room for the
   image, before it asks for any blob. For every blob the image
   manifest references that the server does not already hold, the
   server asks the client on an
   [oci-blob](/endpoints/images-push/server/oci-blob/) channel,
   verifies the bytes against the blob's digest, and sends one
   response, the byte `0` followed by the blob's digest and size. The
   server asks the client for no blob it already holds. When it holds
   every byte of the image, the server makes the nonce check that
   [Possession](/shared/possession/) defines on exactly one
   [oci-prove](/endpoints/images-push/server/oci-prove/) channel,
   whether or not it asked the client for any blob.
6. **The image enters the Store.** When the image was obtained from a
   registry, or from the client and the nonce check passed, the image
   is in the client's Store, with the description of the request. The
   server sends exactly one response, the byte `1` followed by the
   digest, the size and the source, and the response finish. From
   that moment, every [images::list](/endpoints/images-list/) scope
   the client opens lists the image, and every list scope the client
   holds open is sent the image as added, until an
   [images::delete](/endpoints/images-delete/) request by the client
   deletes it.

## The rules that hold throughout

- **The refusals.** Each refusal is exactly one response followed by
  the response finish, and no image enters the client's Store as a
  result of the request:
  - a Store with no room for the image, by the sizes the manifest
    declares, is answered by the byte `3`; the server takes no blob
    after it so determines;
  - a manifest or a blob the client answers with a channel response
    finish that no channel response precedes, where no registry the
    server consults serves the digest, is answered by the byte `4`;
  - a nonce check that fails is answered by the byte `5`, and the
    server removes what [Image sources](/endpoints/#image-sources)
    states;
  - a manifest that does not parse, a manifest of a media type the
    server does not take, and a manifest or a blob whose bytes do not
    match its digest or its declared size are answered by the byte
    `6`.
- **The image is the digest.** The image the server keeps is the
  image the digest of the request names, and the source answered is
  the source from which the server obtained it. A push never has the
  source `Store`.
- **The description.** The `description` of the request is absent,
  or a description as
  [The description](/endpoints/daemons-announce/request/#the-description) defines it. The
  image carries it from the moment it enters the Store, until an
  [images::edit](/endpoints/images-edit/) by the client replaces or
  clears it.
- **The client.** The client is the identity under which the
  connection was authorized, as [Authorization](/authorization/)
  provides. The image enters that identity's Store, as an image the
  client built enters it, and that identity alone can examine it,
  edit it, pull it, delete it, or run it from its Store.
- **No eviction.** The end of the scope, and the end of every
  connection of the client, leave a pushed image in the Store. The
  server does not remove the image from the Store on its own account.
- **The error.** An error, the byte `8` followed by an error, states
  that no image entered the client's Store as a result of the
  request, for a reason other than a refusal.
