A client opens the scope with a request whose payload is the tag byte
`0` followed by the request as JSON. The server runs the
container the request describes for as long as the scope lives,
sends the container's id on the scope and, after it, the agent's
chunks as they come, or an error, and ends the scope by the response finish. This section states
what the server does, in the order it does it. It states nothing
about the client, which may open any channel at any time.

- **The request.** [Request](/endpoints/containers-agents-run/request/) states its form and
  every constraint the server enforces on it.
- **The response.** [Response](/endpoints/containers-agents-run/response/) states the one
  response and the sequence of the main stream.
- **The channels.** The client opens the channels that
  [Client Channels](/endpoints/containers-agents-run/client/) defines; the server
  opens the channels that [Server Channels](/endpoints/containers-agents-run/server/)
  defines. Each channel is its own section.

## The order

1. **The server reads the request.** A request whose payload does not
   decode is answered by a response finish that no response precedes,
   as [Endpoints](/endpoints/) provides. A request the server refuses
   is answered by exactly one response, the error, and the finish.
   The server refuses a request that names a volume not in the
   client's [volumes::list](/endpoints/volumes-list/) listing, a mount
   whose path is the root of the container, two mounts with one path,
   a mount inside another mount, a mount path with a component that
   is empty, `.` or `..`, two FUSE mounts with one `id`, or an image
   it will not supply. A request
   that names in `volume_mounts` a volume under a
   [volumes::stat](/endpoints/volumes-stat/),
   [volumes::edit](/endpoints/volumes-edit/) or
   [volumes::delete](/endpoints/volumes-delete/) at the time of the
   request is answered by exactly one response, the byte `1`
   followed by the name of that volume, and the finish; the server
   fetches nothing and deploys nothing for it. A request may name one
   volume more than once, at different paths.
2. **The server obtains the image.** The server obtains the image the
   digest names, from wherever it obtains images; this specification
   does not prescribe the source. Where it would obtain the image
   from the client, the server may ask the client whether it holds
   the image on an [oci-has](/endpoints/containers-agents-run/server/oci-has/) channel, and
   for a manifest or a blob it requires on an
   [oci-manifest](/endpoints/containers-agents-run/server/oci-manifest/) or
   [oci-blob](/endpoints/containers-agents-run/server/oci-blob/) channel. The server runs
   only the image the digest names: bytes that are not those the
   digest names are the run's error, and so is an image the server
   obtains from nowhere. How the server holds, verifies or streams
   what it obtains is not prescribed.
3. **The server deploys the container.** The server starts the image
   with `memory` and `disk` as limits; every volume mount resolved by
   `volume_name` against the identity under which the connection was
   authorized, descended by `volume_relative_path`, at `container_path`;
   the container proxy
   injected into the container and started; and TCP
   port `14979` of the container reachable to the server. The deploy
   is complete when the proxy accepts a WebSocket connection at that
   port. The server sets no environment from the request. A deploy
   that does not complete is the run's error.
4. **The server connects to the proxy.** The server opens exactly
   one WebSocket to port `14979` of the container, the connection of
   the [Container Proxy](/container-proxy/) layer, and on it, before
   anything else, the begin scope of the container's family —
   [agents::begin](/container-proxy-endpoints/agents-begin/),
   carrying the `arguments` of the request verbatim.
   A proxy that does not accept the connection, or that answers the
   begin with an error, is a container that did not come up: the
   server stops the container, and the failure is the run's error.
   The server opens no second connection to a container.
5. **The server asks the client to deploy the tools.** The `Begun`
   the proxy answers carries the tools the container declared. When
   the list is not empty, the server opens exactly one
   [tools](/endpoints/containers-agents-run/server/tools/) channel on the scope carrying it
   verbatim, and reads the answer to its finish. A deploy lets the
   run go on. An error, a channel response finish that no channel
   response precedes, and a client that is gone are the run's error,
   and the server stops the container. When the list is empty the
   server opens no tools channel.
6. **The server makes every FUSE mount.** For each entry of
   `fuse_file_mounts`, and after the last of them for each entry of
   `fuse_directory_mounts`, in the order of the request, the server
   opens one mount scope on the proxy's connection, naming the path
   and the kind, and waits for its answer before opening the next. A
   mount the proxy does not make is the run's error, and the server
   stops the container. The server opens no tree scope and sends no
   response before the last mount is complete. The mounts and the
   tools channel proceed beside each other, and the server acts on
   the failure of either only when both have ended.
7. **The server holds what the client opened.** A channel the client
   opens before the server sends the id is served after the id, in
   the order opened, and is neither refused nor read before the last
   FUSE mount is complete and the tools channel, when one was opened,
   has ended.
8. **The server mints and sends the id.** The id is a string the
   server chooses, unique among the containers it is running, and
   not derivable from the request, from the identity of the
   connection, or from any other id. The server
   sends it as exactly one response. From that moment the container
   is running for the client, and a
   [containers::tools::connect](/endpoints/containers-tools-connect/)
   request naming the id finds it. After the id, the server sends the
   agent's chunks as they come, each as one response, and no other
   response on the scope.
9. **The server serves the scope.** Concurrently, for as long as the
   scope lives: every channel the proxy opens on the begin scope, and
   every ask a mount makes on its own scope, is relayed to the client
   as a channel the server opens; every channel the client opens is
   served as its section defines.
10. **The server ends the run.** When it receives the client's
   [stop](/endpoints/containers-agents-run/client/stop/), when the proxy's
   connection ends, or when the client's connection ends,
   the server ends every connect scope on the container, stops the
   container, ends every channel task, and sends the response
   finish. After the id, the
   server sends no error on the main stream: the finish that ends a
   running container carries none.

## The rules that hold throughout

- **Who may mount a volume.** A volume whose `mode` is `ephemeral`
  or `read_only` may be mounted in any number of containers of its
  client at once. A volume whose `mode` is `persistent` has one user
  at a time: it is mounted in one running container, which may name
  it at several paths, or served on one
  [volumes::serve](/endpoints/volumes-serve/) scope, and a request
  naming it while either holds it is refused with `VolumeHeld`.
  The server holds every volume a request names, shared, from the
  moment it accepts the request until the run ends: a stat, an edit
  or a delete of a volume so held is refused for as long as any run
  holds it, and a run naming a volume under a stat, an edit or a
  delete is refused for as long as that is in flight.
- **The means of deployment.** This revision prescribes no runtime,
  no operating system, no virtualization, no network topology and no
  vendor. The server may deploy the container on hardware it
  operates, on infrastructure a third party supplies, or through an
  intermediary, and every requirement of this section holds however
  it deploys.
- **No timeout.** The server times nothing out: not a fetch, not a
  deploy, not a channel, not the scope. A container whose entrypoint
  never listens is served as a container whose exchanges the proxy
  cannot serve.
- **The conduit.** The server relays the bytes of every relayed
  exchange verbatim. It does not read them, does not alter them,
  does not reorder frames within one channel, and does not send an
  ask a second time. A channel the client finishes with no frame
  before the finish is relayed to the proxy as a channel response
  finish that no channel response precedes.
- **What the server never does.** The server never refuses or alters
  a FUSE ask on its own account: whether a change to a FUSE mount is
  allowed is the client's answer to that ask. The server never
  writes to a volume or a mount on its own account. The server never
  sends a second id.
