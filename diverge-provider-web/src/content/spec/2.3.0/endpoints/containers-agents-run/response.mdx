The server sends the id; or one of five refusals — the volume that
refused the run, named, and why; or an error; and, after the
id, zero or more loops: for each, the word that it began, the chunks
the agent says in it, and the word that it ended, for the life of
the run. The response finish ends the scope. No frame bearing the
scope follows the finish.

```text
[0][id JSON …]                          once, when the container is running
[1][volume-held JSON …]                 once, when an operation holds a named volume
[2][volume-mounted JSON …]              once, when a running container holds a named volume and the server mounts a volume of its mode once
[3][volume-fuse-served JSON …]          once, when a FUSE serve holds a named volume and the server does not mount a volume of its mode beside one
[4][volume-mount-unsupported JSON …]    once, when the server does not mount a volume of a named volume's mode
[5][volume-mode JSON …]                 once, when a named volume is not in the mode its mount names
[6][error JSON …]                       once, when it is not running for another reason
[7][chunk JSON …]                       zero or more, within a loop, for the life of the run
[8]                                     active: a loop began
[9]                                     inactive: that loop ended
```

- **The sequence.** Before the id, the server sends no response.
  The first response is the id, one of the five refusals, or an
  error. A refusal and an error are each followed by the response
  finish, and the container is not running and will not be. After
  the id, the server sends zero or more loops, and no other response
  until the finish. A loop is exactly one response whose payload is
  the byte `8` and nothing else, followed by zero or more chunks, each
  as one response, in the order the proxy sent them, followed by
  exactly one response whose payload is the byte `9` and nothing
  else. The finish carries no error: a run that ended after its id
  ended by the client's stop, by the container's own end, or by the
  client's connection ending. A response finish that no response
  precedes states that the request was not served, as
  [Endpoints](/endpoints/) provides, or that the run ended before the
  server had an id to send.
- **The id.** A payload whose first byte is `0` carries the id after
  that byte as JSON, an object with the member `id`, a string. The
  server sends it after every FUSE mount is complete and, for an
  agent container, after the agent is registered.
- **The refusals, and their order.** The server decides
  the bytes `1` to `5` for each distinct `volume_name` the request
  names, in the order first named, in the order
  [Capabilities](/capabilities/#the-hold) states, the first rule that
  applies deciding; a refusal of any volume gives back every volume
  held for the request before it. Every refusal is sent before the
  server fetches or deploys anything, the finish follows it, and the
  container was not started.
- **Volume held.** A payload whose first byte is `1` carries, after
  that byte as JSON, an object with the member `name`, a string: the
  `volume_name` of a volume the request named that is under a
  [volumes::stat](/endpoints/volumes-stat/),
  [volumes::read](/endpoints/volumes-read/),
  [volumes::write](/endpoints/volumes-write/),
  [volumes::filetree](/endpoints/volumes-filetree/),
  [volumes::edit](/endpoints/volumes-edit/) or
  [volumes::delete](/endpoints/volumes-delete/) at the time of the
  request.
- **Volume mounted.** A payload whose first byte is `2` carries, after
  that byte as JSON, an object with the member `name`, a string: the
  `volume_name` of a volume the request named that a running
  container of the client holds at the time of the request, on a
  server whose [mode object](/capabilities/#the-mode-object) for the
  volume's mode has `mount_many` `false`. A volume a running
  container holds does not refuse a run where `mount_many` is `true`.
- **Volume FUSE served.** A payload whose first byte is `3` carries,
  after that byte as JSON, an object with the member `name`, a
  string: the `volume_name` of a volume the request named that a
  [volumes::fuse_serve](/endpoints/volumes-fuse-serve/) of the
  client holds at the time of the request, on a server whose mode
  object for the volume's mode has `mount_and_fuse_serve` `false`. A
  volume a FUSE serve holds does not refuse a run where
  `mount_and_fuse_serve` is `true`.
- **Volume mount unsupported.** A payload whose first byte is `4`
  carries, after that byte as JSON, an object with the member `name`,
  a string: the `volume_name` of a volume the request named whose
  `mode` the server holds out no mode object for, or whose mode
  object has `mount` `false`. The volume is as it was.
- **Volume mode.** A payload whose first byte is `5` carries, after
  that byte as JSON, an object with the members `name`, a string, and
  `mode`, a string: the `volume_name` of a volume the request named
  under a `mode` the volume is not in, and the mode the volume is in,
  as the client's listing reports it, one of `persistent`,
  `ephemeral` and `read_only`. The volume is as it was. A request
  naming one volume under two modes is answered the same way, with
  the mode the volume is in.
- **The error.** A payload whose first byte is `6` carries an error
  after that byte, exactly one JSON value in the form defined on the
  [volumes::list response](/endpoints/volumes-list/response/) page.
  This revision prescribes nothing about its content.
- **The chunk.** A payload whose first byte is `7` carries, after
  that byte as JSON, one chunk of the agent's conversation, exactly as
  the proxy sent it; the server does not read it. The server sends a
  chunk only after the id. A chunk is one of the forms the included
  files below define, told apart by its `type` member. A message of
  the client's lands as its user parts: one chunk per content block,
  its `type` the block's kind — `user_text_content`,
  `user_image_content`, `user_audio_content`, `user_resource`,
  `user_resource_link` — each carrying the message's `key` as the
  enqueue gave it, consecutive in the message's order. The first
  chunks the server sends after the id are the user parts of the
  message the loop started on, or of every message it started on,
  in the order sent. A message's user parts mark it landing, and a
  `notification` chunk whose `is_fatal` is `true` marks a loop that
  ended in failure. No chunk marks the end of a loop: the byte `9`
  does.
- **Active and inactive.** A payload that is the byte `8` and
  nothing else states that a loop began: the agent's server answered
  the loop's `POST /run` with `2xx`. A payload that is the byte `9`
  and nothing else states that the loop ended: the event stream of
  that answer ended, cleanly or by failing. The server sends each
  exactly as the proxy sent it on the
  [begin response](/container-proxy-endpoints/agents-begin/response/),
  where the proxy produces both and relays neither from the agent's
  server. The server sends no byte `8` before the id, none while a
  loop is open, and no byte `9` while none is. An agent is quiet
  between a `9` and the next `8`; quiet between an `8` and its `9`
  is an agent still working.
- **Malformed.** A payload with no byte, a payload whose first byte
  is none of `0` to `9`, a payload whose bytes after `0` do not
  parse as the id, a payload whose bytes after `1`, `2`, `3`, `4` or
  `5` do not parse as that refusal, a payload whose bytes after `7`
  do not parse as a chunk, and a payload whose bytes after `6` are
  not one JSON value are malformed. A payload whose first byte is
  `8` or `9` is read by that byte alone; bytes after it are not
  read.
