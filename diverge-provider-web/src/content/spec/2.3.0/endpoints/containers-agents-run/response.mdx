The server sends the id, the volume that refused the run — held, or
in another mode — or an error, and, after the id, zero or more loops: for each, the word that
it began, the chunks the agent says in it, and the word that it
ended, for the life of the run. The response finish ends the scope.
No frame bearing the scope follows the finish.

```text
[0][id JSON …]                  once, when the container is running
[1][volume-held JSON …]         once, when a named volume is held
[2][volume-mode JSON …]         once, when a named volume is not in the mode its mount names
[3][error JSON …]               once, when it is not running for another reason
[4][chunk JSON …]               zero or more, within a loop, for the life of the run
[5]                             active: a loop began
[6]                             inactive: that loop ended
```

- **The sequence.** Before the id, the server sends no response.
  The first response is the id, the volume that refused the run, or
  an error. A refusal and an error are each followed by the response
  finish, and the container is not running and will not be. After
  the id, the server sends zero or more loops, and no other response
  until the finish. A loop is exactly one response whose payload is
  the byte `5` and nothing else, followed by zero or more chunks, each
  as one response, in the order the proxy sent them, followed by
  exactly one response whose payload is the byte `6` and nothing
  else. The finish carries no error: a run that ended after its id
  ended by the client's stop, by the container's own end, or by the
  client's connection ending. A response finish that no response
  precedes states that the request was not served, as
  [Endpoints](/endpoints/) provides, or that the run ended before the
  server had an id to send.
- **The id.** A payload whose first byte is `0` carries the id after
  that byte as JSON, an object with the member `id`, a string. The
  server sends it after every FUSE mount is complete and, for an
  agent container, after the agent is registered.
- **Volume held.** A payload whose first byte is `1` carries, after
  that byte as JSON, an object with the member `name`, a string: the
  `volume_name` of a volume the request named that is under a
  [volumes::stat](/endpoints/volumes-stat/),
  [volumes::edit](/endpoints/volumes-edit/) or
  [volumes::delete](/endpoints/volumes-delete/) at the time of the
  request, or a `persistent` volume that a running container mounts
  or a [volumes::serve](/endpoints/volumes-serve/) holds at the time
  of the request. An `ephemeral` or a `read_only` volume mounted in
  another container does not refuse a run: it may be mounted in any
  number of containers of the client at once. The server sends it
  before it fetches or deploys anything, and the finish follows. The
  container was not started.
- **Volume mode.** A payload whose first byte is `2` carries, after
  that byte as JSON, an object with the members `name`, a string, and
  `mode`, a string: the `volume_name` of a volume the request named
  under a `mode` the volume is not in, and the mode the volume is in,
  as the client's listing reports it, one of `persistent`,
  `ephemeral` and `read_only`. The server sends it after it has held
  the volume and given the hold back, before it fetches or deploys
  anything, and the finish follows. The container was not started,
  and the volume is as it was. A request naming one volume under two
  modes is answered the same way, with the mode the volume is in.
- **The error.** A payload whose first byte is `3` carries an error
  after that byte, exactly one JSON value in the form defined on the
  [volumes::list response](/endpoints/volumes-list/response/) page.
  This revision prescribes nothing about its content.
- **The chunk.** A payload whose first byte is `4` carries, after
  that byte as JSON, one chunk of the agent's conversation, exactly as
  the proxy sent it; the server does not read it. The server sends a
  chunk only after the id. A chunk is one of the forms the included
  files below define, told apart by its `type` member. A message of
  the client's lands as its user parts: one chunk per content block,
  its `type` the block's kind — `user_text_content`,
  `user_image_content`, `user_audio_content`, `user_resource`,
  `user_resource_link` — each carrying the message's `key` as the
  enqueue gave it, consecutive in the message's order. The first
  chunks the server sends after the id are the user parts of the
  message the loop started on, or of every message it started on,
  in the order sent. A message's user parts mark it landing, and a
  `notification` chunk whose `is_fatal` is `true` marks a loop that
  ended in failure. No chunk marks the end of a loop: the byte `6`
  does.
- **Active and inactive.** A payload that is the byte `5` and
  nothing else states that a loop began: the agent's server answered
  the loop's `POST /run` with `2xx`. A payload that is the byte `6`
  and nothing else states that the loop ended: the event stream of
  that answer ended, cleanly or by failing. The server sends each
  exactly as the proxy sent it on the
  [begin response](/container-proxy-endpoints/agents-begin/response/),
  where the proxy produces both and relays neither from the agent's
  server. The server sends no byte `5` before the id, none while a
  loop is open, and no byte `6` while none is. An agent is quiet
  between a `6` and the next `5`; quiet between a `5` and its `6` is
  an agent still working.
- **Malformed.** A payload with no byte, a payload whose first byte
  is none of `0`, `1`, `2`, `3`, `4`, `5` and `6`, a payload whose
  bytes after `0` do not parse as the id, a payload whose bytes after
  `1` or `2` do not parse as the refusal, a payload whose bytes after
  `4` do not parse as a chunk, and a payload whose bytes after `3`
  are not one JSON value are malformed. A payload whose first byte is
  `5` or `6` is read by that byte alone; bytes after it are not read.
