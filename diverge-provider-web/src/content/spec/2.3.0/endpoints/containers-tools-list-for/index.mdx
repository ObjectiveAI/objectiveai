A client, the lister, opens the scope with a request whose payload is
the tag byte `3` followed by the request as JSON: an identity, named
by the mode it authenticates in. The server asks the runner of every
tool container that identity is running whether the lister may see it,
and sends the lister each container whose runner says so, one
response each, the moment that answer arrives. When every runner asked
at the opening has answered or gone, the server sends the word that
the listing is whole, and keeps the scope open: a tool container the
identity starts after is asked about the same way and sent as added
when its runner allows, and a container whose run ends is sent as
removed to a lister it was sent to. The scope ends at the lister's
stop, at the lister's connection ending, or at an error; the response
finish follows, and no frame follows the finish. This section states
what the server does, in the order it does it. It states nothing about
the lister or the runners.

- **The request.** [Request](/endpoints/containers-tools-list-for/request/) states its form.
- **The response.** [Response](/endpoints/containers-tools-list-for/response/) states the responses and
  the sequence of the main stream.
- **The channels.** The lister opens the one channel of
  [Client Channels](/endpoints/containers-tools-list-for/client/), the
  stop. The server opens no channel on a list scope.

## The order

1. **The server reads the request.** A request whose payload does not
   decode is answered by a response finish that no response precedes,
   as [Endpoints](/endpoints/) provides.
2. **The server finds the containers.** The server finds every tool
   container it is running whose runner is the identity named: every
   [containers::tools::run](/endpoints/containers-tools-run/) scope
   the server holds open under that identity. A container is found by
   its runner alone: a container the identity is attached to as a
   connector is not among them, and no agent container is among them,
   whoever runs it. An identity that runs no tool container is
   answered by the byte `2` at once, and the scope stays open.
3. **The server asks every runner, all at once.** For each container
   found, the server opens an
   [authorize-list](/endpoints/containers-tools-run/server/authorize-list/)
   channel on the RUN scope of the container, carrying the peer
   address of the lister's connection as the server observed it and
   the identity under which the lister's connection was authorized,
   as [Authorization](/authorization/) provides. The server opens
   every such channel without waiting on any other's answer.
4. **The server sends each container as its runner allows.** The byte
   `1` on a channel is answered on the list scope by exactly one
   response carrying that container as added, sent when the byte
   arrives and not held for any other runner. The byte `0`, a channel
   response finish with no frame before it, and a runner that is gone
   are each answered by nothing: the container is not sent. A
   container whose run ends before its runner's byte arrives is not
   sent, whatever the byte.
5. **The server says the listing is whole.** When every channel
   opened in step 3 has finished, the server sends exactly one
   response whose payload is the byte `2` and nothing else. The server
   sends it exactly once on a scope.
6. **The server keeps the listing.** For the life of the scope, a
   tool container the identity starts — a
   [containers::tools::run](/endpoints/containers-tools-run/) scope
   under that identity that has been answered with its id — is asked
   about as in step 3 and sent as in step 4; a tool container the
   identity stops, whose run scope ends, is answered on the list
   scope by exactly one response carrying that container as removed
   when the server has sent it as added, and by nothing otherwise.
   The server asks each runner about each container exactly once per
   list scope.
7. **The server ends the scope.** When the server receives the
   lister's [stop](/endpoints/containers-tools-list-for/client/stop/),
   or the lister's connection ends, the server lets go of every ask
   not yet answered and sends the response finish. An ask let go is
   answered on its own channel as its runner answers it, and the
   server sends nothing of that answer.

## The rules that hold throughout

- **No timeout.** The server times nothing out: a runner that does
  not answer holds the byte `2` back, and holds nothing else.
- **No end of its own.** The server does not end the scope because
  the identity runs no tool container, nor because every container
  sent has been removed. The lister's stop, the lister's connection
  ending, and an error are the only ends.
- **No order.** The server sends containers in the order the runners'
  answers arrive, and promises no other. A container is sent as
  removed only after it was sent as added.
- **Nothing but the id.** A container is sent as its id and nothing
  else of it: not its image, not its mounts, not who is attached to
  it.
- **The lister's own containers.** A listing is FOR somebody else: a
  lister that names the identity its own connection was authorized
  under is asked on its own run scopes like any other lister, and
  learns nothing it did not already hold.
- **Seeing is not joining.** A container sent is a container named.
  A lister that joins one opens a
  [containers::tools::connect](/endpoints/containers-tools-connect/)
  with its id and an authorization, and the runner is asked again.
