A [request](/frames/scopes/) opens a scope for exactly one
**endpoint**. The request's payload begins with a single tag byte
designating the endpoint; the remainder of the payload is the
endpoint's request content, in the form the endpoint defines.

The tag values are normative as tabulated. Each endpoint has its own
section. Every section of this layer states requirements of the
server only: a sentence describing what the client sends states the
input the server serves, and imposes no requirement on the client.

- **An unreadable request is answered, not dropped.** A request whose
  payload the server cannot read — a tag the server does not define,
  or content that does not conform to the endpoint's form — is
  answered by a response finish with no response preceding it. The
  scope opens and closes; the client observes an unanswered request.
- **Growth is new tag values.** A future endpoint is a new tag value
  in this table. The frame types of the [Frames](/frames/) layer are
  unaffected by the addition of endpoints.
- **Capabilities.** The server states in the `capabilities` object
  of its [info](/endpoints/info/) response which of the parts of this
  layer it serves, as the [Capabilities](/capabilities/) layer
  defines, and answers every request past a part it does not serve by
  the response that layer names for the endpoint. Every requirement
  of this layer on an endpoint a capability governs holds subject to
  that layer.

## One open at a time

Six endpoints are held at most once each per connection:
[volumes::list](/endpoints/volumes-list/),
[images::list](/endpoints/images-list/),
[discover](/endpoints/discover/),
[daemons::accept](/endpoints/daemons-accept/),
[messages::listen](/endpoints/messages-listen/) and
[messages::send](/endpoints/messages-send/).

- **One at a time.** On one connection, at most one scope of each of
  the six endpoints is open at a time.
- **Open until its finish.** A scope of one of the six is open from
  the moment the server reads its request until the server sends its
  response finish.
- **Refused, not queued.** The server answers a request for one of
  the six endpoints, on a connection on which a scope of that
  endpoint is open, with exactly one response, the endpoint's
  already-open response, which its response page defines. The
  response finish follows it, and no other frame bearing the scope
  precedes or follows it. The server lists nothing and accepts nothing
  for the refused request, sends no message for it, and the open
  scope is unaffected.
- **Free before the finish.** The server ceases to hold a scope of
  one of the six open before it sends that scope's response finish.
  A request for the same endpoint that the server reads after it has
  sent that finish is not refused under this section.
- **Per endpoint, per connection.** The six endpoints are
  independent of one another. A scope open on one connection has no
  bearing on a request read on another connection, except as
  [daemons::accept](/endpoints/daemons-accept/) and
  [messages::listen](/endpoints/messages-listen/) provide for an
  identity.

## Image sources

The server obtains the image of a
[containers::agents::run](/endpoints/containers-agents-run/) request,
of a [containers::tools::run](/endpoints/containers-tools-run/)
request and of an [images::push](/endpoints/images-push/) request from
exactly one **source**. The image is the image the request's `digest`
names. The Store of a client is the set of images that the client
owns on the server: every image the client built by
[images::build](/endpoints/images-build/) or pushed by
[images::push](/endpoints/images-push/) and has not deleted by
[images::delete](/endpoints/images-delete/). An image is in a
client's Store when its digest is the digest of an image the client
owns.

| Source | Where the server obtains the image | Runs | Pushes |
|--------|------------------------------------|------|--------|
| `Registry` | a registry in the server's [`images_registries`](/capabilities/#images_registries) | yes | yes |
| `Client` | the client of the scope, on the scope's OCI channels | yes | yes |
| `Store` | the client's own Store | yes | no |

1. **Registry.** The source is `Registry` when the server obtains the
   image from a registry that is in its
   [`images_registries`](/capabilities/#images_registries) and that a
   reference of the request names, under the digest, or from bytes it
   holds that it obtained from such a registry under the digest. The
   `reference` member of the source is the reference under which the
   server obtained the image, of the form
   `<registry>/<name>@<digest>`.
2. **Client.** The source is `Client` when the server obtains the
   image from the client of the scope: the client answers the
   scope's `has` ask that it holds the image, and the server takes
   from the client, on the scope's manifest and blob channels, every
   manifest and every blob of the image that it does not already
   hold. The server may take from the client none of the image's
   bytes, where it already holds every byte of the image.
3. **Store.** The source is `Store` when the image is in the Store of
   the client of the scope. The server obtains the image from the
   bytes it holds for that Store, and asks the client for nothing.
4. **The order of a run.** For a
   [containers::agents::run](/endpoints/containers-agents-run/) or a
   [containers::tools::run](/endpoints/containers-tools-run/)
   request, the server consults the sources in the following order,
   and the first that applies is the source: `Store`, where the image
   is in the client's Store; otherwise `Registry`, where a registry
   that is in its `images_registries` and that a reference of the
   request names serves the digest; otherwise `Client`, where the
   client answers the `has` ask that it holds the image. Where none
   applies, the server obtains the image from no source, and the run
   ends with the error that the run's page states.
5. **The order of a push.** For an
   [images::push](/endpoints/images-push/) request, the server
   consults `Registry` and, where `Registry` does not apply,
   `Client`, in the order and on the terms of item 4.
6. **The Store source applies to runs only.** The source of a push is
   never `Store`. The server answers an
   [images::push](/endpoints/images-push/) request whose image is in
   the client's Store with `Exists`, and obtains nothing for it, as
   the push's page states.
7. **The nonce check.** The server makes the nonce check that
   [Possession](/shared/possession/) defines if, and only if, the
   source is `Client`. The server makes it after it holds every byte
   of the image, and before it deploys a container from the image or
   records the image in the client's Store. The server makes it
   whether or not it took any byte of the image from the client. The
   server makes no nonce check where the source is `Registry` or
   `Store`.
8. **The source is stated.** Every answer that states the success of
   a request whose image the server obtained carries a member
   `source`, the source from which the server obtained the image: the
   `Id` of a run, and the `Pushed` of a push. The source of a push is
   `Registry` or `Client`.
9. **A failed check.** When the nonce check fails, the server answers
   the request with `ProofFailed`, as the request's page states. The
   server deploys no container from the image and records no image in
   any Store. The server removes every manifest and every blob that
   it stored for the request and that no image in any client's Store,
   and no image whose nonce check passed before, references.

The source is defined by `diverge-sdk-rs/src/shared/containers/response/source.rs`.
In JSON, `Store` is exactly the string `"store"`, `Client` is exactly
the string `"client"`, and `Registry` is an object with the one member
`registry`, whose value is an object with the one member `reference`,
a string. In the postcard wire format, as the postcard reading of
[Notation](/endpoints/#notation) provides, the source is the varint
`0` followed by `reference` for `Registry`, the varint `1` for
`Client`, and the varint `2` for `Store`:

```rust include=diverge-sdk-rs/src/shared/containers/response/source.rs
```

## Notation

The JSON payloads of this layer are defined by type declarations,
written as Rust with serde attributes. The declarations are normative
for the JSON they describe — the protocol is not Rust, and the
notation binds no implementation language — under the following
reading:

- A `struct` is a JSON object. A field is a member of the same name,
  unless `#[serde(rename = "…")]` states the wire name; `r#type` is
  the member `type`.
- A field marked `#[serde(default, skip_serializing_if = …)]` may be
  absent, and absence has the marked default's meaning. An `Option`
  field without that marking is present, and may be `null`.
- An enum marked `#[serde(untagged)]` is exactly one of its variants'
  shapes, with no wrapper naming the variant.
- An enum of unit variants is a string: each variant's
  `#[serde(rename = "…")]` value, or its name in `snake_case` where
  `#[serde(rename_all = "snake_case")]` is stated. A one-variant enum
  is thereby a constant.
- A field marked `#[serde(flatten)]` contributes its members to the
  containing object; the field's own name never appears.
- `String` is a string; `bool` is a boolean; `u64` and `i64` are
  integers; `f64` and `Decimal` are numbers; `Vec<T>` is an array;
  `Vec<u8>` is an array of integers; a map is an object;
  `serde_json::Value` is any JSON value.
- Types named from `rmcp::model` are the types of the
  [Model Context Protocol specification](https://modelcontextprotocol.io/specification/2025-11-25),
  serialized as MCP defines them; they are incorporated by reference
  and not restated. Wherever a declaration references one, its
  definition in [rmcp](https://docs.rs/rmcp/3.1.2/rmcp/) 3.1.2 — the MCP
  implementation this revision builds against — is linked beneath the
  declaration.

The binary payloads of this layer that a page marks as postcard are
defined by the same type declarations, under the following reading,
which is the [postcard wire format](https://postcard.jamesmunns.com/wire-format):

- A `struct` is its fields, in declaration order, with no delimiter
  between them and no name before them.
- `u16`, `u32`, `u64` and `usize` are unsigned LEB128 varints: seven
  bits of the value per byte, least significant first, the high bit
  of every byte but the last set. A `u64` occupies at most 10 bytes.
  `u8` is one byte. `bool` is one byte, `0` or `1`.
- `String` is a varint byte length followed by that many bytes of
  UTF-8.
- `Vec<T>` is a varint count followed by that many elements, each
  encoded as `T`.
- An enum is a varint discriminant, the index of the variant in
  declaration order counted from `0`, followed by the variant's
  fields in declaration order.
- `Option<T>` is the byte `0`, or the byte `1` followed by `T`.
