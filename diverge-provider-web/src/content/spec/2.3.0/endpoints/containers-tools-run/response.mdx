The server sends the id, the volume that refused the run — held, or
in another mode — or an error, as the first response on the scope.
After the id, the server sends one response for every connector it
attaches to the container and one for every connector whose scope on
the container ends. The response finish ends the scope. No frame
bearing the scope follows the finish.

```text
[0][id JSON …]                  once, when the container is running
[1][volume-held JSON …]         once, when a named volume is held
[2][volume-mode JSON …]         once, when a named volume is not in the mode its mount names
[3][error JSON …]               once, when it is not running for another reason
[4][connector JSON …]           per connector attached, after the id
[5][connector JSON …]           per connector whose scope ended, after the id
```

- **The sequence.** Before the id, the server sends no response.
  The first response is the id, the volume that refused the run, or
  an error. A refusal and an error are each followed by the response
  finish, and the container is not running and will not be. After
  the id, the server sends zero or more connector responses, then
  the finish, and the finish carries no error: a run that ended after its id
  ended by the client's stop, by the container's own end, or by the
  client's connection ending. A response finish that no response
  precedes states that the request was not served, as
  [Endpoints](/endpoints/) provides, or that the run ended before the
  server had an id to send.
- **The id.** A payload whose first byte is `0` carries the id after
  that byte as JSON, an object with the member `id`, a string. The
  server sends it after every FUSE mount is complete and, for an
  agent container, after the agent is registered.
- **Volume held.** A payload whose first byte is `1` carries, after
  that byte as JSON, an object with the member `name`, a string: the
  `volume_name` of a volume the request named that is under a
  [volumes::stat](/endpoints/volumes-stat/),
  [volumes::edit](/endpoints/volumes-edit/) or
  [volumes::delete](/endpoints/volumes-delete/) at the time of the
  request, or a `persistent` volume that a running container mounts
  or a [volumes::serve](/endpoints/volumes-serve/) holds at the time
  of the request. An `ephemeral` or a `read_only` volume mounted in
  another container does not refuse a run: it may be mounted in any
  number of containers of the client at once. The server sends it
  before it fetches or deploys anything, and the finish follows. The
  container was not started.
- **Volume mode.** A payload whose first byte is `2` carries, after
  that byte as JSON, an object with the members `name`, a string, and
  `mode`, a string: the `volume_name` of a volume the request named
  under a `mode` the volume is not in, and the mode the volume is in,
  as the client's listing reports it, one of `persistent`,
  `ephemeral` and `read_only`. The server sends it after it has held
  the volume and given the hold back, before it fetches or deploys
  anything, and the finish follows. The container was not started,
  and the volume is as it was. A request naming one volume under two
  modes is answered the same way, with the mode the volume is in.
- **The error.** A payload whose first byte is `3` carries an error
  after that byte, exactly one JSON value in the form defined on the
  [volumes::list response](/endpoints/volumes-list/response/) page.
  This revision prescribes nothing about its content.
- **A connector attached.** A payload whose first byte is `4`
  carries, after that byte as JSON, an object with the members
  `identity`, a string, the identity under which the server
  authorized the connector's connection, and `address`, a string,
  the peer address of that connection as the server observed it.
  The server sends it once per
  [containers::tools::connect](/endpoints/containers-tools-connect/)
  scope it attaches to the container, after it has attached the
  connector and before it serves any channel of the connect scope,
  and never before the id. One identity connected twice is two
  connectors and two responses.
- **A connector gone.** A payload whose first byte is `5` carries
  the same object as a `4`. The server sends it once for every
  `4`, when that connect scope has ended — by the connector's
  disconnect, by the connector's connection ending, or by the run
  ending — and after the `4` it answers. A run that ends with
  connectors attached sends a `5` for each of them before the
  finish.
- **Malformed.** A payload with no byte, a payload whose first byte
  is none of `0`, `1`, `2` and `3`, a payload whose bytes after `0`
  do not parse as the id, a payload whose bytes after `1` or `2` do
  not parse as the refusal and a payload whose bytes after `3` are not one JSON
  value are malformed.
