A client opens the scope with a request whose payload is the tag byte
`8` followed by the name of a volume. The server sends exactly one
response, which is either `Serving` or an error. After `Serving` the
scope stays open: the client opens on it, as channels, the nine asks a
FUSE mount makes of a client — a stat, a read of a piece, a write of a
piece, a truncate, a setattr, a listing, a removal, a rename and a
mkdir — and the server answers each from the volume. The client's stop
ends the scope: the response finish follows the last answer, and no
frame follows the finish. After an error the response finish follows
the error, and no channel is served.

- **The request.** The request carries the name of one volume.
  [Request](/endpoints/volumes-serve/request/) states its form.
- **The volume named.** The client names a volume by the `name` its
  [volumes::list](/endpoints/volumes-list/) listing gave it. The
  server resolves the name against the identity under which the
  connection was authorized, as [Authorization](/authorization/)
  provides. A name that is not in the client's listing is answered
  with an error. A client cannot name another client's volume.
- **The response.** [Response](/endpoints/volumes-serve/response/) states the one response
  and what follows it.
- **The channels.** The client opens the channels that
  [Client Channels](/endpoints/volumes-serve/client/) defines: the nine asks, and the
  stop. The server opens no channel on a serve scope.
- **A served volume is a mounted volume.** The server holds the volume
  as a running container that mounts it holds it, from the moment it
  sends `Serving` until the response finish. Any number of serves and
  any number of running containers may hold one volume at once. While
  any of them holds it, a `volumes::stat`, `volumes::read`,
  `volumes::write`, `volumes::filetree`, `volumes::edit` or
  `volumes::delete` naming the volume is answered with an error. A
  volume that is under one of those six at the time of the request is
  not served: the request is answered with an error.
- **The asks are the mount's.** Each ask is, byte for byte, the ask a
  FUSE mount's scope carries on the container proxy, with no id: the
  scope is the volume, as the mount scope is the mount. Each answer is
  the answer that ask defines. A client that bridges a FUSE mount on
  one provider to a volume on another relays each ask and each answer
  as it is.
- **Every piece crosses as it is.** A read is one piece at an offset,
  a write lands one piece in place, and a stat is the entry's kind,
  size, mode, owner, group and times as the volume records them at the
  time of the answer. The server buffers no content of the volume on
  the client's behalf: what a write asks for is in the volume when
  the answer is `ok`.
- **Asks in flight at once.** A client may have any number of asks open
  at once. The server answers each on its own channel, in whatever
  order it answers them.
- **A volume that keeps nothing.** A volume whose `persist` is `false`
  is served. The server answers every stat, read and listing of it as
  it answers those of any volume, and answers every write, truncate,
  setattr, removal, rename and mkdir of it with the ephemeral byte:
  the change is refused, and the volume is as it was.
- **The stop.** The client ends the scope by opening the stop channel.
  The server answers every ask still open, sends the response finish,
  and gives the volume back. The server sends nothing on the stop's
  own channel. A connection that closes with a serve scope open ends
  the scope the same way: the server gives the volume back.
- **The error.** An error states that the volume is not served, and
  that nothing was determined about the volume. A volume absent from
  the client's listing, a volume under a `volumes::stat`,
  `volumes::read`, `volumes::write`, `volumes::filetree`,
  `volumes::edit` or `volumes::delete` at the time of the request, and
  a volume the server could not open are each answered with an error.
