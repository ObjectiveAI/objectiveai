A server serves every endpoint of the [Endpoints](/endpoints/)
layer: it reads every request and answers it as that layer provides.
Some of what a request may ask, a server may not do: run
containers, keep the Store, pull from a registry, keep volumes of a mode, let more
than one party hold a volume at once. Each such part is a
**capability**. The server states the capabilities it holds out in
the `capabilities` object of its [info](/endpoints/info/) response,
and this layer defines that object and binds the server by it: for
every capability, the endpoints it governs, what the server does
where it holds the capability out, and exactly what the server sends
for a request past a capability it does not hold out.

- **The object is a fact of the server.** The server sends the same
  `capabilities` object in every `info` response it sends, on every
  connection, for as long as it runs. The object does not depend on
  the identity under which a connection was authorized, on the
  request, or on the time.
- **A capability held out is served.** A server that holds out a
  capability serves the endpoints it governs as the pages of the
  Endpoints layer state, in full, and sends none of the responses
  this layer defines for the capability's absence.
- **A capability not held out is refused as this layer states.** A
  server that does not hold out a capability answers every request
  past it with exactly the response this layer names for that
  endpoint, as the first and only response on the scope, followed by
  the response finish, serves no channel on the scope, looks nothing
  up for the request, holds nothing, fetches nothing, deploys
  nothing and changes nothing. The server sends no error, no other
  refusal and no bare finish in place of the response named.
- **Every page of the Endpoints layer is read with this one.** A
  requirement of an endpoint page that a capability governs holds
  where the server holds the capability out; where it does not, the
  response this layer names is the whole of the server's answer, and
  the endpoint page's requirements on what follows the request do
  not arise.

## The object

The `capabilities` member of the info response is one JSON object,
read as [Notation](/endpoints/#notation) provides, with the members
tabulated. Every member is optional. An absent member has the meaning
the table gives its absence, and a server that does not hold out a
capability may send the member with that value or omit it; the two
are one statement. The server sends no member this revision does not
define.

| Member | Type | Absent | Governs |
|--------|------|--------|---------|
| `containers` | boolean | `false` | [containers::agents::run](/endpoints/containers-agents-run/) and [containers::tools::run](/endpoints/containers-tools-run/) |
| `images_store` | boolean | `false` | [images::list](/endpoints/images-list/), [images::stat](/endpoints/images-stat/), [images::build](/endpoints/images-build/), [images::push](/endpoints/images-push/), [images::edit](/endpoints/images-edit/), [images::delete](/endpoints/images-delete/), the client's Store as a source of [images::has](/endpoints/images-has/), [images::oci](/endpoints/images-oci/) and [images::hash](/endpoints/images-hash/), and the `Store` source of a run |
| `images_registries` | array of strings | `[]` | the registries as a source of [images::has](/endpoints/images-has/), [images::oci](/endpoints/images-oci/) and [images::hash](/endpoints/images-hash/), and the `Registry` source of a run and of an [images::push](/endpoints/images-push/) |
| `volumes_persistent` | object, [the mode object](#the-mode-object) | every member `false`: no volume of the mode | the eleven volume endpoints, and the volume mounts of the two runs, for a volume whose `mode` is `persistent` |
| `volumes_ephemeral` | object, [the mode object](#the-mode-object) | every member `false`: no volume of the mode | the same, for a volume whose `mode` is `ephemeral` |
| `volumes_read_only` | object, [the mode object](#the-mode-object) | every member `false`: no volume of the mode | the same, for a volume whose `mode` is `read_only` |
| `messages` | object, [the messages object](#messages) | no object: no message is relayed | [messages::listen](/endpoints/messages-listen/) and [messages::send](/endpoints/messages-send/) |

## `containers`

The server runs containers: the agent containers of
[containers::agents::run](/endpoints/containers-agents-run/) and the
tool containers of
[containers::tools::run](/endpoints/containers-tools-run/), as the
pages of those endpoints define.

- **Held out.** The server serves
  [containers::agents::run](/endpoints/containers-agents-run/) and
  [containers::tools::run](/endpoints/containers-tools-run/) as their
  pages state.
- **Not held out.** The server runs no container. The server
  answers:
  - a [containers::agents::run](/endpoints/containers-agents-run/)
    request with exactly one response, the byte `10` and nothing
    else, and the response finish;
  - a [containers::tools::run](/endpoints/containers-tools-run/)
    request with exactly one response, the byte `9` and nothing else,
    and the response finish.

  The server sends the response before it checks the request's
  mounts or image, and it decides none of the volume refusals of
  [the hold](#the-hold) for the request. It sends no id, opens no
  channel on the scope, and answers no channel the client opens on
  the scope.

## `images_store`

The server keeps the Store: for each client, the images the client
owns on the server, each named by its digest alone — every image the
client builds by [images::build](/endpoints/images-build/) or pushes
by [images::push](/endpoints/images-push/) and has not deleted — held
for the client and for no other identity, as
[Image sources](/endpoints/#image-sources) and the pages of those
endpoints define.

- **Held out.** The server serves [images::list](/endpoints/images-list/),
  [images::stat](/endpoints/images-stat/),
  [images::build](/endpoints/images-build/),
  [images::push](/endpoints/images-push/),
  [images::edit](/endpoints/images-edit/),
  and [images::delete](/endpoints/images-delete/) as their pages
  state; the client's Store is a source from which the server answers
  [images::has](/endpoints/images-has/), serves
  [images::oci](/endpoints/images-oci/) and computes the proof of
  [images::hash](/endpoints/images-hash/); and the `Store` source of
  [Image sources](/endpoints/#image-sources) is a source of a run.
- **Not held out.** The server keeps no Store. The client's Store is
  not a source of [images::has](/endpoints/images-has/),
  [images::oci](/endpoints/images-oci/) or
  [images::hash](/endpoints/images-hash/), and no run's image has the
  source `Store`. The server answers:
  - an [images::list](/endpoints/images-list/) request with exactly
    one response, the byte `4` and nothing else, and the response
    finish; it sends no image, no byte `3` and no byte `5`;
  - an [images::stat](/endpoints/images-stat/) request with exactly
    one response, the byte `1` and nothing else, and the response
    finish;
  - an [images::build](/endpoints/images-build/) request with exactly
    one response, the byte `5` and nothing else, and the response
    finish; it sends no line of output before it, and builds nothing;
  - an [images::push](/endpoints/images-push/) request with exactly
    one response, the byte `7` and nothing else, and the response
    finish; it sends no blob response before it, opens no channel and
    obtains nothing;
  - an [images::edit](/endpoints/images-edit/) request with exactly
    one response, the byte `2` and nothing else, and the response
    finish;
  - an [images::delete](/endpoints/images-delete/) request with
    exactly one response, the byte `2` and nothing else, and the
    response finish;
  - where [`images_registries`](#images_registries) is empty, an
    [images::has](/endpoints/images-has/) request and an
    [images::hash](/endpoints/images-hash/) request each with exactly
    one response, the byte `2` and nothing else, and the response
    finish, and an [images::oci](/endpoints/images-oci/) request with
    exactly one response on the main stream, the byte `1` and nothing
    else, and the response finish, after which it answers no channel
    the client opens on the scope. Where `images_registries` is not
    empty, the server answers each of the three from the registries
    alone.
- **The `images_disk` member of a capacity response.** The server
  sends the `images_disk` member of every
  [capacity](/endpoints/capacity/) response whether or not it holds
  out `images_store`. Where it does not, the member carries any
  value, and a client does not read it.

## `images_registries`

The registries the server pulls images from: an array of strings,
each the host of one registry as a reference's `registry` member
names it — `docker.io`, `ghcr.io`, `registry.example.com:5000` — and
every registry the server pulls from is in the array.

- **The registries as a source.** Where the client's Store does not
  supply the image, the server answers an
  [images::has](/endpoints/images-has/) request, serves an
  [images::oci](/endpoints/images-oci/) scope, and computes the proof
  of an [images::hash](/endpoints/images-hash/) request by consulting
  exactly the registries in the array that a reference of the request
  names, as `<registry>/<name>@<digest>`. A reference naming a
  registry not in the array is ignored. The registries are a source
  the server has when the array is not empty.
- **A run's image and a push's image.** A server obtains the image of a
  [containers::agents::run](/endpoints/containers-agents-run/), of a
  [containers::tools::run](/endpoints/containers-tools-run/) or of an
  [images::push](/endpoints/images-push/) from a
  registry only where the registry is in the array and a reference
  of the request names it; it obtains an image from no registry the
  array does not list.
- **Empty.** An empty array, or an absent member, states that the
  server pulls from no registry. The registries are not a source the
  server has. Where [`images_store`](#images_store) is also `false`,
  the server answers an [images::has](/endpoints/images-has/) request
  and an [images::hash](/endpoints/images-hash/) request each with
  exactly one response, the byte `2` and nothing else, and the
  response finish, and an [images::oci](/endpoints/images-oci/)
  request with exactly one response on the main stream, the byte `1`
  and nothing else, and the response finish. Where `images_store` is
  `true`, the server answers each of the three from the client's Store
  alone. A run's image is obtained from the
  client's Store or from the client, and a push's image from the
  client, as [Image sources](/endpoints/#image-sources) states, and
  from no registry.

## `messages`

The server relays direct messages between the identities connected to
it, at most at the rate the object states, as the pages of
[messages::listen](/endpoints/messages-listen/) and
[messages::send](/endpoints/messages-send/) define.

- **The object.** The object has exactly the members `messages` and
  `seconds`, each an integer from `1` to `4294967295`: at most
  `messages` sends of one identity in one window of `seconds` seconds.
  Both members are present whenever the object is present. A server
  that relays messages holds out the object; no server relays
  messages without a rate.
- **Held out.** The server serves
  [messages::listen](/endpoints/messages-listen/) and
  [messages::send](/endpoints/messages-send/) as their pages state,
  and counts every send against the window the
  [messages::send](/endpoints/messages-send/#the-window) page defines.
- **Not held out.** The server relays no message. The server answers:
  - a [messages::listen](/endpoints/messages-listen/) request with
    exactly one response, the byte `2` and nothing else, and the
    response finish; it opens no mailbox;
  - a [messages::send](/endpoints/messages-send/) request with exactly
    one response, the byte `4` and nothing else, and the response
    finish; it queues nothing and counts nothing.

The object is defined by
`diverge-sdk-rs/src/provider/endpoints/info/server/response/messages_capabilities.rs`:

## What every server does

Every server that holds out [`containers`](#containers) makes every
FUSE mount a run request names, and every mount a client asks for on
the fuse-mount channel of a run, and
serves every [containers::fuse_serve](/endpoints/containers-fuse-serve/)
request, as those pages state: no capability governs them, and the
`capabilities` object has no member for them.

## The volume modes

Each of `volumes_persistent`, `volumes_ephemeral` and
`volumes_read_only` is [the mode object](#the-mode-object) for
volumes whose `mode` is, respectively, `persistent`, `ephemeral` and
`read_only`, as [volumes::create](/endpoints/volumes-create/) defines
the three modes: what the server does with a volume of the mode. A
mode object with at least one member `true` is a mode the server
holds out, and keeps volumes in; a mode object with every member
`false` — or absent, which is the same statement — is a mode the
server does not hold out.

- **Held out.** The server keeps volumes of the mode. A
  [volumes::list](/endpoints/volumes-list/) listing of the server
  may contain a volume of the mode, a
  [volumes::create](/endpoints/volumes-create/) request may state the
  mode, and a [volumes::edit](/endpoints/volumes-edit/) request may
  change a volume into the mode. What a running container, a FUSE
  serve and an operation may do with a volume of the mode is the
  mode object.
- **Not held out.** The server keeps no volume of the mode. No listing of
  the server contains a volume of the mode. The server answers a
  [volumes::create](/endpoints/volumes-create/) request whose `mode`
  is the mode with exactly one response, the byte `2` and nothing
  else, and the response finish, and creates nothing. The server
  answers a [volumes::edit](/endpoints/volumes-edit/) request whose
  change states the mode — as `Mode`, or as `Both` — and names a
  volume in the client's listing with exactly one response, the byte
  `3` and nothing else, and the response finish, and changes nothing;
  a request naming a volume not in the listing is answered with the
  error the edit page states, whatever the change.
- **None held out.** A server that holds out none of the three keeps
  no volume at all, and the eleven volume endpoints are not served.
  The server answers every request of each with exactly one
  response, the byte tabulated and nothing else, and the response
  finish; it sends nothing else on the scope, serves no channel, and
  neither lists, examines, reads, writes, walks, serves, measures,
  creates, edits nor deletes anything for the request. Such a server
  has no volume a run can name: a run request whose `volume_mounts`
  has an entry is answered with the error the run pages state for a
  volume not in the client's listing, and an
  [images::build](/endpoints/images-build/) request naming a context
  is answered with the error its page states for a volume not in the
  client's listing.

| Endpoint | The byte, alone |
|----------|-----------------|
| [volumes::list](/endpoints/volumes-list/) | `4` |
| [volumes::stat](/endpoints/volumes-stat/) | `4` |
| [volumes::read](/endpoints/volumes-read/) | `4` |
| [volumes::write](/endpoints/volumes-write/) | `4` |
| [volumes::filetree](/endpoints/volumes-filetree/) | `4` |
| [volumes::fuse_serve](/endpoints/volumes-fuse-serve/) | `5` |
| [volumes::create_capacity](/endpoints/volumes-create-capacity/) | `1` |
| [volumes::create](/endpoints/volumes-create/) | `3` |
| [volumes::edit_capacity](/endpoints/volumes-edit-capacity/) | `1` |
| [volumes::edit](/endpoints/volumes-edit/) | `7` |
| [volumes::delete](/endpoints/volumes-delete/) | `4` |
- **The `volumes_disk` member of a capacity response.** The server
  sends the `volumes_disk` member of every
  [capacity](/endpoints/capacity/) response whether or not it holds
  out a mode object. Where it holds out none, the member carries any
  value, and a client does not read it.

## The mode object

The value of each of `volumes_persistent`, `volumes_ephemeral` and
`volumes_read_only` is one JSON object of five boolean members, each
optional, an absent member being `false`. The object with every
member `false` is the mode not held out, and is what an absent mode
member means; every rule below that speaks of a mode object absent
speaks of that object too.

| Member | `true` states that |
|--------|--------------------|
| `mount` | a running container of the client may mount a volume of the mode |
| `fuse_serve` | a [volumes::fuse_serve](/endpoints/volumes-fuse-serve/) scope of the client may hold a volume of the mode |
| `mount_many` | more than one running container may mount a volume of the mode at once |
| `fuse_serve_many` | more than one FUSE serve may hold a volume of the mode at once |
| `mount_and_fuse_serve` | a running container and a FUSE serve may hold a volume of the mode at once |

- **The mode allows at most.** A mode allows at most what
  [volumes::create](/endpoints/volumes-create/) states for it: a
  `persistent` volume may be mounted in any number of running
  containers at once, is held by at most one FUSE serve at a time,
  and is never held by a FUSE serve and a running container at once;
  an `ephemeral` or a `read_only` volume may be held by any number of
  running containers and FUSE serves at once. A server holds out no
  more than the mode allows: the `volumes_persistent` object has
  `fuse_serve_many` and `mount_and_fuse_serve` `false`, absent or
  present.
- **Consistency.** A server that sends `mount_many` `true` sends
  `mount` `true`. A server that sends `fuse_serve_many` `true` sends
  `fuse_serve` `true`. A server that sends `mount_and_fuse_serve`
  `true` sends `mount` `true` and `fuse_serve` `true`.
- **One running container is one holder.** A running container that
  mounts a volume at several `container_path`s of one request is one
  running container holding the volume. An
  [images::build](/endpoints/images-build/) that names a directory
  of the volume as its context holds the volume as one running
  container does, for the life of the build.

## The hold

The server holds a volume for a running container from the moment it
accepts the run request that names the volume until the run ends;
for a FUSE serve from the moment it sends `Serving` until the
response finish; for a build naming the volume as its context from
the moment it accepts the build request until the response finish;
and to itself for a [volumes::stat](/endpoints/volumes-stat/),
[volumes::read](/endpoints/volumes-read/),
[volumes::write](/endpoints/volumes-write/),
[volumes::filetree](/endpoints/volumes-filetree/),
[volumes::edit](/endpoints/volumes-edit/) or
[volumes::delete](/endpoints/volumes-delete/), an **operation**,
from the moment it accepts the request until the response finish, a
delete never giving the hold back. Whether a request that would hold
a volume is served is decided by the volume's `mode`, by the mode
object the server holds out for the mode, and by who holds the
volume at the time of the request, in the order stated below, the
first rule that applies deciding; the decision and the hold it takes
are one act, between which no other hold of the volume is taken or
given back and no edit of the volume lands.

- **No containers.** A server that does not hold out
  [`containers`](#containers) holds no volume for a run request and
  decides none of the rules below for it.
- **A run's volume mount.** For each distinct `volume_name` a run
  request names, in the order first named: (1) a volume not in the
  client's listing is the run's error; (2) a volume whose `mode` is
  not the `mode` of every mount naming it is `VolumeMode`, carrying
  the name and the mode the volume is in; (3) a volume of a mode
  whose object is absent, or whose `mount` is `false`, is
  `VolumeMountUnsupported`, carrying the name; (4) a volume an
  operation holds is `VolumeHeld`, carrying the name; (5) a volume a
  running container holds, where `mount_many` is `false`, is
  `VolumeMounted`, carrying the name; (6) a volume a FUSE serve
  holds, where `mount_and_fuse_serve` is `false`, is
  `VolumeFuseServed`, carrying the name; (7) otherwise the server
  holds the volume for the run. A refusal of any volume gives back
  every volume held for the request before it, and the server
  fetches nothing and deploys nothing for the request. The run pages
  state each response's form.
- **A FUSE serve.** For the volume a [volumes::fuse_serve](/endpoints/volumes-fuse-serve/)
  request names: (1) a volume not in the client's listing is the
  error; (2) a volume whose `mode` is not the request's `mode` is
  `VolumeMode`, carrying the name and the mode the volume is in; (3)
  a volume of a mode whose object is absent, or whose `fuse_serve` is
  `false`, is `Unsupported`; (4) a volume an operation holds is
  `Held`; (5) a volume another FUSE serve holds, where
  `fuse_serve_many` is `false`, is `FuseServed`; (6) a volume a
  running container holds, where `mount_and_fuse_serve` is `false`,
  is `Mounted`; (7) otherwise the server holds the volume for the
  FUSE serve. That page states each response's form.
- **An operation.** For the volume an operation names: (1) a volume
  not in the client's listing is the error; (2) a volume another
  operation holds is `Held`; (3) a volume a running container holds
  is `Mounted`; (4) a volume a FUSE serve holds is `FuseServed`; (5)
  otherwise the server holds the volume to itself for the operation.
  Each operation's page states each response's form.
- **A build's context.** For the volume an [images::build](/endpoints/images-build/)
  request names as its context: (1) a volume not in the client's
  listing is the error; (2) a volume an operation holds, a volume a
  running container holds where the mode object is absent or its
  `mount_many` is `false`, and a volume a FUSE serve holds where the
  mode object is absent or its `mount_and_fuse_serve` is `false`, are
  each `ContextHeld`; (3) otherwise the server holds the volume for
  the build. That page states each response's form.
- **Who holds, as of the request.** A running container holds a
  volume from the moment the server holds it for the run until the
  run ends, whether or not the id has been sent. A FUSE serve holds a
  volume from `Serving` until the response finish. An operation
  holds a volume from the moment the server accepts the request until
  its response finish.
