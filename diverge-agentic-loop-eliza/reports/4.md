# Report 4: making Eliza work

A design, written before any of it is built. Reports 1–3 mapped the
pinned ElizaOS source (commit `90bb56ea`, root 2.0.4 / core
2.0.3-beta.7) and proposed a container against the API of their day.
That API is gone: the containers API of `STATUS_REPORT_14` replaced
it, and three of its rulings override report 3 directly. This report
says what the Eliza container is under the current API and the new
rulings, what is settled by evidence, what is chosen, and what a live
run has to prove.

## Where things stand

The crate is a skeleton. `src/main.rs` is 124 lines that build a
router, refuse the run with `501`, and answer the queue verbs as a
container whose run will never begin; it imports
`agentic_loop_container`, which no longer exists, so the crate — and
with it the workspace — does not build. The `Containerfile` copies
two proxy crates that were deleted and bakes them into the image. The
agent types still live in the provider SDK under `agents::agent::
eliza`, which by that module's own doc is the mark of an image that
has not been brought up. Nothing of report 3's proposal was ever
implemented. This is a fresh build, not a migration.

## The rulings this design answers to

1. **Agent arguments include arbitrary plugins.** The container
   installs plugins based on what the agent needs. Report 3's "third-
   party plugins: no" is overruled.
2. **Plugin settings split by kind.** Auth secrets come from the
   vault; non-auth configuration comes from the agent. Nothing secret
   is ever an argument.
3. **All other state goes to Postgres.** Eliza itself is pointed at
   the caller's database through the proxy's pgwire, and the harness
   keeps any continuation state of its own in custom tables beside
   Eliza's.
4. **Everything the other containers keep** (`STATUS_REPORT_14`): the
   agent's own HTTP server at `agent::port()` with `/run`, `/schema`,
   `/enqueue`, `/dequeue`; the proxy injected by the host and touched
   by nothing before a request; one run at a time with the lock the
   settlement's; the agent types owned by the crate with a derived
   schema; the image the harness alone.

## The thesis: the continuation is the database

This is the one place Eliza is simpler than every container before
it. `@elizaos/plugin-sql` speaks real Postgres: `createDatabaseAdapter`
takes `POSTGRES_URL` first and falls back to PGlite only without it
(`plugins/plugin-sql/src/index.ts:123-172`, `:233-242`). Set
`POSTGRES_URL` to the container SDK's `postgres_url()` and Eliza's
entire state — agents, memories, embeddings, entities, rooms, worlds,
relationships, logs, cache, tasks, thirty-five schema modules — lives
in the caller's database from the first turn, written by Eliza, read
by Eliza. There is no PGlite directory, no lock artifacts to strip,
no fold, no tagged frames, no ingest before start, no harvest at the
end. Report 2's F1–F3 and report 3's §8 — the sidecar, the path-header
chunk encoding, the non-fast stop before harvest — describe a problem
that no longer exists, and are withdrawn.

What the harness itself must remember across runs is small, and goes
in one custom table:

```sql
CREATE TABLE IF NOT EXISTS eliza_lineage (
    id smallint PRIMARY KEY CHECK (id = 1),
    agent_id uuid NOT NULL,
    room text NOT NULL,
    embedding_dimensions integer,
    plugins jsonb NOT NULL
)
```

- `agent_id` is the identity. Every Eliza id derives from it
  (`createUniqueUuid` is `stringToUuid("<external>:<agentId>")`,
  `packages/core/src/entities.ts:763-773`), and it is pinned by the
  runtime constructor's `opts.agentId` — a source between
  `character.id` and the name hash that report 2 B3 missed
  (`packages/core/src/runtime.ts:1582-1585`). Since the harness
  constructs the runtime, the identity is one argument: minted as a
  v4 UUID on the first run, stored, read back after. A renamed
  character keeps its memory, and no `character.id` is injected.
- `room` is the conversation's external id, constant for the lineage
  (`"diverge"`); the room UUID derives from it and the agent id, so
  resumption is "same agent id, same room", and there is no session
  tip to compute — report 2 F7 stands.
- `embedding_dimensions` is what the vectors were built at, so a run
  that names a different width is warned before Eliza silently drops
  or re-embeds (report 2 C4).
- `plugins` records each installed package with the version npm
  resolved, so the next run of the lineage installs the same code
  and not whatever the registry has moved to.

The row is read at the top of every run and cached in memory after
the first, the way cc caches its session id: a later run reads no row
for the identity. It is written on the first run, and again whenever
the plugin set or the embedding width changes.

Three things the caller's database has to allow, to be proven live:
`CREATE EXTENSION IF NOT EXISTS` for `vector`, `fuzzystrmatch` and
`pg_trgm` (`plugins/plugin-sql/src/runtime-migrator/extension-manager.
ts:2,27`), DDL on every cold start since `DatabaseMigrationService`
migrates each plugin's schema at boot (`migration-service.ts:1-8`),
and the thirty-five tables landing in the caller's namespace beside
`eliza_lineage`. `ENABLE_DATA_ISOLATION` stays off — it demands an
`ELIZA_SERVER_ID` and row-level security the caller did not ask for.

## The agent value

The types move out of the SDK into `src/agent/`, drop `Upstream`, and
derive `JsonSchema`; `GET /schema` is `schema_for!(Agent)`. The shape
changes in three ways: every secret leaves it, arbitrary plugins
enter it, and the plugin settings the caller states are typed as
what they are.

```text
Agent {
    character:  Character            // as report 3: name, system, bio,
                                     // topics, adjectives, style,
                                     // message_examples; no id, no
                                     // plugins, no settings, no secrets
    provider:   Provider { base_url, model }          // OPENAI_API_KEY from the vault
    embedding:  Option<Embedding { base_url, model, dimensions }>
                                                      // EMBEDDING_API_KEY from the vault
    memory:     Memory               // the four booleans, as report 3
    toolsets:   Toolsets             // coding_tools, browser, documents,
                                     // generate_media: booleans;
                                     // web_search: bool — TAVILY_API_KEY
                                     // from the vault
    plugins:    Vec<Plugin>          // NEW
}

Plugin {
    package:  String                 // an npm spec: "@elizaos/plugin-discord",
                                     // "@elizaos/plugin-discord@2.0.4",
                                     // "@scope/anything"
    settings: Map<String, Value>     // non-auth configuration, by the
                                     // setting name the plugin reads
    secrets:  Vec<Secret>            // the settings that are secrets;
                                     // each is a VAULT KEY
}

Secret  = "NAME"                     // static: get once per run
        | { key: "NAME", rotates: Rotates }
Rotates = true                       // rotated in place: read back
                                     // getSetting(key)
        | { setting: "OTHER" }       // read back another setting
        | { file: ["a", "b"] }       // read back a file, the path
                                     // components from the root
```

**Secrets are vault keys named by the setting they fill.** A plugin
reads `DISCORD_API_TOKEN` through `runtime.getSetting`; the vault holds
it under `DISCORD_API_TOKEN`; the agent says `secrets:
["DISCORD_API_TOKEN"]`; the harness gets it and puts it where the
plugin reads it. The same rule covers the three secrets report 3
carried as arguments: `OPENAI_API_KEY`, `EMBEDDING_API_KEY` and
`TAVILY_API_KEY` are fixed vault keys implied by the structures that
need them, and the `api_key` fields are gone. One rule, no exceptions,
and a secret never appears in the agent value, in the character, in a
row, or in the schema. A bare name is a static
secret, and its cycle is `get` only — no lock, no set.

**A rotating secret says where the rotated value lands.** A plugin
that rotates a login — an OAuth refresh token that is single-use —
names it as `{key, rotates}`, and `rotates` names the one of two
places an elizaOS plugin can leave the rotated value: the setting of
the same name (`true`, the plugin called `setSetting` in place),
another setting, or a file. Its cycle is Hermes's: lock the key for
the run, refreshed on a task; get; set as the setting; after EVERY
turn and at the end, read the value back from the named place, set it
into the vault; unlock at the end. Reading back per turn, not only at
the end, is what the in-process runtime allows and Hermes could not:
a container that dies mid-run has already put the last rotation
where the caller's next run finds it. A read-back that finds nothing
new is nothing; one that finds nothing at all is a run-end warning
naming the key.

**Credentials never live in the database.** The caller's database
will be snapshotted and rewound — that is how a lineage rewinds — and
a credential rewound is a login burned. Eliza is built on the same
expectation, a plugin keeping its credentials in settings rather
than tables, and this container assumes it: a plugin that persists a
rotating credential in a table of its own cannot be supported, and
there is no read-back from the database on purpose. Eliza's cache is
the database too, so it is not a channel either. The vault is the
home; the harness re-applies the vault's copy at the top of Eliza's
setting precedence at every run's start, so a rewound row never wins
over the vault.

**Settings are the plugin's own names.** ElizaOS has no other
vocabulary: a plugin is configured by string keys read through
`runtime.getSetting` (`packages/core/src/runtime.ts:3686-3692`), and
the caller who chose the plugin knows its keys. Values are JSON
values; the harness renders them as the strings Eliza expects
(`"true"`/`"false"` come back as booleans, `runtime.ts:3709`).

### Where each setting is put, and why both places

`runtime.getSetting()` deliberately never reads `process.env` — the
core says so in its header (`runtime.ts:16-19`) and resolves
`character.secrets` → `character.settings` → `settings.extra` →
`settings.secrets` → `character.env` → the constructor `settings` map.
Some plugins add a `process.env` tail of their own — plugin-openai's
`getSetting` (`plugins/plugin-openai/utils/config.ts:20-30`) and
plugin-embeddings do — but `plugin-sql` reads `POSTGRES_URL` through
the core path with no shim. So the harness puts EVERY setting and
every secret in the runtime's constructor `settings` map, and the
same set in the entry process's environment for the plugins that
look there. Nothing goes in `character.secrets`, so nothing in the
`agents` row is encrypted and `SECRET_SALT` is a throwaway per run
(report 3's rule, kept). Report 3 §9's "the process env is the
configuration" was half wrong, and this is the correction.

### The alternative considered: a script per plugin

The question was raised whether each plugin should be configured by a
script of its own — a small program per plugin that turns the agent's
configuration and the vault's secrets into whatever that plugin
needs. It would absorb any plugin's quirks and make adding a plugin
adding a script. It is not recommended, on the evidence: at this pin
every plugin is configured the same way, by named settings through
one function, so there are no quirks to absorb; a script would need
a Python in the image and would be the one place secrets pass through
outside the harness's control; and it would move the knowledge of a
plugin's keys from the caller, who chose it, to a script the image
has to ship before the caller can use the plugin — which is
report 3's closed set by another name. The declarative shape above
carries the same information. The decision is recorded as one to
revisit if a live run finds a plugin that cannot be configured
through settings and environment; then a per-plugin hook earns its
place, and not before.

### What is not in the value, still

`character.plugins` (nothing in the runtime honors it; the
constructor's `plugins` array of objects is what loads, `runtime.ts:
1626`), `settings` and `secrets` on the character, `templates`, `id`,
`knowledge`, connectors, wallets, cloud and host plugins — report 3's
absences hold, and the arbitrary-plugins ruling does not reopen them:
a plugin the caller wants arrives through `plugins`, configured
through its own keys, not through Eliza's host machinery.

## Installing plugins

The harness's Node project lives in the image at a fixed path with
`@elizaos/core`, `@elizaos/plugin-sql`, `plugin-openai`,
`plugin-embeddings`, `plugin-coding-tools`, `plugin-browser`,
`plugin-documents`, `plugin-agent-skills` and the harness's own
`diverge` plugin installed at build time, versions pinned to the
source pin. Everything the agent's `plugins` names that is not
already present is installed at `POST /run`, before the runtime
starts: `bun add --ignore-scripts <spec>` into that project (the
command ElizaOS's own installer runs, `packages/agent/src/services/
plugin-installer.ts:903-911`), npm as the fallback the same code
keeps. The install is the one thing a run does before the proxy is
touched, and it is not the proxy's — it is the registry's, over the
network the container has. The resolved version of each package is
read back from the project's lockfile and recorded in
`eliza_lineage.plugins`; a later run of the lineage installs
`name@<that version>`, whatever the agent's spec said, so a
conversation is never resumed against a plugin that changed under it.
A spec the registry cannot resolve, or a package that is not an
ElizaOS plugin once imported (no `Plugin` default or named export),
refuses the run before the runtime starts.

Installs are cached for the program's life: a package already in the
project is not reinstalled, so a second run with the same plugin set
installs nothing.

Two things are accepted, not solved. A third-party plugin is
arbitrary JavaScript imported into the agent's process with the
caller's MCP tools reachable — the isolation ElizaOS declares is
unimplemented at this pin (`installRemotePlugin` throws, `runtime.ts:
13600-13605`) — and the container is the sandbox, exactly as it is
for Hermes's yolo mode and Claude Code's skipped permissions. And an
install needs the npm registry reachable from the container at run
time, the way cc needs it at startup.

## The runtime, and how the harness drives it

Report 3 §9 stands: the harness runs its own Node entry over
`@elizaos/core`, never the `@elizaos/agent` host. The host always
loads eleven plugins of its own, serves a two-hundred-module HTTP
surface, folds environment into `character.secrets`, and has no
working abort route; the library gives one process, one
`AgentRuntime`, and `handleMessage` with the full-fidelity firehose
(`packages/core/src/services/message.ts:13424-13432`). The template
is ElizaOS's own headless example (`packages/examples/code/src/lib/
agent.ts:86-156`): import the plugins, `new AgentRuntime({character,
plugins, settings, agentId})`, `initialize()`, and `stop()` at the end.

The entry process is started per run, like Hermes's gateway, because
the agent value — and so the plugin set — may differ between runs. It
is spawned with the environment above, its stdin and stdout the
harness's: the harness writes one JSON line per turn (the input, the
room, the options), the entry answers JSON lines — the stream chunks
as they come, a `done` with the turn's result — and the harness
converts them to the chunk vocabulary exactly as cc converts Claude
Code's stream-json. `onStreamChunk` delivers text deltas and, inside
the same string, JSON envelopes for tool calls, tool results and
evaluations (`message.ts:13930-13963`); the discriminator has to be
verified in the source before the converter is written, and is the
first thing to verify. Usage, if the turn reports any, rides `done`;
if it does not, the harness says so in a non-fatal notification
rather than inventing a bill.

Readiness is the entry's own `ready` line after `initialize()`
returns, not a port poll. A failure before it — an install that
fails, a plugin that will not import, a database that will not
migrate, an embedding probe that fails fatally — is the stream's one
`Err`, the server's status. After it, every failure is a fatal
notification, and the run still stops the runtime.

The stop is `runtime.stop()` in its ordinary mode, never fast: the
post-turn work — facts, reflection, the embedding queue — is the
lineage's memory, and it lands in the database only if the runtime is
allowed to finish it. That is the one place Eliza's ending is slower
than another container's, and it is the whole reason the database is
consistent at the next run.

## The turn, and the queue

One `handleMessage` at a time. The harness serializes turns itself and
never uses Eliza's supersede semantics (`keepExistingResponses` is
moot). The queue is the container's own — openrouter's `queue.rs`, as
Hermes carries it — and it is taken at each turn's end: pending
messages are each answered `delivered`, yielded as a `user` chunk, and
joined with a blank line into the next turn's input in the same room;
an empty queue at a turn's end closes it in the same lock hold and
ends the run. Invoking Eliza again is the delivery, as it is for
Hermes.

In-process Eliza offers what Hermes cannot: `MessageProcessingOptions.
abortSignal` (`packages/core/src/types/message-service.ts:52`) is a
real cancellation handle. It is used for one thing — the teardown,
when the stream drops — and not for steering: a message that arrived
mid-turn waits for the seam, because a turn cut short would leave
half a response in the lineage's memory, and the seam is what every
other container does.

## One run at a time, and the settlement

cc's three-phase claim, in a `Teardown` captured into the run's
stream: on drop the claim is marked settling, the queue is closed on a
task and the entry process is stopped — `abortSignal` first, then the
kill the `kill_on_drop` guarantees — and only then is the claim
released, so a request landing meanwhile waits and never sees a
settlement arriving late. A run abandoned by its caller leaves the
database as the runtime left it: consistent up to the last committed
write, which is the property Postgres gives and PGlite-as-bytes never
could.

## The vault, exactly

Per run, before the runtime starts: for each secret the agent implies
or names — `OPENAI_API_KEY` always; `EMBEDDING_API_KEY` when
`embedding` is present; `TAVILY_API_KEY` when `web_search` is on; each
static entry of every plugin's `secrets` — one `vault_get`. A key
the vault does not hold refuses the run, naming the key. The values
go into the settings map and the environment and nowhere else. A
rotating entry gets the full cycle: `vault_lock` for 300 seconds
refreshed every 100 on a task, `vault_get`, the setting; after every
turn and at the end the rotated value is read back from where the
entry says and `vault_set`; `vault_unlock` at the end, every key
attempted, the first failure reported.

## Eliza's own vault, on by default

Eliza's vault is not a runtime feature but a library, `@elizaos/vault`,
that plugins import directly — telegram, wallet, browser,
google-workspace, registry, even plugin-sql — and the core runtime has
no hook for it. On a headless host it needs two things, and the
harness gives both every run: a master key derived from
`ELIZA_VAULT_PASSPHRASE` (twelve characters or more, read from the
process environment, with `ELIZA_VAULT_DISABLE_KEYCHAIN=1` so the
keychain is not probed), and a store at `<ELIZA_STATE_DIR>/
.vault-pglite/`. The passphrase is a static secret in the caller's
vault under that key, minted by the harness and set there when
absent, so a lineage never changes it and never has to provision it.
`ELIZA_STATE_DIR` is pinned to a fixed path always; a caller who wants
the store to outlive the container mounts a volume there, and one who
does not gets a store that dies with it. The library recovers a stale
PGlite lock on its own, so a volume that moves between hosts is fine.

Three implications for rotating secrets. The vault is a third place a
plugin may leave a rotated value, which `rotates` cannot read; a store
on a volume keeps such a value across runs inside Eliza, so that
secret is a static seed, and a caller who wants it back in their own
vault needs a `{"vault": entry}` variant, added when a real plugin
asks for it. Re-seeding at the top of Eliza's precedence every run can
hand a plugin its stale seed if the plugin re-reads the setting rather
than trusting its own entry; the caller declares which by declaring
the secret static or rotating. And the store is outside Postgres, so a
snapshot rewind leaves it alone — the property credentials need — at
the cost that a lineage's vault and its database can be rewound
apart.

## The chunk vocabulary, mapped

- Text deltas → `AssistantTextContent`.
- A tool-call envelope → `AssistantToolCall`, the id Eliza's own where
  it has one, minted where it does not (Hermes's rule); a tool-result
  envelope → `ToolResponse`, its content as Eliza reports it. For the
  caller's MCP tools the `diverge` plugin is the one calling the proxy
  and can report the result byte-faithfully, which Hermes could not.
- An evaluation or a context event → a non-fatal notification, in
  Eliza's own words.
- A delivered queue message → `User`.
- `done` → `Usage` when the turn reports it.

The `diverge` plugin registers each of the caller's MCP tools as a
native action, listing them from the proxy at `mcp_url()` once per run
and calling through it; this is the tool channel, and the only plugin
the harness writes.

## The image

`node:24` on Debian slim — plugins like `plugin-browser` and
`plugin-documents` want a real distro, as skills did for Claude Code —
with `bun` installed for the ElizaOS installer's own command, the
harness's Node project with the pinned core plugins and the `diverge`
plugin, and the harness binary as the entrypoint. No proxy, nothing
exposed, nothing of the proxy's touched before a request. Versions
and digests are looked up when the Containerfile is written, never
recalled.

## What a live run has to prove

1. The chunk envelope discriminator in `onStreamChunk` at the pin.
2. `CREATE EXTENSION` for `vector`, `fuzzystrmatch`, `pg_trgm` through
   the proxy's pgwire against the caller's database, and the cost of
   the startup migration on a cold lineage.
3. That every plugin at the pin reads its configuration through
   `getSetting` or `process.env` and nothing else — the assumption the
   declarative settings rest on, and the trigger for revisiting the
   per-plugin script.
4. `bun add --ignore-scripts` of an arbitrary `@elizaos/plugin-*`
   into the harness's project, and that its default export is a
   `Plugin` the runtime accepts.
5. The embedding width probe with the caller's embedding endpoint,
   and the warning when a lineage changes width.
6. Node's startup plus `initialize()` per run, to decide whether the
   entry process should instead be kept alive across runs whose
   agent value hashes the same.
