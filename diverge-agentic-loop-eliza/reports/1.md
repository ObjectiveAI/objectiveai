# Eliza documentation sources — where everything lives

Survey of where Eliza (elizaOS — the TypeScript agent framework, not
the 1966 chatbot) is documented: source repositories, official docs,
API references, papers, and secondary material. Everything below was
reachable and checked on 2026-08-29. Nothing here is a design
decision; this is the map for the research that will produce one.

---

## Primary source code

### The monorepo — `elizaOS/eliza`

<https://github.com/elizaOS/eliza> — MIT, TypeScript, ~19.2k stars,
default branch `main`. "Open source agentic operating system." The
whole platform is one monorepo (Bun + Lerna + Turbo):

- `packages/` — runtime, hosts, UI, CLI, docs, cloud, native code,
  tooling. The load-bearing ones:
  - `@elizaos/core` (`packages/core`) — the runtime core:
    `AgentRuntime` and the plugin contracts. This is the crate-level
    equivalent of what our loop will drive.
  - `@elizaos/agent` (`packages/agent`) — a standalone agent **and
    HTTP backend**; the plugin loader and default plugin map.
  - `@elizaos/app-core` (`packages/app-core`) — the API + dashboard
    host that runs agents.
  - `elizaos` (`packages/elizaos`) — the CLI (`create`, scaffolding,
    deployment).
  - `packages/registry` — the app/plugin catalog as it lives today.
- `plugins/` — first-party model, connector, domain, app, and device
  plugins (90+ official; 200+ counting community).
- `scripts/`, `patches/`, `upstreams/`, `reports/`, `docs/` — repo
  tooling and in-repo notes.
- Root files worth reading before anything else: `README.md`,
  `AGENTS.md`, `CLAUDE.md`, `STATUS.md`, `CONTRIBUTING.md`,
  `WINDOWS.md`.

Caveat for anything read second-hand: descriptions of the package
layout disagree between sources (one summary claims
`packages/typescript|python|rust` language splits; the README on
`main` says `packages/core` etc. as listed above). The tree on `main`
is the authority — the layout has been churning, so re-verify paths
at read time.

Clone shallow-ish for local grepping (their own README's form):

    git clone --filter=blob:none https://github.com/elizaOS/eliza.git

Releases: <https://github.com/elizaOS/eliza/releases>.

### The legacy archive — `elizaOS/eliza-archive`

<https://github.com/elizaOS/eliza-archive> — archive of the v0.x and
v1.x branches, tags, and releases. Most third-party tutorials, the
whitepaper, and a lot of blog material describe THESE versions
(character files / providers / actions / evaluators vocabulary), not
current `main`. When a secondary source contradicts the monorepo,
check whether it is describing the archive's era.

### The docs source — `elizaOS/docs`

<https://github.com/elizaOS/docs> — the source of the official docs
site, Mintlify + MDX, actively maintained. Top-level dirs mirror the
site's nav: `rest-reference/`, `cli-reference/`, `runtime/`,
`guides/`, `plugins/`, `plugin-registry/`, `agents/`, `projects/`,
`launch-resources/`, with `docs.json` as the Mintlify config. Being
plain MDX in a repo, it is greppable — often faster than the site.

### Plugin registries

- <https://github.com/elizaos-plugins> — the ElizaOS Plugins GitHub
  org (per-plugin repos).
- <https://github.com/elizaos-plugins/registry> — the JSON registry
  (`index.json`) publish-a-plugin PRs target.
- <https://github.com/elizaOS/registry> — **archived 2025-05-26,
  read-only**; plugins migrated into the monorepo. Historical only.

## Official documentation site

<https://docs.elizaos.ai/> — the one official docs site. Nav worth
bookmarking:

- Getting started: `/quickstart`, `/installation`,
  `/what-you-can-build`.
- CLI reference: `/cli-reference/overview` (incl.
  `/cli-reference/monorepo`).
- REST API reference: `/api-reference` (also reachable as
  `/rest-reference/...`) — all agent-server endpoints.
- Runtime/architecture: `/runtime/...` (e.g. `/runtime/services`).
- Plugins: `/plugin-registry/overview`, `/plugins/components`,
  `/plugins/reference`, `/guides/create-a-plugin`,
  `/guides/publish-a-plugin`.
- Deployment: `/guides/deploy-to-cloud`.

**For LLM-driven research, the site publishes both**
<https://docs.elizaos.ai/llms.txt> (index of every page — start
here) **and** <https://docs.elizaos.ai/llms-full.txt> (the whole
corpus in one file). This is the cheapest way to sweep the docs.

### The wire surface our loop will care about

The agent server speaks HTTP, and conversations are **Sessions**:

- `GET /agents/{agentId}/sessions` — the agent's active/recent
  sessions.
- `POST /api/messaging/sessions/{sessionId}/messages` — send a
  message into a session (docs page:
  `/api-reference/messaging/send-session-message`).
- Sessions track state/context/history, idle out after inactivity,
  and can be configured to close on timeout — which maps naturally
  onto our continuation-token story, so the Sessions pages deserve
  the first deep read.

Known doc-quality hazards, from the project's own tracker:
[elizaOS/eliza#5370 "REST API Documentation is misleading"](https://github.com/elizaOS/eliza/issues/5370)
and [#3702 "No REST API backend"](https://github.com/elizaOS/eliza/issues/3702).
Treat the REST reference as a claim to verify against
`packages/agent` / `packages/app-core` source, not as ground truth.

1. `llms.txt` → the Sessions + messaging REST pages, and
   `/runtime/...` — the surface a container would drive.
