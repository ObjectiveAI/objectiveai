# What SHOULD go into an Eliza agent

A proposal, not a decision: the shape of the `eliza` agent in the
SDK's vocabulary and of the harness that honors it, derived from
the philosophy the protocol has settled across cc, openrouter and
hermes — and from the legacy ObjectiveAI before them — applied to
what the pinned monorepo actually is (report 2's findings; paths
under `sources/eliza/`). Where report 2 asks, this answers, and says
which answers are firm and which are a recommendation waiting on a
ruling or a live run.

---

## 1. The philosophy, restated as rules

Everything below follows from these, each already written into the
SDK, the spec, or a HARNESS.md:

1. **An agent is the parameters of the call, post-transform.**
   Nothing in the agent rewrites a conversation; what shaped the
   request upstream (personality, prefix messages) is already
   applied; `prompt` is new text only, history lives in the
   continuation (`request/frame.rs`, `agent/mod.rs`).
2. **One variant per upstream, and every field HONORABLE.** A field
   names a mechanism the container actually has — a config key the
   harness writes, a per-request field on the wire it drives — and
   nothing else makes the cut (`hermes/agent.rs`). What cannot be
   told through the upstream's wire is not in the vocabulary.
3. **Auth is an argument.** Inference credentials ride the
   provider structure, tool credentials the toolset structures; the
   filesystem, the mounts and `environment` never carry a
   credential. Rotating state is a RESOURCE: fetched by identity,
   mutated by the run, surfaced back whole (`hermes/provider/mod.rs`,
   `toolsets/mod.rs`).
4. **The container receives nothing of the caller's but the
   request.** Mounts (files, directories, read-only, by identity)
   and `environment` are provisioning; the image is the server's
   choice by agent kind; three loopback ports: the loop, MCP,
   Postgres (spec `container/index.mdx`).
5. **The caller's tools arrive over MCP, and only over MCP.** The
   container is the MCP client, the proxy on 8081 is its one server,
   and the proxy's view of a call is the byte-faithful one
   (`HARNESS.md`, "the stream is not the tool channel"). Built-ins
   are the upstream's own, switched by plain booleans (cc's `Tools`)
   or tri-state/structured toolsets (hermes's `Toolsets`).
6. **The continuation is the upstream's own state as bytes**, never
   held whole in memory, harvested after the process has exited and
   folded to consistency by us, chunk boundaries kept, ingested
   before the process starts, with nothing that regenerates (caches,
   rendered config) inside it (`HARNESS.md`, continuation section).
7. **What nobody drives is off.** Sub-agents whose results wake a
   session off every stream, cron, wake-ups, connectors: a run is
   one caller's conversation, and a turn nobody asked for has no
   stream to land on (hermes: delegation disabled; cc: no cron, no
   plan mode).
8. **Plugins, in the lineage of this project, are containers.** The
   legacy ObjectiveAI plugin is an MCP server built from a
   Containerfile, run as an ephemeral container beside the
   completion, its tools reaching the agent prefixed by the server's
   name (`README.md`, "Plugins"); the first-party ones did X,
   Discord, souls, skills and background tasks THAT way. The Diverge
   protocol kept the MCP half and dropped the viewer half. That is
   the standing answer to "how does a caller extend an agent".

## 2. What an Eliza agent is, in one paragraph

An `eliza` agent is a **character with a model source, an optional
embedding source, and a set of switches over Eliza's own
capabilities**, run by our harness as ONE Eliza runtime in a fresh
container, its tools the caller's MCP servers through the proxy,
its memory the PGlite database that travels as the continuation.
Eliza's plugins are the HARNESS's business — fixed in the image,
selected by the switches — and the caller's extensibility is MCP.
Eliza's connectors, cloud, wallets, device bridges and life-ops are
out: they are other products' concerns, and the protocol has a
channel for each need they served.

---

## 3. The vocabulary — `eliza::Agent`

```text
Agent {
    upstream: Upstream,            // "eliza"
    character: Character,          // §4
    provider: Provider,            // §5 — inference, auth as argument
    embedding: Option<Embedding>,  // §5 — vectors, auth as argument
    reasoning: Option<...>?        // §5 — only if a plugin honors it
    toolsets: Toolsets,            // §6 — Eliza's own capabilities
    memory: Memory?                // §7 — what the run accumulates
}
```

Firm: `upstream`, `character`, `provider`, `toolsets`. Recommended:
`embedding` as an option. Open: whether `memory` switches are the
caller's (§7).

Not in the vocabulary, by rule 2: `plugins` as a list of names
(nothing honors it — `character.plugins` is dead in the host,
`plugin-collector.ts:442` keys off `eliza.json`, and a name the
image lacks resolves to nothing), `templates` (unhonored where it
matters, `services/message.ts:61`), model tiers as a ladder (§5),
connectors (§6), the vault (§8), `conversationLength` (an Eliza
internal the caller has no standing to tune — recommendation).

## 4. The character — a parameter, not a transform

Report 2 B1 is the one place the "post-transform" rule meets a
harness that will not take a finished prompt. The ruling this
proposal takes: **the character is a parameter of the call**, on
the same footing as hermes's `system_prompt`, because it is applied
by the upstream PER REQUEST from its own fields and there is no
representation of "already applied" that Eliza would accept. What
the rule forbids is the AGENT rewriting a conversation; the
character rewrites nothing, it is how Eliza speaks. A caller who
authored a personality upstream renders it INTO these fields.

Fields, each honorable (all rendered by the CHARACTER provider or
the canonical system prompt every turn — `providers/character.ts:
88-247`, `runtime/system-prompt.ts:40-100`):

- `name: String` — required by us. It is the identity's seed and
  the prompt's `{{agentName}}`; Eliza's minimum too
  (`character.ts:173-177`).
- `system: Option<String>` — the system prompt head; absent gives
  Eliza's own "You are {{name}}, an autonomous AI agent powered by
  elizaOS" (`prompts/src/index.ts:217`).
- `bio: Vec<String>`, `topics: Vec<String>`,
  `adjectives: Vec<String>`, `style: Style{all, chat, post}`,
  `message_examples: Vec<Vec<Example{name, text}>>` — the prompt
  ingredients Eliza samples deterministically. `post_examples` too,
  though it renders only in FEED/THREAD rooms
  (`providers/character.ts:151-166`), which a DM-driven loop never
  is; recommendation: leave it OUT until a room type other than DM
  is a thing here.
- `username` — mention detection only (`services/message.ts:
  15702`); OUT: the loop's DM room always responds.
- `knowledge`/`documents` — NOT here. Knowledge is files, files are
  MOUNTS (rule 4); the harness points `DOCUMENTS_PATH` at the mount
  root and `LOAD_DOCS_ON_STARTUP` at the switch (§6). Content-hash
  dedupe (`features/documents/utils.ts:268-305`) makes re-mounting
  each run free (report 2 G7 to confirm).
- `settings`/`secrets` — NOT here. Every setting the harness needs
  is rendered from the typed structures; a free map would be the
  "environment carries credentials" hole rule 3 closes.

**Identity is pinned by the harness, not by the name** (report 2
B3). The harness writes `character.id` as a constant UUID it derives
once per lineage and stores IN the continuation (a tiny sidecar
file, or the `agents` row itself since `character.id` wins over the
name in `runtime.ts:1584-1585`). A fresh start mints it; a resume
reads it. Then a caller renaming the character between turns keeps
its memory, which is what "the continuation is the memory" means.
The room id and the caller's entity id are derived from fixed
external ids (`createUniqueUuid(runtime, "diverge")`,
`entities.ts:763-773`), so the conversation is one room across the
lineage and the RECENT_MESSAGES provider sees all of it.

## 5. Models — one provider structure, tiers collapsed

**The provider is `plugin-openai` pointed at an OpenAI-compatible
base URL, or nothing else** — recommendation, with the reason:
every other in-tree provider plugin is either wire-specific with no
base URL (anthropic, google-genai, zerollama), text-only (zai), or
not a network provider (cli-inference, local-inference, elizacloud).
The Diverge relay and every upstream this protocol routes speak
OpenAI-compatible; `plugin-openai` is the one path the monorepo's
own docs name for "OpenRouter, Cerebras, local servers"
(`plugins/plugin-openai/CLAUDE.md`), and it is the only provider
that registers embeddings, tokenizer, planner and response-handler
tiers in one place (`plugin-openai/src/index.ts:202-277`).

So `Provider` is ONE structure, not thirty-six (report 2 C1):

```text
Provider {
    base_url: String,   // OPENAI_BASE_URL
    api_key: String,    // OPENAI_API_KEY (any non-empty; missing only warns)
    model: String,      // every text tier, see below
}
```

Applied as process env (`plugin-openai/src/utils/config.ts:168,
222, 245`) and as the plugin's auto-enable key (`provider-plugin-
map.json:14` — `OPENAI_API_KEY` present ⇒ plugin-openai loads).
Should hermes-style per-provider structures be wanted later
(anthropic direct, google direct), they are additive variants of
`Provider`; nothing here forecloses them, and each would be
honorable through its own plugin's env vars.

**Tiers collapse to `model`** (report 2 C2). The harness sets
`OPENAI_NANO/SMALL/MEDIUM/LARGE/MEGA_MODEL` all to `model`, so
`RESPONSE_HANDLER`, `ACTION_PLANNER`, the reasoning tiers and the
reply generator (`TEXT_LARGE`) all resolve to the one model the
caller named, and the fallback chains (`model.ts:169-181`) never
surprise. Firm as the first cut. A `small`/`large` pair is the one
refinement worth considering later — Eliza spends its Stage-1
envelope, planner and post-turn evaluators on the small tier by
design, and a caller paying per token may want that. Not now.

**Embeddings are a second, optional structure** (report 2 C3):

```text
Embedding {
    base_url: String,   // EMBEDDING_BASE_URL (plugin-embeddings)
    api_key: String,    // EMBEDDING_API_KEY
    model: String,      // EMBEDDING_MODEL
    dimensions: u32,    // EMBEDDING_DIMENSIONS
}
```

Through `plugin-embeddings` (`plugin-embeddings/src/utils/config.ts:
96-127`), which auto-enables on its URL and deliberately does not
fall back to `OPENAI_*` — so the two sources are independent facts,
as they should be. Absent ⇒ the harness sets
`ELIZA_DISABLE_LOCAL_EMBEDDINGS=1` and no embedding provider: Eliza
boots, stores memories without vectors, and searches by keyword
(`runtime.ts:3299-3305, 11473-11488`). That degraded mode is HONEST
— the caller who wants semantic memory says so and pays for it. The
on-device embedder (`plugin-local-inference`) is OUT: it needs an
engine the image does not stage (report 2 C3), and a model the
caller did not choose would be embedding their memory.

`dimensions` is the width the continuation was built on; the
harness records it in the sidecar (§8) and, on mismatch, lets Eliza
re-embed (`runtime.ts:11162-11185`) rather than refuse — the caller
changed the model, the cost is theirs, and the memory survives.
Recommendation; report 2 C4 can go either way.

**Reasoning**: no field. `plugin-openai` has no effort knob in this
pin that reaches the wire (it is a `TEXT_*` tier map); the
Anthropic plugin's effort/CoT knobs are that plugin's. When a
provider variant that honors one exists, it gets the field.

## 6. Toolsets — Eliza's plugins, one switch each; MCP always

This is the plugins ruling, in three parts.

**(a) The caller's tools are MCP, always on, never a switch.** The
proxy is Eliza's one MCP server: `settings.mcp.servers.diverge =
{type:"streamable-http", url:"http://127.0.0.1:8081/mcp"}`
(`plugin-mcp/src/types.ts:46-66`), rendered by the harness. Two
things stand between that sentence and a working tool channel, and
BOTH are candidates for a small Diverge plugin of our own rather
than for waiting on upstream:

- the URL guard that rejects private IPs (`security/
  mcp-server-config.ts:23-291`) — if it rejects loopback (report 2
  D5, a live check), the stock plugin cannot reach the proxy;
- the generic `MCP` action's two extra LLM passes to pick the tool
  and fill its arguments (`plugin-mcp/src/actions/mcp.ts`,
  `utils/selection.ts:36-78`) — which makes every tool call cost
  two sub-prompts and hides the arguments the model "chose" behind
  a second model call.

The alternative is honest and small: a `diverge` plugin (a file in
the image, ~a few hundred lines) that lists the proxy's tools at
init and registers EACH as a native Eliza action with the tool's
schema as its parameters — so the planner names it directly, the
arguments come from the planner's own tool call, and the action's
handler is one MCP `call_tool` through the proxy. Resources ride
the same plugin (`list_resources`/`read_resource` as a provider or
two actions). This is not "extending Eliza with a plugin the caller
wrote"; it is the harness's adapter, the way the hermes harness
writes `config.yaml`. Recommendation: build it; keep plugin-mcp as
the fallback if the live run shows the stock action is good enough.

**(b) Eliza's own capabilities are booleans, per plugin.** The cc
precedent, at the grain Eliza itself switches things (`eliza.json`
`plugins.allow` / `plugins.entries[id].enabled`, `plugin-collector.
ts:686-700, 846-870`; `ELIZA_SKIP_PLUGINS` for the always-loaded
core). Every switch names a plugin the image carries and the
harness lists or skips:

```text
Toolsets {
    coding_tools: bool,   // plugin-coding-tools: file/shell in the workspace
    pty: bool,            // plugin-pty: terminals
    browser: bool,        // plugin-browser (puppeteer-core; needs chromium in image)
    web_search: bool,     // plugin-web-search — needs a key? see below
    documents: bool,      // plugin-documents + LOAD_DOCS_ON_STARTUP over the mount
    pdf: bool,            // plugin-pdf: ingestion of mounted PDFs
    notes: bool,          // plugin-notes
    scheduling: bool,     // plugin-scheduling: tasks WITHIN a turn; see §7
    computeruse: bool,    // plugin-computeruse — probably never (no display)
    vision: bool,         // plugin-vision (sharp): image description
    generate_media: bool, // the GENERATE_MEDIA built-in action (needs an image tier)
}
```

Which of those carry a credential becomes a STRUCTURE, not a
boolean, exactly as hermes's `web`, `tts`, `image_gen` did: if
`plugin-web-search` needs a search backend's key, `web_search:
Option<WebSearch{ provider, api_key }>`. The plugin inventory report
did not read each tool plugin's config; the toolset structures are
the next research pass, one file per plugin that takes anything.

Always on, no switch: `plugin-sql` (required, `core-plugins.ts:24-
27`), basic-capabilities (unconditional, `runtime.ts:2977-3013`:
REPLY, IGNORE, NONE, CHOOSE_OPTION, ATTACHMENT, CALCULATE,
CHANNEL_RECAP, SEARCH_CHANNEL_TOPICS, and the 21 providers),
`plugin-agent-skills` (skills are mounts — see below), the `diverge`
MCP adapter.

Always off, no switch — and the reasons, so nobody re-opens them
without a new fact:

- **Connectors** (discord, telegram, x, slack, whatsapp, wechat,
  matrix, imessage, instagram, google-workspace): a second inbound
  channel the queue does not see, and a turn nobody drives (rule
  7). A caller who wants an agent on X runs an X MCP server — the
  legacy `psychological-operations` shape — and the agent posts by
  tool call, on the stream.
- **Cloud and host** (elizacloud, cloud-apps, app-control,
  app-manager, registry, native-filesystem's host paths, the ~35
  `plugin-native-*` bridges, capacitor, omarchy, companion): another
  product's plumbing.
- **Wallets** (wallet, taskmarket): keys in a vault under a
  passphrase, ERC-6551 accounts, chain RPCs — credentials by rule 3
  are arguments, and a private key as a plain argument in a request
  is a design nobody should ship without a resource story (a
  rotating wallet is not rotating; a wallet is a secret). OUT until
  someone asks with a threat model.
- **Life-ops** (personal-assistant, goals, todos, inbox, reminders,
  health, finances, blocker, feed): tied to connectors, proactivity
  and the host UI.
- **Sub-agents and orchestration** (agent-orchestrator, workflow):
  the delegation objection — background children outliving the
  run. cc's `Task` is on because its sub-agents' chunks are
  attributed on the SAME stream; Eliza's orchestrator has no such
  attribution found. Off until it does.
- **Local inference** (local-inference, native-inference,
  native-llama, cli-inference): the caller names a model source;
  the container does not run one.
- **Trajectory logger**, **form**, **video**, **fish-audio**,
  **local-storage**, **inmemorydb**: diagnostics or alternatives to
  what the harness already decides.

**(c) Third-party plugins: no.** Not from npm at start (no such
path exists, and it would be a supply-chain hole with a network
dependency, report 2 D2); not as drop-in mounts under
`plugins/custom/` (unreviewed code in the agent's process, with the
caller's tool channel in reach and no isolation in this pin,
`types/plugin.ts:1160-1174`). The lineage's answer stands: a plugin
is a container the caller runs, and its tools arrive over MCP. If a
specific upstream plugin ever earns a switch, it earns it by being
put in the IMAGE and named in `Toolsets` — the harness's decision,
reviewed, pinned.

**Skills** are mounts, as for hermes and cc: the harness names the
mount root to `plugin-agent-skills` and the switch is "something is
mounted there". Where that root is, is a research item (report 2
G6).

## 7. What a run does, and does not, on its own

Settled by rule 7, rendered as fixed env/config by the harness:

- **Always respond.** `checkShouldRespond: false` / the DM room's
  fast path: the caller's turn is never IGNOREd or STOPped
  (`services/message.ts:15665-15770`; `runtime.ts:3788-3806`). A
  loop that may decline to answer has no place for the refusal to
  land except an empty stream.
- **Proactivity off** (`ELIZA_DISABLE_PROACTIVE_AGENT=1`,
  `ELIZA_PROACTIVE_INTERACTIONS=off`). **Autonomy off**
  (`enableAutonomy: false`). No cron-like tasks that fire after the
  turn (`plugin-scheduling` within a turn is fine; anything that
  outlives the run is not — the `scheduling` switch in §6 needs its
  semantics read before it is offered).
- **Memory accumulation is the caller's to switch** — the
  recommendation for report 2 D9. Facts extraction, reflection
  evaluators, long-term memory and advanced planning each cost
  extra model calls per turn and each grow the continuation; they
  are ALSO what makes an Eliza agent an Eliza agent. So a small
  structure, all booleans, non-optional (the cc precedent):

```text
Memory {
    facts: bool,             // runFactsAndRelationshipsStage + reflection evaluators
    long_term: bool,         // advancedMemory: the long_term_memories table
    relationships: bool,     // enableRelationships
    advanced_planning: bool, // advancedPlanning / actionPlanning
}
```

  Naming and grain are open; the point is that these are honorable
  (constructor options and character flags, `runtime.ts:1465-1528,
  1570-1579`) and consequential.

- **Trust, secrets manager, plugin manager, trajectories**: off,
  fixed. The harness is the trust boundary, auth is an argument,
  plugins are the image's, and trajectories are diagnostics that
  would bloat the continuation.

## 8. The continuation

**Contents** (report 2 F1): the PGlite directory whole, minus its
two lock artifacts; a `diverge.json` sidecar the harness owns
(`character.id`, the embedding width the vectors were built on, the
room id); `media/` if the ATTACHMENT action ever writes it. Nothing
else — no `eliza.json` (rendered from the request every run, the
hermes rule), no `secret-salt` (see below), no caches
(`models/`, `tool-cache/`, `plugins/.runtime-imports/`), no
trajectories, no vault (nothing writes it once wallets and
connectors are out), no `auth/`/`credentials/` (auth is an
argument).

**No secrets in the row.** The harness keeps every credential in
PROCESS ENV and out of `character.secrets`, so nothing in the
`agents` row is encrypted and `SECRET_SALT` need not travel; the
harness sets a throwaway salt per run to satisfy the production
check (`settings.ts:134-150`). The host's allowlist copy of env
keys into `character.secrets` (`build-character-config.ts:100-183`)
is a HOST behavior — one more reason the entry point is ours (§9).
If a live run shows the row still carries ciphertext, the salt
joins the sidecar. Report 2 F4.

**Harvest and ingest**, the hermes rules transposed:

- Ingest before the process starts; strip `eliza-pglite.lock` and
  `postmaster.pid` if present (their absence is the clean state;
  the host removes `postmaster.pid` itself, `eliza.ts:2839-2851`);
  police nothing else.
- Harvest after a NON-fast `runtime.stop()` and `adapter.close()`
  have completed (report 2 G5): the post-turn work — facts,
  reflection, the embedding queue — is the lineage, and fast mode
  cuts it. Then walk the directory and stream each file in ≤2 MiB
  pieces, one alive at a time.
- Whether PGlite needs a fold of its own (a WAL equivalent) is
  unknown from source (the package is not vendored); the live run
  answers it, and the sidecar can carry a "harvested clean" mark.
- Never enable the retention sweepers (`logs-retention-service.ts`,
  `memory-retention-service.ts`) in what the harness renders; the
  `logs` table is diagnostic and may be truncated at harvest —
  recommendation.

**Encoding** (report 2 F3): a directory is many files, so each
chunk leads with a header naming its path — tag byte `0` for "a
file of the PGlite tree" + u16 path length + path, `1` for the
sidecar, `2` for `media/` files — and the ingest appends to the
named file. Same grammar as hermes's tag byte, extended by a path;
the SDK's rule that chunk boundaries are kept is untouched. This
crate's business, not the SDK's.

**The fetch answers nothing but the bytes.** With the identity in
the sidecar there is no session tip to compute (report 2 F7); the
room is derived and constant.

## 9. The harness — our entry, the library, one stream

Report 2 A1/E2, answered: **drive `@elizaos/core` from an entry
script of our own, not `@elizaos/agent`'s server.** Reasons, in
order of weight:

1. The host's eleven always-on plugins include five we rule off
   (app-control, cloud-apps, native-filesystem, browser,
   coding-tools) and a workspace resolver, wizard, proactivity and
   plugin manager we would spend env vars disabling.
2. The in-process firehose is the complete one: `handleMessage`'s
   `onStreamChunk` carries text deltas interleaved with
   `tool_call`/`tool_result`/`evaluation` JSON (`services/message.ts:
   13930-13963`); pipeline hooks see every model call's prompt and
   result and every persisted memory (`types/pipeline-hooks.ts:
   80-241`); `RUN_ENDED` is exactly once per message. The host's
   SSE gives tool frames and tokens but thought only on `done` and
   no model-call boundaries (report 2 E1).
3. The `diverge` adapter plugin (§6a) and the secrets-out-of-the-row
   rule (§8) both need the runtime constructed by us:
   `new AgentRuntime({character, plugins: [sql, openai, embeddings?,
   diverge, ...switched], settings, checkShouldRespond: false,
   enableAutonomy: false, ...})` then `initialize()`, `ensureConnection
   ({entityId, roomId, source:"diverge", type: DM})`, then per turn
   `handleMessage(runtime, memory, callback, {onStreamChunk})`
   (`runtime.ts:1465-1530, 2927, 4763-4776`; `message.ts:13427`).
   The worked example is `packages/examples/code/src/lib/agent.ts:
   88-153`.

The shape, then, mirrors hermes with the gateway replaced by a Node
program we ship in the image (`/opt/diverge/eliza.mjs`, a few
hundred lines, pinned with the image):

- The Rust harness is the socket (`main.rs`, unchanged in role),
  the fetcher, the stores, `filesystem::prepare` (renders
  `character.json`, the runtime options JSON, the process env —
  `OPENAI_*`, `EMBEDDING_*`, `PGLITE_DATA_DIR`, `ELIZA_STATE_DIR`,
  `LOG_LEVEL=error`, `NODE_ENV=production`, a per-run `SECRET_SALT`)
  and `filesystem::finish` (the harvest).
- The Node entry reads that JSON, builds the runtime, and speaks
  one line-delimited JSON protocol on stdio (or a loopback socket,
  the hermes `/v1/runs` analogue): `{turn: prompt}` in;
  `{text_delta}`, `{tool_call: {id, name, arguments}}`,
  `{tool_result: {id, content, is_error}}`, `{thought}`, `{usage}`,
  `{done}` out — each mapped to the chunk vocabulary by the Rust
  side (`assistant_text`, `assistant_reasoning`, `assistant_tool_call`,
  `tool_response`, `usage`). Tool responses for MCP calls are
  emitted from the PROXY's view when the byte-faithful relay exists
  (the hermes rule); until then from the adapter plugin's own
  result, which for a native action IS the bytes the proxy returned.
- The queue is the proxy's, unchanged: a pending prompt folds onto
  the next tool response at its head; one that outlives the turn is
  the next turn's prompt. Eliza's supersede semantics are not used
  — the harness serializes turns itself (one `handleMessage` at a
  time, `keepExistingResponses` moot).
- Provisional text (report 2 E3): emitted as it comes. A
  replacement is another `assistant_text` chunk; the stream is a
  record of what the agent said, and Eliza said both.
- Stop: SIGTERM to the Node process → `runtime.stop()` non-fast →
  `adapter.close()` → exit; then harvest.

The fallback if the entry-script route is ruled out is the host's
`POST /api/conversations/:id/messages/stream` over loopback with no
token (`conversation-routes.ts:4058`; `loopback-trust.ts:445-487`),
which report 2 E1 documents in full; it loses model-call boundaries
and needs `ELIZA_SKIP_PLUGINS` for everything §6 rules off.

## 10. The image

`FROM ghcr.io/elizaos/eliza:stable@sha256:…` pinned by digest to the
image built from the pinned source (the hermes pattern): Debian
`node:24-slim`, the workspace's `npm install --omit=dev` closure,
`bun` and `tsx` present, ffmpeg/libopus/yt-dlp/tailscale we ignore
(`packages/app-core/deploy/Dockerfile.ci:59-215`). We add our two
musl-static binaries (the loop, the proxy — they run fine on glibc
Debian, as in the hermes image), the Node entry, the `diverge`
plugin, and an entrypoint that starts nothing of the host's
(`ELIZA_DISABLE_DIRECT_RUN` and the rest are moot when our entry is
the only process). The current Alpine Containerfile is replaced.
Unknown until built: whether the image's node_modules closure
