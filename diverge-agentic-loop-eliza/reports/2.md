# Eliza — the questions, after the first investigation

What the first read of the pinned monorepo (`sources/eliza`, commit
`90bb56ea`, 2026-08-30; root `package.json` 2.0.4, `packages/core`
2.0.3-beta.7) leaves OPEN about what an Eliza agent should be in
this protocol. Report 1 was the map; this is the list of things the
map did not settle. Every question states what was established and
why that is not yet an answer. Report 3 proposes answers; the
questions stand until a decision or a live run closes them.

Paths are under `sources/eliza/` unless said otherwise. The docs
corpus (`sources/llms-full.txt`, seven months older) is cited only
where it contradicts the tree, which is nearly everywhere the wire
is concerned: `elizaos start`, `character.plugins`,
`plugin-bootstrap`, `/api/messaging/sessions`, socket.io,
`ELIZA_SERVER_AUTH_TOKEN` — none exist in this pin.

---

## A. What IS the product we are wrapping?

**A1. Library or host?** Two very different things carry the name.
`@elizaos/core` is a runtime library (`AgentRuntime`, the plugin
contract, the message service — `packages/core/src/runtime.ts`,
`services/message.ts`). `@elizaos/agent` is a HOST around it
(`eliza-autonomous serve`, `packages/agent/src/cli/index.ts:69-79`)
that always loads eleven "core" plugins — sql, local-inference,
app-control, cloud-apps, native-filesystem, coding-tools,
agent-skills, commands, browser, scheduling, documents
(`packages/agent/src/runtime/core-plugins.ts:269-281`) — and speaks
a 200-module HTTP surface. cc and hermes both wrap the upstream's
OWN gateway. Here the upstream's gateway is a product host with
opinions (a workspace resolver, a first-run wizard, proactive
interactions, a plugin manager, cloud provisioning). Which do we
drive: the host over loopback HTTP, or the library from an entry
script of our own?

**A2. Is `elizaos` (the CLI package) anything to us?** It is
`create/upgrade/info/plugins submit/deploy/capability-router/
migrate-agent` (`packages/elizaos/src/cli.ts:66-150`). `deploy`
targets Eliza Cloud. Nothing there starts an agent. Presumed: no.

**A3. Which version is the pin?** The monorepo disagrees with
itself (2.0.4 vs 2.0.3-beta.7). The npm-published `@elizaos/agent`
is 2.0.3-beta.7; the GHCR image `ghcr.io/elizaos/eliza:stable` is
built from main (`.github/workflows/build-agent-image.yml:34-36,
293-301`). If we `FROM` that image (the hermes pattern), the pin is
a digest and the version question is moot; if we `npm install`, it
is a beta on a moving main. Which?

## B. The character — is it "post-transform"?

The protocol rule: an agent as authored carries a system prompt,
prefix and suffix messages, a personality, and those are applied
BEFORE a provider sees the request; `prompt` is the result, not the
ingredients (`diverge-provider-sdk/.../request/frame.rs`,
`agent/mod.rs`).

**B1. Eliza's character IS the prompt-rendering mechanism.** `name`,
`system`, `bio`, `topics`, `adjectives`, `style`, `messageExamples`,
`postExamples` are re-rendered by the runtime EVERY turn — the
CHARACTER provider samples bio lines, one topic, one adjective, five
example groups deterministically (`packages/core/src/features/
basic-capabilities/providers/character.ts:88-215`), and the canonical
system prompt is assembled from `system` + `bio` + `style`
(`packages/core/src/runtime/system-prompt.ts:40-100`). There is no
way to hand Eliza a finished prompt: the prompt is Eliza's to build
from the character, around twenty-one providers' output
(`basic-capabilities/index.ts:1424-1446`). So is the character a
parameter of the call (like hermes's `system_prompt`, which is
"applied per request") — or is it the "personality" the rule says
was applied upstream and must not be here? If it is a parameter,
which fields: only `system`? `system` + `bio` + `style`? All of
them?

**B2. Templates are NOT overridable where the docs say they are.**
`messageHandlerTemplate` is imported directly
(`services/message.ts:61, 5519`) and the runtime states prompt-shaped
keys are ignored (`contracts/first-run-options.ts:37-40`). Only
`replyTemplate`, `postCreationTemplate` and eight failure-reply
strings are read from `character.templates`
(`features/basic-capabilities/actions/reply.ts:358`;
`services/message.ts:16493-16608`). Should `templates` be in the
vocabulary at all, or is the honest answer "no — Eliza's prompts are
Eliza's"?

**B3. Identity.** `agentId = character.id ?? stringToUuid(name)`
(`runtime.ts:1584-1585`; SHA-1, unsalted, `utils.ts:1120-1140`), and
every room/entity/world id is derived from it. A continuation is
recognized by the next run ONLY if the agentId is the same — so a
caller renaming the character between turns orphans the whole
database. Do we pin `character.id` ourselves (one constant per
lineage, written by the harness), or accept that the name is the
identity and document it?

**B4. Every field is optional, even `name`** (`types/agent.ts:67-88`;
`createCharacter` alone demands it, `character.ts:173-177`; the host
substitutes "Unnamed Character"). What is our minimum?

## C. Models — the provider structure

**C1. Which provider plugins are candidates?** In the tree: openai
(OpenAI-compatible `OPENAI_BASE_URL`, plus a separate
`OPENAI_EMBEDDING_URL`), anthropic (Anthropic wire only, NO
embeddings), google-genai (no base URL), zerollama (Ollama wire),
zai (OpenAI-compatible, text only), embeddings (BYO OpenAI-compatible
`/embeddings` only), cli-inference (subscription CLIs), elizacloud,
local-inference (on-device). NOT in the tree despite the docs:
openrouter, ollama, local-ai (`plugins/` inventory;
`first-run-options.ts:419-425` names openrouter only as an npm
specifier). Is the vocabulary "one structure per plugin" (hermes
style, 36 providers), or "one OpenAI-compatible structure" because
`plugin-openai` + a base URL reaches everything we route (the
Diverge relay speaks OpenAI-compatible)?

**C2. Tiers, not a model.** Eliza does not take "the model". It
takes a ladder — `TEXT_NANO/SMALL/MEDIUM/LARGE/MEGA`,
`RESPONSE_HANDLER`, `ACTION_PLANNER`, `TEXT_EMBEDDING`, reasoning
tiers, image, transcription, TTS (`types/model.ts:59-108`) — and each
provider plugin maps env vars to tiers (`OPENAI_{NANO,SMALL,MEDIUM,
LARGE,MEGA}_MODEL`, `plugin-openai/src/utils/config.ts:325, 355`).
Fallback chains collapse missing tiers (`RESPONSE_HANDLER → NANO →
SMALL`, `ACTION_PLANNER → MEDIUM → SMALL`, `model.ts:169-181`), and
`LLM_MODE=SMALL|LARGE` forces one (`runtime.ts:6920-6940`). Does our
agent carry ONE model and the harness sets every tier to it? Two
(small/large)? The whole ladder? Per-action routing exists too
(`useModel`, `runtime.ts:6860`).

**C3. Embeddings are a second provider.** Anthropic has none; the
host forces `EMBEDDING_PROVIDER=local` so plugin-local-inference's
on-device embedder wins (`packages/agent/src/runtime/eliza.ts:
1040-1078`) — which needs a "fused libelizainference" engine that only
source checkouts stage; the CI image boots with
`ELIZA_DISABLE_LOCAL_EMBEDDINGS=1`. Without any `TEXT_EMBEDDING`
handler, boot continues, memories are stored WITHOUT vectors, and
documents fall back to keyword search (`runtime.ts:3299-3305,
11473-11488`; `features/documents/service.ts:1970-1975`). Do we
require an embedding source (a second auth-as-argument structure,
OpenAI-compatible `/embeddings`), make it optional (degraded memory
when absent), or forbid it (no vectors, ever)?

**C4. Embedding dimension is stateful.** The `embeddings` table has
seven fixed vector columns, one active (`plugin-sql/src/schema/
embedding.ts:36-61`); a model change between runs switches the
column, deletes stale rows and re-embeds in the background
(`runtime.ts:11162-11185`). A continuation therefore carries an
implicit dependency on the embedding model's width. Do we record it
and refuse a mismatch, or let Eliza re-embed at the caller's cost?

**C5. Model defaults in the pin** are `gpt-5.6-luna` / `gpt-5.6-sol`
/ `text-embedding-3-small` (`plugin-openai/src/utils/config.ts`).
Irrelevant once every tier is set, but only if we set every tier.

**C6. `MODEL_USED` is emitted only by provider plugins**, never by
core (`types/events.ts:302-331`). Which plugins emit it, and with
usage? The `done` SSE frame carries `usage`
(`conversation-routes.ts:2143`); the JSON twin omits it. Where does
our `usage` chunk come from?

## D. Plugins — the big one

Eliza's plugin is arbitrary JavaScript `import()`ed into the agent
process with full privilege — "Trusted, full agent privilege, shared
crash domain … the default for every existing plugin"
(`packages/core/src/types/plugin.ts:1160-1174`). No permissions, no
signatures, shape-only validation (`plugin.ts:45, 65`). The remote/
isolated plugin model is declared and unimplemented
(`installRemotePlugin` always throws, `runtime.ts:13600-13607`).

**D1. Which of the seven kinds does a Diverge Eliza agent get?**
The 114 real plugins group as: model providers; database (sql,
inmemorydb); the always-loaded functional core (agent-skills,
commands, scheduling, documents, app-control, native-filesystem,
coding-tools, browser); connectors (discord, telegram, x, slack,
whatsapp, wechat, matrix, imessage, instagram, google-workspace);
knowledge (documents, pdf, notes, relationships, web-search); tools
(mcp, coding-tools, agent-orchestrator, pty, computeruse, browser,
workflow, github, linear, notion, dropbox, spotify, doordash, maps,
calendar, meetings); wallets (wallet, taskmarket); life-ops
(personal-assistant, goals, todos, inbox, reminders, health,
finances, blocker, feed); ~35 `plugin-native-*` device bridges;
meta (registry, app-manager, cloud-apps, trajectory-logger, form,
vision, video, fish-audio, local-storage). Each kind needs a ruling.

**D2. Are third-party plugins in scope at all?** There is no install
at start (`plugin-installer.ts:903-911` is the explicit installer,
which then requests a restart). A plugin the caller wants would have
to be (a) in the image, (b) mounted as a drop-in under
`<stateDir>/plugins/custom/` or `plugins.load.paths`
(`plugin-resolver.ts:2528`), or (c) installed by the harness from
npm at container start. (c) is a supply-chain hole with a network
dependency; (b) means "a plugin is a mount", which fits the protocol
(skills are mounts) but runs unreviewed code in the agent's process
with the caller's MCP tools reachable. In the legacy ObjectiveAI a
plugin is a CONTAINER — an MCP server built from a Containerfile,
run beside the completion (`README.md`, "Plugins") — and the Diverge
protocol keeps only the MCP half of that. Does an Eliza plugin have
any standing beside "the caller's tools arrive over MCP", or is the
answer that Eliza plugins are the harness's business (fixed in the
image) and the caller's extensibility is MCP, full stop?

**D3. Connectors: never?** Discord/Telegram/X/Slack are how Eliza
usually meets the world. In this protocol the loop meets the world
through the request and the tool channel, and the legacy first-party
plugin `psychological-operations` did X and Discord as MCP servers.
A connector inside the container would also be a second inbound
channel the caller's queue does not see. Presumed: never — but the
`x` plugin's timelines and the `discord` plugin's presence are what
some callers will want from "an Eliza agent". Is that a caller's MCP
server's job?

**D4. Wallets.** `plugin-wallet` (EVM+Solana, ERC-6551) keys live in
the vault as `agent.<agentId>.wallet.<chain>`
(`runtime/agent-wallets.ts:44-49`), vault = a second PGlite DB under
`ELIZA_VAULT_PASSPHRASE` (`packages/vault/src/pglite-vault.ts:
790-798`). Is a wallet a RESOURCE (caller-held state the run mutates,
the hermes OAuth pattern), an argument (a private key — plain
value), or out of scope?

**D5. The MCP plugin and the proxy.** `plugin-mcp` reads `settings.
mcp.servers` (`plugin-mcp/src/types.ts:46-66`) — HTTP servers are
`{type:"http"|"streamable-http"|"sse", url}` with NO headers/auth
field, and its URL guard REJECTS PRIVATE IPs (`packages/core/src/
security/mcp-server-config.ts:23-291`; SSRF-guarded fetch,
`service.ts:65-72`). Our proxy is `http://127.0.0.1:8081/mcp`. Does
the guard reject loopback? If so the stock plugin cannot reach the
tool channel and we need either a config escape (none found: the
`ELIZA_ALLOW_UNAUTHENTICATED_STDIO_MCP` switch is for stdio writes
over the API, `server-helpers-mcp.ts:60-83`) or our own plugin.

**D6. How MCP tools reach the model.** Not as native tools. One
generic `MCP` action (`plugin-mcp/src/actions/mcp.ts:42, 447-469`)
whose handler runs TWO extra LLM passes — pick a tool, then fill its
arguments against the schema (`utils/selection.ts:36-78`) — unless
the planner already named `serverName`+`toolName`. So a tool call is
an Eliza ACTION whose inside is an MCP call; the arguments the model
"chose" are produced by a sub-prompt, and the tool's result comes
back into the action's `ActionResult`. What is our `tool_call`
chunk: the Eliza action (`MCP`, with the planner's parameters) or the
inner MCP call (name + arguments as sent to the proxy)? The proxy's
view is byte-faithful for the latter (the hermes rule); the
in-process streaming hooks carry both (`types/streaming.ts:28-61`).

**D7. Resources and prompts.** plugin-mcp lists and reads resources
(`service.ts:592-657`, MCP provider `provider.ts:30-61`); it never
touches prompts. Fine for our five channels (no prompts channel) —
but confirm `list_resources`/`read_resource` route through the
proxy's relay the way tools do.

**D8. Actions ARE tools.** Eliza's own vocabulary — REPLY, IGNORE,
NONE, CHOOSE_OPTION, GENERATE_MEDIA, ATTACHMENT, SEARCH_CHANNEL_
TOPICS, CALCULATE, CHANNEL_RECAP (`basic-capabilities/index.ts:
1451-1461`) plus whatever coding-tools, browser, pty, web-search,
documents register — are built-ins with no switch of their own; the
cc precedent is a boolean per built-in. Do Eliza's built-ins get the
same treatment (a `tools`/`toolsets` structure of booleans per plugin
or per action), and at which grain: per PLUGIN (coding_tools:
bool) or per ACTION (the plugin registers several)?
`disableBasicCapabilities` empties the core arrays but the plugin
stays registered (`runtime.ts:1483-1488`).

**D9. Evaluators and the advanced features.** Reflection
(`factMemory`/`relationships`/`identities`/`success`), long-term
memory, advanced planning, autonomy, trust, secrets manager, plugin
manager, trajectories are constructor switches (`runtime.ts:
1465-1528`: `advancedCapabilities, actionPlanning, enableAutonomy,
enableTrust, enableSecretsManager, enablePluginManager,
enableDocuments, enableRelationships, enableTrajectories`) and
character flags (`advancedPlanning`, `advancedMemory`). They shape
what the continuation accumulates (facts, long_term_memories) and
how many model calls a turn costs. Which are the caller's switches
and which are fixed?

**D10. `shouldRespond`, proactivity, autonomy.** Eliza may decide
NOT to reply (IGNORE/STOP, `services/message.ts:15665-15770`);
`checkShouldRespond:false` forces a reply, and `DM` rooms are the
fast path. The host also runs PROACTIVE interactions by default
(`ELIZA_PROACTIVE_INTERACTIONS=subtle`) and can run an autonomy loop
(`features/autonomy/service.ts:873`) — turns nobody asked for, off
every stream the run has (the hermes delegation objection). Presumed:
always respond, proactivity off, autonomy off — confirm each is a
hard switch.

## E. The wire — how the harness drives a turn

**E1. Host path: SSE on the POST.** `POST /api/conversations/:id/
messages/stream` (`conversation-routes.ts:4058-4062`) runs the whole
turn inside the request and streams `status`, `tool` (phase
call/result/error, callId, toolName, args, result), `token` (deltas;
`delta-v2` protocol), `done` (fullText, thought, usage,
actionResults), `error` (`packages/shared/src/contracts/chat.ts`).
Loopback callers need no token (`loopback-trust.ts:445-487`) unless
`ELIZA_REQUIRE_LOCAL_AUTH=1`. Thought arrives only on `done`; model
calls are not frames. Is that fidelity enough? (reasoning as one
lump at the end; no usage until the end.)

**E2. Library path: in-process.** `runtime.messageService.
handleMessage(runtime, memory, callback, {onStreamChunk,
abortSignal, onSettledActionResult})` (`services/message.ts:13427`;
`types/message-service.ts:26-88`) is the single firehose: text deltas
interleaved with `tool_call`/`tool_result`/`evaluation`/
`context_event` JSON chunks (`message.ts:13930-13963`), plus pipeline
hooks that see the live prompt and result of every model call
(`types/pipeline-hooks.ts:80-241`) and the trajectory recorder that
records args and results of every tool stage
(`runtime/trajectory-recorder.ts:80-160`). Full fidelity — at the
price of a JS entry of our own in the image and a JSON-over-stdio (or
loopback) bridge to the Rust harness. Which path? (This is A1 again,
seen from the stream.)

**E3. Done.** Exactly one `RUN_ENDED` per inbound message
(`message.ts:11666-11782`); on the wire, the `done` frame. Multiple
deliveries per turn are normal (REPLY, progress acks, final
synthesis all call the callback; `provisional:true` marks text the
final reply may replace, `chat-routes.ts:2531-2585`). What is our
rule for provisional text — emit it as `assistant_text` and let a
replacement stand beside it, or hold it?

**E4. Interrupts and the queue.** There is no working abort route
(the UI calls `POST /api/turns/:roomId/abort`; no handler exists;
`turn-controller.ts:160` is unreachable from HTTP); closing the SSE
connection is the only interrupt. HTTP serializes same-room turns
per room (`roomHandlerQueue.withLease`, `chat-routes.ts:4536`);
in-process, same-room turns run concurrently and a newer message
SUPERSEDES an older one's response unless `keepExistingResponses`
(`message.ts:13346-13360, 14673`). Our queue folds a pending prompt
onto the next tool response (the proxy's `/enqueue`), and a prompt
that outlives the turn opens the next one. With E1 the fold works
unchanged (the proxy is upstream of the MCP action); with E2 we could
also inject directly. Same design as hermes, or does Eliza's
supersede semantics offer something better?

**E5. Which endpoint is "the turn"?** Three exist: `POST
/api/agents/:id/message {userId,text}` (synchronous, room
`${agentId}:${userId}`, `chat-routes.ts:5606-5745`), the conversation
routes above, and OpenAI/Anthropic-compatible `/v1/chat/completions`
+ `/v1/messages` (`chat-routes.ts:4870, 5241`). The conversation
stream is the only one with tool frames. Confirm, and confirm what
`/v1/chat/completions` does with history (does it load the room, or
take `messages` as the whole context, the hermes question).

**E6. Readiness.** Port opens BEFORE the runtime exists; `/api/*`
answers 503 until `GET /api/status` says `running` + `canRespond`
(`health-routes.ts:510`); stdout line `[eliza-api] Listening on
http://host:port` (`server.ts:5417`); `EADDRINUSE` silently falls to
an ephemeral port unless `ELIZA_API_STRICT_PORT=1`. The CI smoke
allows 420 s (`docker-ci-smoke.sh:49`). How slow is a cold boot with
PGlite migrations on a fresh dir, and with a large continuation?

**E7. History.** History is the room's `memories` rows (RECENT_
MESSAGES provider); nothing is sent by the caller. Good — matches
`prompt` being the new text only. But `conversationLength`
(constructor) bounds what the provider shows: is that a parameter?

## F. The continuation

**F1. What travels?** Eliza's own agent-backup enumerates the
state: `.elizadb`, `media/`, `.vault-pglite/`, `vault.json`,
`audit/vault.jsonl`, `models/`, `tool-cache/`, `cache/`,
`.activation/`, `backups/`, config file, character
(`packages/agent/src/services/agent-backup-v2-capture.ts:32-42`).
Proposed: PGlite dir + `secret-salt` + `media/`; drop caches, drop
the vault if nothing writes it (D4), drop `eliza.json` (rendered from
the request each run, the hermes rule). Confirm which plugins write
outside the DB (`message-interactions/`, `agent-vfs/`, `auth/`,
`credentials/`, `trajectories/`).

**F2. PGlite portability.** Single process, single connection
(`base.ts:959-961`). The dir contains two elizaOS lock artifacts:
`eliza-pglite.lock` (JSON with the ABSOLUTE dataDir, pid, boot-id,
proc ticks, `manager.ts:509-510, 706-761`) and `postmaster.pid`
(removed by the host at start, `eliza.ts:2839-2851`). Stale-lock
detection is pid/boot-id heuristic (7-day cap) — a copied dir from
another machine may look HELD. Strip both on harvest? On ingest? Is
there any WAL-like fold to do (PGlite is WASM Postgres; does a clean
`adapter.close()` leave the dir consistent, and is the physical file
list — `PG_VERSION`, `base/`, `pg_wal/` — known)? The PGlite package
itself is not vendored; unknown from source.

**F3. Chunking a directory.** Hermes's continuation is three files
with a tag byte each. A PGlite dir is MANY files under a tree. The
protocol keeps chunk boundaries and never holds the whole in memory
— so the tag byte must become a path (a header per chunk: tag, path
length, path, then bytes), or the dir is streamed as an archive
(tar) piece by piece. Which encoding, and is it an SDK matter or
this crate's?

**F4. Secrets encryption.** `character.secrets` are encrypted with
`sha256(SECRET_SALT)` when plugin-sql persists the agents row
(`plugin-sql/src/base.ts:652, 1204, 1278`; `core/src/settings.ts:
202-280`); a new salt makes old ciphertext undecryptable
(`settings.ts:247-257` returns ciphertext unchanged). The host mints
`<stateDir>/secret-salt` (`eliza.ts:4361-4396`). Since auth is an
argument re-applied every run, do we NEED anything encrypted in the
row — or should the harness keep secrets OUT of the character
(`process.env` allowlist copies them IN, `build-character-config.ts:
100-183`) so the salt need not travel?

**F5. The agents row.** `ensureAgentExists` upserts the character
into the DB and merges DB settings back with character-file
precedence (`runtime.ts:3091-3182, 11301-11386`). A continuation thus
carries LAST run's character; this run's request carries the
current. Character-file precedence means the request wins — confirm,
and confirm settings the caller REMOVED do not resurrect from the
row.

**F6. Growth.** Per turn: ≥2 memories + embeddings, 1 central_
messages, 1 logs, 0–N facts/relationships/long_term_memories,
memory_access_logs on reads, trajectories if enabled. Retention
sweepers exist (`runtime/logs-retention-service.ts`,
`memory-retention-service.ts`) — the hermes rule is "never prune the
lineage from inside the continuation". Same here? And `logs` are
diagnostic, not lineage — prune those?

**F7. Session id.** Hermes's continuation answered the session tip.
Eliza has no sessions; the room is the conversation, and the room id
is derived from `(externalId, agentId)` deterministically
(`entities.ts:763-773`). With B3 settled, the fetch answers nothing
beyond the bytes — or does it answer the room id the last run used?

## G. The image and the process

**G1. Base.** The official image is `node:24-slim` (Debian) with
ffmpeg, libopus, tailscale, yt-dlp, a `bun` binary and `tsx`, `npm
install --omit=dev --ignore-scripts` of the workspace
(`packages/app-core/deploy/Dockerfile.ci:59-215`). Our Containerfile
today is Alpine + two musl binaries. `FROM ghcr.io/elizaos/eliza:
stable@sha256:…` (the hermes pattern: the upstream image, our
binaries and entrypoint added) or a Debian node base with a
controlled `npm install` of the minimal set (`@elizaos/agent`,
`plugin-sql`, `plugin-openai`, … at 2.0.3-beta.7)? Unknown whether
the npm set boots outside the workspace closure; CI only builds from
the workspace.

**G2. Node, not Bun, at runtime** (`bin.ts:1` shebang; the image's
CMD is `node --import tsx … bin.js start`). Bun is the build tool.
Fine either way for us — noted so nothing assumes `bun` at runtime.

**G3. Env is the whole configuration.** No `--character`, no
`--port`: `ELIZA_AGENT_CHARACTER_JSON` (inline) or
`ELIZA_CHARACTER_PATH`, `ELIZA_STATE_DIR`, `ELIZA_WORKSPACE_DIR`,
`PGLITE_DATA_DIR`, `ELIZA_PORT`, `ELIZA_API_BIND`, `LOG_LEVEL`,
`SECRET_SALT`, `ELIZA_VAULT_PASSPHRASE`, `ELIZA_PLUGIN_SET`,
`ELIZA_SKIP_PLUGINS`, `OPENAI_*`, `EMBEDDING_*`, `ELIZA_DISABLE_
LOCAL_EMBEDDINGS`, `ELIZA_DISABLE_PROACTIVE_AGENT`,
`NODE_ENV` (`packages/shared/src/runtime-env.ts`;
`sandbox-character.ts:109-159`; `eliza.ts:2749-2840`). Plus
`eliza.json` (JSON5) at `<stateDir>` for `plugins.allow/entries`,
`connectors`, `env.vars`, `serviceRouting`. The harness renders both
from the request (the hermes `filesystem::prepare` shape). Any
setting that can ONLY be reached through the wizard or the UI?

**G4. Workspace.** The host uses cwd as the workspace when it
contains `AGENTS.md/CLAUDE.md/package.json/skills/.git`
(`workspace-resolution.ts:93-155`) — coding-tools and pty run there.
Where do the caller's mounts land, and is the workspace one of them?

**G5. Shutdown.** SIGTERM → `runtime.stop()` (bounded drain) →
`adapter.close()` → exit (`process-lifecycle.ts:63-86`; `eliza.ts:
1656-1720`). Fast mode caps service stops at 500 ms and may cut the
post-turn work (facts, reflection, embedding queue) short
(`runtime.ts:2722-2731`). Harvest after a NON-fast stop, or accept
lost post-turn work?

**G6. Skills.** `plugin-agent-skills` + `@elizaos/skills`; the
Claude-Code-style `SKILL.md` directories under a skills root. Same
