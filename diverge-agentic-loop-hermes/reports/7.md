# Report 7 — clarify in the container: a safe no-op today, a real feature someday

From the pinned source (`sources/hermes-agent`, v0.20.6).

## What it is

A tool that asks the human a question mid-run and BLOCKS the agent
thread on a platform-supplied callback until they answer or a
timeout returns the "use your best judgement" sentinel
(`tools/clarify_tool.py:326-421`, `:31-34`;
`tools/clarify_gateway.py:1-30`).

## What it does on OUR wire

The `hermes-api-server` toolset excludes clarify by design ("no
interactive UI tools", `toolsets.py:442`), and the API server never
wires the callback — it runs its own agent lifecycle and bypasses
the gateway turn path that would set it
(`gateway/platforms/api_server.py:829-832`; zero occurrences of
"clarify" in that file). If a caller force-enables it through
`platform_toolsets`, the tool returns a GRACEFUL error — "Clarify
tool is not available in this execution context"
(`clarify_tool.py:371-374`) — as a tool result the model reads and
moves past. **It never hangs.** (One-shot mode is even tidier: its
callback answers "no user available, pick the best option
yourself", `hermes_cli/oneshot.py:551-567`.)

## The interesting future

Our protocol HAS an answer path clarify was built for: the caller
watches the stream, sees the question, and `enqueue` is a message
into the running conversation. Wiring a clarify callback that
surfaces the question as a chunk and resolves on the next delivered
message would make this a real capability — but it is harness work
plus an upstream-ish integration, not a switch.

## Verdict and recommendation

Headless-safe either way; keeping the `clarify` switch is harmless
(worst case: graceful errors the model routes around), but until
the enqueue wiring exists it buys nothing. Keep or drop by taste;
if kept, its doc should say "currently answers as unavailable on
this wire."
