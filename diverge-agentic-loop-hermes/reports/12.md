# Report 12 — the gateway and the tool response: never truncated, never emitted, and modified before the model sees it

From the pinned source (`sources/hermes-agent`, v0.20.6). Two
questions, answered as fact: does the `/v1/runs` SSE stream ever
truncate the tool response — and does Hermes modify the tool
response it gets back from MCP, and how.

## 1. The SSE stream does not truncate the tool response — it does not carry it

The executor snapshots the FULL result before any context clamp
and hands it to the gateway callback
(`agent/tool_executor.py:2742-2749`, `:2782-2786`; concurrent twin
`:1817-1824`, `:1865-1869`):

```python
agent.tool_progress_callback(
    "tool.completed", function_name, None, None,
    duration=tool_duration, is_error=_is_error_result,
    result=display_function_result,
)
```

The `/v1/runs` callback throws it away
(`gateway/platforms/api_server.py:7526-7534`):

```python
elif event_type == "tool.completed":
    _push({
        "event": "tool.completed",
        "run_id": run_id,
        "timestamp": ts,
        "tool": tool_name,
        "duration": round(kwargs.get("duration", 0), 3),
        "error": kwargs.get("is_error", False),
    })
```

`result=` lands in `**kwargs` and is never read. This is OMISSION,
not truncation: `tool.completed` on `/v1/runs` is name + duration
+ error flag, nothing else. `tool.started` carries an ARGS preview
only (`tool_executor.py:1054-1057`; unlimited by default —
`display.tool_preview_length` defaults 0 = no cap,
`agent/display.py:113`, `gateway/run.py:29244-29246`). There is NO
`tool.progress` and NO `tool.failed` event on `/v1/runs` at all —
`tool.progress` exists only on the session-chat stream and carries
REASONING text, truncated to 500 chars at the source
(`agent/conversation_loop.py:6920`, `_think_text[:500]`); failures
ride `tool.completed` with `error: true`. The transport adds no
caps (`_sse_frame`, `api_server.py:315-316`; unbounded queue
`:7690`). The full result IS available in-process via
`tool_complete_callback` — which `/v1/runs` deliberately does not
wire (`api_server.py:7753-7762`).

**Consequence for our harness:** tool responses can never be
sourced from the gateway's event stream. Our container must emit
its `tool_response` chunks from its own side of the exchange — the
MCP proxy, which sees every result whole — and that is also where
the enqueue-fold SHA already lives. The gateway events supply
timing and the assistant's text; the proxy supplies the tool
traffic.

## 2. Hermes DOES modify the MCP tool response — the pipeline

What the model receives is never the raw text: it is a JSON
envelope built in `tools/mcp_tool.py` (`_call`, `:6145`). Success
path, in order:

1. **Per-block render** (`:6278-6312`): text blocks pass through
   `strip_unicode_tags` (removes plane-14 tag chars U+E0000–E007F,
   the ASCII-smuggling channel; emoji tag sequences preserved —
   `tools/ansi_strip.py:101-115`); image/audio blocks are saved to
   the gateway cache and replaced by `MEDIA:<path>` strings
   (`:1185`, `:1273`; >50 MiB → a bracketed too-large placeholder,
   `:1249`, `_MCP_RESOURCE_MAX_BYTES` `:1194`); `resource_link` →
   `[MCP resource link: uri=… — fetch it with …read_resource]`
   (`:1300-1310`); embedded text resources pass as text
   (`:1316-1318`), embedded blobs are cached to disk and replaced
   by `[MCP resource saved to <path> …]` (`:1348`). Blocks that
   render empty are DROPPED, contributing no separator.
2. **Join with a single `\n`** (`:6313`) — not `\n\n`, not
   nothing.
3. **2,000,000-char hard cap** (`:6317`, `:139`, `:150-158`):
   under it, byte-identical passthrough; over it, head 800,000 +
   `\n\n... [MCP RESULT TRUNCATED - {omitted:,} chars omitted out
   of {total:,} total] ...\n\n` + tail 1,200,000.
4. **Envelope** (`:6349-6368`): `{"result": <text>}` — plus
   `"structuredContent"` when present (kept as a JSON object
   unless its own serialization exceeds 2M, in which case it is
   truncated INTO A STRING, `:6341-6347`), plus filtered `"_meta"`
   (`:6348`, reserved-key strip `:1102-1132`). Structured content
   with EMPTY text becomes the result itself. Serialized
   `json.dumps(..., ensure_ascii=False)` — so the model-visible
   bytes have `\n` and `\"` escapes throughout.

**Error path differs on every count** (`:6248-6264`): blocks
concatenated with NO separator, `strip_unicode_tags` NOT applied,
non-text blocks dropped, then the 2M truncate, then credential
REDACTION (`_sanitize_error`, `:768-774` — `ghp_…`, `sk-…`,
`Bearer …`, `token=/key=/password=` → `[REDACTED]`), then
`tool_error` wraps as `{"error": …}` with a **2048-char cap** +
`… [truncated]` (`tools/registry.py:33-48`, `:1308-1320`) — the
effective error budget is 2 KiB, not 2 M.

Explicitly NOT done: no strip/normalize of whitespace, no ANSI
stripping, no control-char sanitization (raw `\x1b[…]`/`\r`
survive), no `<untrusted>` wrapping, no content rewriting. The
plane-14 tag strip is the only injection defense that mutates
bytes.

**Downstream of mcp_tool.py, model-facing only:** the SSE/display
snapshot is taken BEFORE these, but the model's context gets the
spillover clamps — `mcp_`-prefixed tools have a 50,000-char
per-result budget (`tools/budget_config.py:32`, applied `:106`),
oversize results spill to `$HERMES_HOME/cache/spillover/` and are
replaced in-context by a `<persisted-output>` preview
(`tools/tool_result_storage.py:339-396`; hard-truncation fallback
when no sandbox write is possible, `:392-396`); per-turn aggregate
200,000 chars (`budget_config.py:18`); terminal tool caps itself
at 50,000 chars before any of this (`tools/terminal_tool.py:
3694-3703`, `tool_output_limits.py:39`).

## 3. Consequence for the enqueue-fold SHA

The SHA is computed by OUR proxy over the folded result's text
blocks — upstream of every transform above. Nothing Hermes does to
the string afterward (envelope, join, tag-strip, spillover) can
break correlation, because the caller also receives the tool
response from the proxy's side of the fence, never from Hermes's:
the gateway stream could not carry it even if we wanted it to
(§1), and the model-visible string is a derived artifact (§2), not
the response. The proxy's view is the only byte-faithful one, and
both ends of the correlation already stand on it.
