# Report 1 — the Hermes learning resources

What exists to learn Hermes from, compiled before any crate work.
Hermes Agent is Nous Research's open-source autonomous agent
(released February 2026, v0.2.x line) — Python at the core, MIT
licensed, multi-provider, multi-platform. Everything below is a
resource we can actually use, with what it covers.

## Primary sources

1. **The source repository — `github.com/NousResearch/hermes-agent`
   (MIT).** The single most valuable resource, and clonable the way
   Claude Code's unminified source was for the cc crate — but
   BETTER: it is openly licensed, so "the emitter is truth" research
   needs no caveats, and MIT even permits baking Hermes into our
   image (a licensing posture cc never had; the install-at-startup
   dance may be unnecessary here). Top-level layout worth knowing
   before the clone: `agent/` (core loop), `hermes_cli/` (the CLI),
   `providers/` (LLM provider integrations — the upstream question
   lives here), `gateway/` (messaging platforms), `skills/`,
   `tools/`, `plugins/`, `docker/`, `web/`, entry points `cli.py` /
   `run_agent.py`, `pyproject.toml` (the package's real name and
   deps) + `package.json` (JS components).

2. **The official docs — `hermes-agent.nousresearch.com/docs`,
   sourced from `website/docs/` IN the same repo.** So one clone
   carries both the code and its documentation; the docs can be
   grepped beside the emitters they describe. Known pages of
   particular value to the container work:
   - `reference/cli-commands.md` — the whole CLI surface. Already
     confirmed load-bearing facts: `hermes -z "prompt"` is the pure
     one-shot ("single prompt in, final response text out"),
     `hermes chat --oneshot -q` its richer sibling; `--quiet`
     programmatic mode; `--json` output on several commands;
     `--usage-file <path>` writes a JSON bill (cost, tokens,
     api_calls, model, provider, **session_id**); `hermes chat
     --resume <session>` / `--continue`; `hermes sessions export
     <output> --session-id` exports JSONL; `--provider` /
     `--model` per-run overrides; `--ignore-rules`, `--safe-mode`,
     `--yolo` (the permission-bypass analog); profiles via
     `--profile`.
   - `user-guide/cli.md` — the TUI-side story.
   - config reference / environment variables pages (auth by env is
     stated to exist; exact names need the clone).

3. **The install script — `hermes-agent.nousresearch.com/install.sh`.**
   Canonical install path (`curl | bash`), with `uv` (and plain
   `pip`) underneath. Read it to learn the real package name,
   version pinning story, and what a container install needs.

## Secondary sources

4. **`github.com/mudrii/hermes-agent-docs`** — third-party
   "comprehensive documentation" for v0.2.0. Useful as a second
   opinion and overview; never authoritative over the repo.
5. **`hermes-agent.org`** — a second site presenting the agent
   ("persistent memory" framing). Likely marketing-plus-docs;
   check once, keep only if it says something the repo doesn't.
6. **Nous Portal** — Nous's hosted provider with consolidated OAuth
   (`hermes setup --portal`, `hermes model` wizard). Its docs matter
   for the auth question if the container's identity rides Portal
   rather than a raw provider key.

## Our own prior art

7. **The cc crate** — the sibling-harness template: container

## What the first real read must answer

The questions this crate opens with, mapped to where their answers
live:

- **Does Hermes have its own upstreams?** Yes — it is
  multi-provider by design: Nous Portal, OpenRouter, OpenAI,
  Anthropic, Copilot, custom endpoints (`providers/`, `--provider`
  flag). The design question for OUR agent surface is which of
  those the container exposes — a pinned provider+model pair like
  cc's `model` field, or the whole provider vocabulary.
- **How do we do auth?** Three visible mechanisms: `hermes auth add
  <provider> --api-key`, environment variables, and Portal OAuth.
  The container wants the non-interactive one; the env-var
  reference (from the clone) decides.
- **Continuation shape.** Hermes persists memory, skills, and
  session history in **SQLite** — NOT Claude Code's append-only
  JSONL files. The cc trick (token = the session's files, written
  back before launch) needs re-examination against SQLite (a
  binary file is still a file; `sessions export` JSONL is an
  alternative path). `--resume <session>` exists, so resuming
  itself is supported.
- **Programmatic output.** `-z` prints final text ONLY — no
  stream-json equivalent is visible in the CLI reference so far.
  Whether a structured streaming output exists (or the RPC
  mentioned in the repo — "Python scripts that call tools via
  RPC") decides how the chunk stream gets made.
- **Steering.** No visible enqueue/cancel analog in the CLI
  reference. The queue verbs may need a different mechanism (or
  honest `missed`-only behavior) — to be settled from source.
- **Skills.** Hermes has a first-class `skills/` concept and a
  self-improving skill loop; whether its skill format matches the
  harness-agnostic folder our SDK's `skills` field assumes needs
  checking against `skills/` in the repo.
