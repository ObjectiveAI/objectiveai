# Report 2 — every inference source Hermes speaks to

From the pinned source (`sources/hermes-agent`, `4209d371`,
v0.20.6). Hermes is radically multi-provider: **44 registered
provider profiles from 39 bundled plugins**, all one dataclass —
`ProviderProfile` (`providers/base.py`) — discovered from
`plugins/model-providers/<name>/` at first use
(`providers/__init__.py`), user-overridable via
`$HERMES_HOME/plugins/model-providers/`. Every downstream layer
(auth resolution, model listing, transport kwargs, hostname→provider
mapping, the setup wizard's env-var knowledge) reads from these
profiles; there is no second list.

## The five API modes (the transports)

`api_mode` on the profile picks the wire (`agent/transports/`):

| api_mode | transport | providers |
|---|---|---|
| `chat_completions` (default) | `chat_completions.py` — OpenAI-compatible | the majority |
| `anthropic_messages` | `anthropic.py` | anthropic, minimax(-cn), commandcode-anthropic |
| `codex_responses` | `codex.py` (+ `codex_app_server*.py` for the OAuth Codex backend) | openai-codex, xai, router, actual, meta-ai |
| `bedrock_converse` | `bedrock.py` | bedrock |
| `copilot_acp` | external ACP subprocess, handled in `run_agent.py` | copilot-acp |

One documented quirk: gemini reports `chat_completions` but uses a
custom native client underneath.

## The auth types

`auth_type` on the profile (`providers/base.py:56`):
`api_key` (default) · `oauth_device_code` (nous — the Portal) ·
`oauth_external` (openai-codex, qwen-oauth, minimax-oauth) ·
`copilot` (GitHub token exchange) · `aws_sdk` (bedrock — SDK
credentials, no env key) · `vertex` (service account / ADC) ·
`external_process` (copilot-acp) · keyless (opencode-free — no
account at all). `hermes_cli/auth.py` auto-registers every api-key
profile and special-cases the bespoke-token set: copilot,
kimi-coding(-cn), zai, **openrouter**, custom.

## The roster, grouped

**Aggregators and routers** — openrouter (`OPENROUTER_API_KEY`,
"unified API for 200+ models"; its profile clamps reasoning effort
to the model catalog's advertised levels and knows which Anthropic
models mandate reasoning), ai-gateway (Vercel), router (Ramp Router
— cheapest-model-that-clears-quality routing), kilocode,
opencode-zen / opencode-go / opencode-free (the last keyless),
huggingface (the HF router).

**First-party labs** — nous (Nous Portal,
`inference-api.nousresearch.com`, OAuth device code — the home
team), anthropic (Messages API; env accepts `ANTHROPIC_API_KEY`,
`ANTHROPIC_TOKEN`, **`CLAUDE_CODE_OAUTH_TOKEN`**; aliases include
`claude-code`), openai-codex (the ChatGPT Codex backend over
external OAuth — a subscription ride, not a platform key), gemini
(Google AI Studio), xai, meta-ai (Muse Spark / MSL), deepseek.

**Clouds and hosts** — bedrock (AWS), vertex (GCP), azure-foundry
(user-supplied endpoint), nvidia (NIM), alibaba (DashScope),
nebius-token-factory, novita, deepinfra, fireworks, gmi, upstage
(Solar), ollama-cloud, actual (Actual Computer).

**Coding-plan / subscription tiers** — copilot and copilot-acp
(GitHub Copilot, token-exchange and ACP-subprocess forms),
kimi-coding and kimi-coding-cn (Moonshot), zai (Z.AI / GLM,
`GLM_API_KEY`), qwen-oauth (portal.qwen.ai), alibaba-coding-plan,
commandcode and commandcode-anthropic, minimax / minimax-cn /
minimax-oauth, stepfun (step_plan), xiaomi (MiMo).

**Local and custom** — custom: empty base_url, no fixed key, and its
aliases are the local-runtime vocabulary — `ollama`, `local`,
`vllm`, `llamacpp` — i.e., any OpenAI-compatible endpoint, including
one on localhost.

## The curated defaults

A remotely-hosted model catalog
(`website/docs/reference/model-catalog.md`; live JSON at
`hermes-agent.nousresearch.com/docs/api/model-catalog.json`, in-repo
snapshot fallback) drives picker lists for exactly two providers:
**OpenRouter and Nous Portal** — with `z-ai/glm-5.2` as the shipped
default model on both. That pair is what Hermes itself treats as the
mainstream path.

## What this means for our container

- The agent surface question from report 1 now has its size: the
  provider vocabulary is 44 wide and plugin-extensible — we will
  NOT mirror it. The sane surface is openrouter-style narrowness:
  `provider` (probably a small allowlist, or just a string passed
  through) + `model`, with auth arriving as the provider's own env
  var(s) — which the profiles enumerate exactly.
- **`OPENROUTER_API_KEY` is the same env var our openrouter
  container already rides** — an OpenRouter-backed Hermes container
  could share the credential story wholesale.
- Non-interactive auth is genuinely available for the api-key
  majority (env var in, nothing else); the OAuth tiers
  (nous device-code, openai-codex, qwen, copilot) are interactive
  by nature and likely out of a container's first cut — worth
  stating in the spec rather than discovering later.
- The transports matter for output fidelity later: whatever
  chunk-conversion we build reads Hermes's own session/output
  layer, not the provider wire — but knowing that five API modes
  feed one session store says the session store is the right place
  to look (report 3 territory).
